  153: =head1 DESCRIPTION
  154: 
  155: C<Database::BI::Model::DataSource> is a thin, table-agnostic adapter that
  156: wraps L<Database::Abstraction> and exposes three accessors (C<fetch_all>,
  157: C<columns>, C<id_column>) used by the controller.
  158: 
  159: L<Database::Abstraction> is a read-only ORM that discovers data files
  160: (CSV, PSV, TSV, SQLite, XML, etc.) automatically from a directory based on the
  161: calling class name.  C<DataSource> generates an ephemeral subclass at
  162: construction time so callers never interact with L<Database::Abstraction>
  163: directly.  To swap the backend for L<Database::Join> in Phase 2, only the
  164: C<open_table> helper in C<Database::BI> needs to change; the controller and
  165: C<DataSource> are untouched.
  166: 
  167: C<_detect_file_info> peeks at the first header line of CSV/PSV/TSV files to
  168: extract the correct separator character, the primary-key column name, and
  169: the full ordered column list.  Without this, two silent L<Database::Abstraction>
  170: defaults corrupt every result: C<sep_char> defaults to C<'!'> (turning a
  171: comma-separated file into a single-field table) and C<id> defaults to
  172: C<'entry'> (causing every row to be discarded when no C<entry> column
  173: exists).
  174: 
  175: Result filtering (C<eq>, C<contains>, C<gt>, etc.) is performed at the
  176: controller layer by C<Dashboard::_apply_filter_spec> after C<fetch_all>
  177: returns.  C<DataSource> itself is filter-unaware.
  178: 
  179: All user-visible strings and exception messages are keyed through the
  180: C<%MESSAGES> dictionary and routed via C<_msg()>, making every diagnostic
  181: replaceable by an i18n object at instantiation time.
  182:

  185: =head1 ENCODING
  186: 
  187: =head2 What is safe to put in cell values
  188: 
  189: Cell values (the actual data inside rows) are passed through as Perl
  190: character strings exactly as C<Database::Abstraction> and the underlying
  191: DBI driver return them.  Full Unicode -- including non-ASCII letters,
  192: accented characters, CJK ideographs, and emoji -- is supported in cell
  193: values, provided the source file is encoded in UTF-8 (or the encoding
  194: declared in its HTTP headers for URL-backed tables).
  195: 
  196: =head2 What must stay ASCII
  197: 
  198: The following structural items must contain B<only ASCII characters>:
  199: 
  200: =over 4
  201: 
  202: =item C<table> constructor argument
  203: 
  204: The bare file stem used to look up the file on disk.  Non-ASCII characters
  205: are not valid SQL identifiers and will be silently replaced with underscores
  206: (C<_>) by the sanitization step in C<new()>.
  207: 
  208: =item Column header names (CSV / TSV / PSV first line)
  209: 
  210: Column names are used as hash keys and as SQL identifiers inside
  211: C<Database::Abstraction>.  Non-ASCII headers cause C<DBD::CSV> to
  212: fail or produce garbage keys.  If your source file has non-ASCII
  213: column headers, rename them before opening via C<DataSource>.
  214: 
  215: =item C<host> argument
  216: 
  217: The hostname or C<user@hostname> string for SFTP access.  Must match
  218: C<[A-Za-z0-9._@-]>; anything outside that character set is rejected by
  219: the host-validation regex and produces C<error_backend_init>.
  220: 
  221: =back
  222: 
  223: =head2 URL-backed tables
  224: 
  225: URL-backed tables (the C<url =E<gt>> constructor path) are fetched with
  226: L<LWP::UserAgent::Cached>.  If the remote server declares a charset in its
  227: HTTP headers or in an HTML C<meta> tag, L<Database::Abstraction> uses it
  228: to decode the response body.  If the charset declaration is absent or wrong,
  229: cell values may arrive as raw bytes rather than character strings, and
  230: multi-byte sequences will look garbled.
  231: 
  232: =head2 File-backed tables (CSV / TSV / PSV)
  233: 
  234: For files smaller than 16 KB, L<Text::xSV::Slurp> reads bytes and returns
  235: them without re-encoding; for larger files the L<DBD::CSV> path is used
  236: instead.  In both cases C<DataSource> forces the slurp path (by passing
  237: C<max_slurp_size =E<gt> -s $file>) so that column names with spaces are
  238: preserved as-is.  The caller (the Mojolicious controller) is responsible
  239: for setting the correct C<Content-Type: text/html; charset=UTF-8> response
  240: header.
  241: 
  242: =cut

 2032: =head1 COMMON PITFALLS
 2033: 
 2034: These are the most common mistakes when using C<DataSource>.
 2035: 
 2036: =over 4
 2037: 
 2038: =item B<SQLite databases may use .sql, .sqlite, or .sqlite3 as their file extension>
 2039: 
 2040: C<DataSource> recognises C<.sql>, C<.sqlite>, and C<.sqlite3> as SQLite
 2041: database files.  It does B<not> recognise C<.db3>.  If you have a file called
 2042: C<inventory.db3>, rename it to C<inventory.sql> before passing it to
 2043: C<DataSource>.
 2044: 
 2045: =item B<The table name is always lowercased>
 2046: 
 2047: The constructor lowercases the C<table> argument before using it.  Passing
 2048: C<table =E<gt> 'Sales'> and C<table =E<gt> 'sales'> both look for
 2049: C<sales.csv> (or C<sales.sql>, etc.).  The matching is case-insensitive on the
 2050: table name but B<case-sensitive on the directory path>.
 2051: 
 2052: =item B<CSV files with the wrong separator appear as one giant field per row>
 2053: 
 2054: C<Database::Abstraction> defaults to C<!> (exclamation mark) as its field
 2055: separator.  A standard comma-separated CSV file will look like one big field
 2056: per row (for example, C<1,Widget A,North,100>) because the library never sees
 2057: the commas as separators.  C<DataSource> fixes this automatically by reading
 2058: the first line of the file and detecting the actual separator.  If you bypass
 2059: C<DataSource> and call C<Database::Abstraction> directly, you B<must> pass
 2060: C<sep_char =E<gt> ','> yourself.
 2061: 
 2062: =item B<A table with no "entry" column returns zero rows (without DataSource)>
 2063: 
 2064: C<Database::Abstraction> uses C<entry> as its default primary-key column name.
 2065: When slurping a CSV, it discards any row where C<$row-E<gt>{entry}> is
 2066: undefined.  Because most CSV files do not have an C<entry> column, B<all rows
 2067: are silently discarded>.  C<DataSource> prevents this by reading the actual
 2068: first column name from the CSV header and passing it as C<id>, and also by
 2069: setting C<no_entry =E<gt> 1> so all rows are kept as an ordered array.
 2070: 
 2071: =item B<columns() returns undef for SQLite and XML files>
 2072: 
 2073: C<columns()> only returns an arrayref for file formats where the header order
 2074: is visible before data is read (CSV, TSV and PSV).  For SQLite and XML files it
 2075: returns C<undef>.  Always check: C<if ($source-E<gt>columns) { ... }>.  The
 2076: controller falls back to putting C<id_column> first and then sorting the rest
 2077: alphabetically when C<columns()> is C<undef>.
 2078: 
 2079: =item B<XML elements named "name", "id", or "key" cause parse failures>
 2080: 
 2081: C<XML::Simple> (used by C<Database::Abstraction> for XML files) automatically
 2082: turns a child element called C<name>, C<id>, or C<key> into a hash key instead
 2083: of keeping it as an array element.  This breaks the expected data structure.
 2084: Use different element names in your XML: for example, C<E<lt>skuE<gt>>,
 2085: C<E<lt>labelE<gt>>, or C<E<lt>codeE<gt>> instead of C<E<lt>idE<gt>> and
 2086: C<E<lt>nameE<gt>>.
 2087: 
 2088:   <!-- WRONG: these element names trigger XMLin key-folding -->
 2089:   <items>
 2090:     <item><id>1</id><name>Widget</name></item>
 2091:   </items>
 2092: 
 2093:   <!-- CORRECT: use neutral element names -->
 2094:   <items>
 2095:     <item><sku>1</sku><label>Widget</label></item>
 2096:   </items>
 2097: 
 2098: =item B<fetch_all returns an empty arrayref, not undef, for an empty table>
 2099: 
 2100: When a table exists but contains no data rows, C<fetch_all> returns C<[]> (an
 2101: empty arrayref), not C<undef>.  Check with C<scalar @{$records}>, not with
 2102: C<defined $records> or C<$records>.
 2103: 
 2104: =item B<0-byte CSV/TSV/PSV files bypass Database::Abstraction entirely>
 2105: 
 2106: When C<_detect_file_info> opens a CSV, TSV or PSV file and the first C<readline>
 2107: returns C<undef> (the file is 0 bytes), it returns a C<{ _file_is_empty =E<gt>
 2108: 1 }> sentinel instead of the normal C<{ id, sep_char, columns, file_size }>
 2109: hashref.  C<_init_backend> detects this sentinel and skips
 2110: C<Database::Abstraction> construction; C<fetch_all> returns C<[]> immediately.
 2111: B<No DBI connection is created for 0-byte files.>  If you mock or spy on DBI
 2112: handles and open a 0-byte CSV, the mock will never fire - this is expected
 2113: behaviour, not a mock misconfiguration.
 2114: 
 2115: =item B<Remote files require Net::SFTP::Foreign; one connection per open>
 2116: 
 2117: When C<host> is set, C<DataSource> makes one SFTP connection per C<new()>
 2118: call.  It tries the extension list in order (the C<file_ext> hint first,
 2119: if provided, then the full standard-extension list) and downloads the first
 2120: file it finds.  If no file is found under any tried extension, C<new()>
 2121: croaks C<error_backend_init>.  B<Connections are not pooled or reused>
 2122: between C<DataSource> instances.
 2123: 
 2124: If the remote file has a non-standard extension (e.g. C<.log>, C<.dat>),
 2125: the content is sniffed: SQLite magic bytes map to C<.db>, an XML preamble

 2128: the detected extension before further processing.
 2129: 
 2130: =item B<Multi-table SQLite: opening without internal_table silently picks the first table>
 2131: 
 2132: When a SQLite file contains more than one user-defined table and you call
 2133: C<new()> without C<internal_table>, C<DataSource> auto-selects the first
 2134: table whose name matches the filename stem; if there is no match, it picks
 2135: whatever C<sqlite_master> lists first, skipping any whose name is not a safe
 2136: identifier (letters, digits, underscore).  This is B<silent> -- you get data
 2137: from a table you may not have intended to open.
 2138: 
 2139: Always check C<sqlite_tables()> after construction if you are dealing
 2140: with a SQLite file that might have multiple tables:
 2141: 
 2142:     my $tbl_list = $source->sqlite_tables;
 2143:     if ($tbl_list && @{$tbl_list} > 1) {
 2144:         # warn the user or redirect to the schema browser
 2145:     }
 2146: 
 2147: =item B<The symlink used for .db-extension SQLite files is named .sql, not .db>
 2148: 
 2149: C<Database::Abstraction> does not use its DBI/SQLite backend for files
 2150: with a C<.db> extension -- it falls through to the CSV reader, which tries
 2151: to read a SQLite binary file as text and fails with a parse error.
 2152: 
 2153: When C<DataSource> detects a multi-table SQLite C<.db> file, it creates a
 2154: temporary symlink named C<E<lt>tableE<gt>.sql> (not C<.db>) pointing to the
 2155: original C<.db> file.  SQLite follows symlinks transparently, so the data is
 2156: read correctly.  If you ever audit temporary directories and see C<*.sql>
 2157: symlinks pointing at C<*.db> files, this is expected and intentional.
 2158: 
 2159: =item B<DBD::CSV silently lowercases column names for files larger than 16 KB>
 2160: 
 2161: C<Database::Abstraction> uses C<Text::xSV::Slurp> for files up to 16 KB and
 2162: DBD::CSV for larger ones.  The DBD::CSV path lowercases column names and
 2163: replaces spaces with underscores (C<Account Number> becomes
 2164: C<account_number>), which causes a C<"disallowed key"> error at render time
 2165: when the template iterates the original column names.  C<DataSource> avoids
 2166: this by always passing C<max_slurp_size =E<gt> -s $path> to
 2167: C<Database::Abstraction>, forcing the slurp path regardless of file size.
 2168: If you call C<Database::Abstraction> directly, you B<must> pass this option
 2169: yourself for any file whose column names contain spaces or mixed case.
 2170: 
 2171: =back

 2173: =head1 LIMITATIONS
 2174: 
 2175: =over 4
 2176: 
 2177: =item *
 2178: 
 2179: Only read operations are supported.  Write-back is not in scope.
 2180: 
 2181: =item *
 2182: 
 2183: One C<DataSource> instance corresponds to exactly one table.  Multi-table
 2184: joins are now delegated to C<Database::Join> (see L<Database::Join>), which
 2185: accepts C<DataSource> objects directly as component databases via the
 2186: C<selectall_arrayref> and C<columns> methods this class exposes.
 2187: 
 2188: =item *
 2189: 
 2190: The ephemeral backend class is generated into a package namespace
 2191: (C<Database::BI::_DB::*>) that persists for the lifetime of the process.
 2192: Instantiating two C<DataSource> objects for the same table name reuses
 2193: the same ephemeral class.
 2194: 
 2195: =item *
 2196: 
 2197: The C<i18n> object, if supplied, must implement C<maketext($key, @args)>
 2198: compatible with L<Locale::Maketext>.

 2342: =head1 STATE DIAGRAM
 2343: 
 2344: The lifecycle of a single C<DataSource> object from creation to destruction.
 2345: Each state is stable until the trigger event listed to its right fires.
 2346: 
 2347:     +------------------+
 2348:     |     [START]      |  -- new() called
 2349:     +------------------+
 2350:              |
 2351:              v
 2352:     +------------------+  _detect_file_info + _init_backend run
 2353:     |   INITIALISING   |  (SFTP download, BerkeleyDB probe, SQLite
 2354:     |                  |   sqlite_master probe, CSV header parse,
 2355:     |                  |   XLSX parse, or URL fetch)
 2356:     +------------------+
 2357:           /     \
 2358:          /       \
 2359:         v         v
 2360:   +----------+  +-----------+
 2361:   |  ERROR   |  |   READY   |
 2362:   | (croaks) |  |           |
 2363:   +----------+  +-----------+
 2364:                  |         |
 2365:                  |         |
 2366:     fetch_all()  |         |  selectall_arrayref()
 2367:     called       |         |  called
 2368:                  v         v
 2369:          +---------------+
 2370:          |   FETCHING    |  DBI query or pre-loaded data returned;
 2371:          |               |  result stored in CHI cache (if configured)
 2372:          +---------------+
 2373:                  |
 2374:                  v
 2375:          +---------------+
 2376:          | DATA RETURNED |  arrayref of hashrefs delivered to caller
 2377:          +---------------+
 2378:                  |
 2379:                  | (next call to fetch_all or selectall_arrayref)
 2380:                  v
 2381:          +---------------+
 2382:          | CACHE CHECK   |  CHI cache hit? -> DATA RETURNED immediately
 2383:          |               |  CHI cache miss? -> FETCHING
 2384:          +---------------+
 2385: 
 2386:     Special cases branching from INITIALISING:
 2387: 
 2388:     1. File is 0 bytes or blank first line
 2389:        -> _file_is_empty flag set -> READY (fetch_all returns [] instantly)
 2390: 
 2391:     2. Header-less CSV / XLSX / BerkeleyDB
 2392:        -> _file_data pre-loaded -> READY (fetch_all returns pre-loaded rows)
 2393: 
 2394:     3. Multi-table SQLite without internal_table
 2395:        -> _sqlite_tables set -> READY
 2396:        -> caller inspects sqlite_tables() and may redirect to /tables
 2397:           before calling fetch_all (which would open the auto-selected table)
 2398: 
 2399:     4. Multi-table SQLite WITH internal_table
 2400:        -> symlink created for named table -> READY -> fetch_all opens that table
 2401: 
 2402:     5. SFTP remote file
 2403:        -> Net::SFTP::Foreign::get() -> local tmpdir -> normal init -> READY
 2404:        -> tmpdir kept alive via $self->{_remote_tmpdir} until DESTROY
 2405: 
 2406:     Object lifetime ends when $self goes out of scope:
 2407: 
 2408:     +---------------+
 2409:     |   DESTROY     |  File::Temp tmpdirs auto-cleaned (symlinks removed,
 2410:     |               |  SFTP tmpdir removed)
 2411:     +---------------+
 2412: 
 2413:     Valid state transitions summary:
 2414: 
 2415:     [START]          -> INITIALISING     (new() invoked)
 2416:     INITIALISING     -> ERROR            (croak on bad args, SFTP failure,
 2417:                                           no safe id, no SQLite tables, etc.)
 2418:     INITIALISING     -> READY            (all checks passed)
 2419:     READY            -> FETCHING         (fetch_all / selectall_arrayref, cache miss)
 2420:     READY            -> DATA RETURNED    (fetch_all, _file_is_empty or _file_data fast-path)
 2421:     READY            -> CACHE CHECK      (fetch_all / selectall_arrayref, cache configured)
 2422:     CACHE CHECK      -> DATA RETURNED    (cache hit)
 2423:     CACHE CHECK      -> FETCHING         (cache miss)
 2424:     FETCHING         -> DATA RETURNED    (DBI query completed)
 2425:     DATA RETURNED    -> CACHE CHECK      (next call, cache configured)
 2426:     DATA RETURNED    -> FETCHING         (next call, no cache)
 2427:     READY / DATA RETURNED -> DESTROY     ($self goes out of scope)
