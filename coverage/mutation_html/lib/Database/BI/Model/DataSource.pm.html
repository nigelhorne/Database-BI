  499: This document describes Database::BI::Model::DataSource version 0.01.

  570: =head1 DESCRIPTION
  571: 
  572: C<Database::BI::Model::DataSource> is a thin, table-agnostic adapter that
  573: wraps L<Database::Abstraction> and exposes three accessors (C<fetch_all>,
  574: C<columns>, C<id_column>) used by the controller.
  575: 
  576: L<Database::Abstraction> is a read-only ORM that discovers data files
  577: (CSV, PSV, SQLite, XML, etc.) automatically from a directory based on the
  578: calling class name.  C<DataSource> generates an ephemeral subclass at
  579: construction time so callers never interact with L<Database::Abstraction>
  580: directly.  To swap the backend for L<Database::Join> in Phase 2, only the
  581: C<open_table> helper in C<Database::BI> needs to change; the controller and
  582: C<DataSource> are untouched.
  583: 
  584: C<_detect_file_info> peeks at the first header line of CSV/PSV files to
  585: extract the correct separator character, the primary-key column name, and
  586: the full ordered column list.  Without this, two silent L<Database::Abstraction>
  587: defaults corrupt every result: C<sep_char> defaults to C<'!'> (turning a
  588: comma-separated file into a single-field table) and C<id> defaults to
  589: C<'entry'> (causing every row to be discarded when no C<entry> column
  590: exists).
  591: 
  592: Result filtering (C<eq>, C<contains>, C<gt>, etc.) is performed at the
  593: controller layer by C<Dashboard::_apply_filter_spec> after C<fetch_all>
  594: returns.  C<DataSource> itself is filter-unaware.
  595: 
  596: All user-visible strings and exception messages are keyed through the
  597: C<%MESSAGES> dictionary and routed via C<_msg()>, making every diagnostic
  598: replaceable by an i18n object at instantiation time.
  599: 
  600: =head1 COMMON PITFALLS
  601: 
  602: These are the most common mistakes when using C<DataSource>.
  603: 
  604: =over 4
  605: 
  606: =item B<SQLite databases must use .sql as their file extension>
  607: 
  608: C<Database::Abstraction> looks for SQLite databases with the C<.sql> extension.
  609: It does B<not> recognise C<.sqlite>, C<.sqlite3>, or C<.db3>.  If you have a
  610: file called C<inventory.sqlite>, rename it to C<inventory.sql> before passing
  611: it to C<DataSource>.
  612: 
  613: =item B<The table name is always lowercased>
  614: 
  615: The constructor lowercases the C<table> argument before using it.  Passing
  616: C<table =E<gt> 'Sales'> and C<table =E<gt> 'sales'> both look for
  617: C<sales.csv> (or C<sales.sql>, etc.).  The matching is case-insensitive on the
  618: table name but B<case-sensitive on the directory path>.
  619: 
  620: =item B<CSV files with the wrong separator appear as one giant field per row>
  621: 
  622: C<Database::Abstraction> defaults to C<!> (exclamation mark) as its field
  623: separator.  A standard comma-separated CSV file will look like one big field
  624: per row (for example, C<1,Widget A,North,100>) because the library never sees
  625: the commas as separators.  C<DataSource> fixes this automatically by reading
  626: the first line of the file and detecting the actual separator.  If you bypass
  627: C<DataSource> and call C<Database::Abstraction> directly, you B<must> pass
  628: C<sep_char =E<gt> ','> yourself.
  629: 
  630: =item B<A table with no "entry" column returns zero rows (without DataSource)>
  631: 
  632: C<Database::Abstraction> uses C<entry> as its default primary-key column name.
  633: When slurping a CSV, it discards any row where C<$row-E<gt>{entry}> is
  634: undefined.  Because most CSV files do not have an C<entry> column, B<all rows
  635: are silently discarded>.  C<DataSource> prevents this by reading the actual
  636: first column name from the CSV header and passing it as C<id>, and also by
  637: setting C<no_entry =E<gt> 1> so all rows are kept as an ordered array.
  638: 
  639: =item B<columns() returns undef for SQLite and XML files>
  640: 
  641: C<columns()> only returns an arrayref for file formats where the header order
  642: is visible before data is read (CSV and PSV).  For SQLite and XML files it
  643: returns C<undef>.  Always check: C<if ($source-E<gt>columns) { ... }>.  The
  644: controller falls back to putting C<id_column> first and then sorting the rest
  645: alphabetically when C<columns()> is C<undef>.
  646: 
  647: =item B<XML elements named "name", "id", or "key" cause parse failures>
  648: 
  649: C<XML::Simple> (used by C<Database::Abstraction> for XML files) automatically
  650: turns a child element called C<name>, C<id>, or C<key> into a hash key instead
  651: of keeping it as an array element.  This breaks the expected data structure.
  652: Use different element names in your XML: for example, C<E<lt>skuE<gt>>,
  653: C<E<lt>labelE<gt>>, or C<E<lt>codeE<gt>> instead of C<E<lt>idE<gt>> and
  654: C<E<lt>nameE<gt>>.
  655: 
  656:   <!-- WRONG: these element names trigger XMLin key-folding -->
  657:   <items>
  658:     <item><id>1</id><name>Widget</name></item>
  659:   </items>
  660: 
  661:   <!-- CORRECT: use neutral element names -->
  662:   <items>
  663:     <item><sku>1</sku><label>Widget</label></item>
  664:   </items>
  665: 
  666: =item B<fetch_all returns an empty arrayref, not undef, for an empty table>
  667: 
  668: When a table exists but contains no data rows, C<fetch_all> returns C<[]> (an
  669: empty arrayref), not C<undef>.  Check with C<scalar @{$records}>, not with
  670: C<defined $records> or C<$records>.
  671: 
  672: =back

  674: =head1 LIMITATIONS
  675: 
  676: =over 4
  677: 
  678: =item *
  679: 
  680: Only read operations are supported.  Write-back is not in scope.
  681: 
  682: =item *
  683: 
  684: One C<DataSource> instance corresponds to exactly one table.  Multi-table
  685: left joins are composed at the controller layer by C<Dashboard::_left_join>;
  686: C<Database::Join> (Phase 2) is not yet in use.
  687: 
  688: =item *
  689: 
  690: The ephemeral backend class is generated into a package namespace
  691: (C<Database::BI::_DB::*>) that persists for the lifetime of the process.
  692: Instantiating two C<DataSource> objects for the same table name reuses
  693: the same ephemeral class.
  694: 
  695: =item *
  696: 
  697: The C<i18n> object, if supplied, must implement C<maketext($key, @args)>
  698: compatible with L<Locale::Maketext>.
  699: 
  700: =back
