  518: =head1 SYNOPSIS

  587: =head1 DESCRIPTION
  588: 
  589: C<Database::BI::Model::DataSource> is a thin, table-agnostic adapter that
  590: wraps L<Database::Abstraction> and exposes three accessors (C<fetch_all>,
  591: C<columns>, C<id_column>) used by the controller.
  592: 
  593: L<Database::Abstraction> is a read-only ORM that discovers data files
  594: (CSV, PSV, SQLite, XML, etc.) automatically from a directory based on the
  595: calling class name.  C<DataSource> generates an ephemeral subclass at
  596: construction time so callers never interact with L<Database::Abstraction>
  597: directly.  To swap the backend for L<Database::Join> in Phase 2, only the
  598: C<open_table> helper in C<Database::BI> needs to change; the controller and
  599: C<DataSource> are untouched.
  600: 
  601: C<_detect_file_info> peeks at the first header line of CSV/PSV files to
  602: extract the correct separator character, the primary-key column name, and
  603: the full ordered column list.  Without this, two silent L<Database::Abstraction>
  604: defaults corrupt every result: C<sep_char> defaults to C<'!'> (turning a
  605: comma-separated file into a single-field table) and C<id> defaults to
  606: C<'entry'> (causing every row to be discarded when no C<entry> column
  607: exists).
  608: 
  609: Result filtering (C<eq>, C<contains>, C<gt>, etc.) is performed at the
  610: controller layer by C<Dashboard::_apply_filter_spec> after C<fetch_all>
  611: returns.  C<DataSource> itself is filter-unaware.
  612: 
  613: All user-visible strings and exception messages are keyed through the
  614: C<%MESSAGES> dictionary and routed via C<_msg()>, making every diagnostic
  615: replaceable by an i18n object at instantiation time.
  616: 
  617: =head1 COMMON PITFALLS
  618: 
  619: These are the most common mistakes when using C<DataSource>.
  620: 
  621: =over 4
  622: 
  623: =item B<SQLite databases must use .sql as their file extension>
  624: 
  625: C<Database::Abstraction> looks for SQLite databases with the C<.sql> extension.
  626: It does B<not> recognise C<.sqlite>, C<.sqlite3>, or C<.db3>.  If you have a
  627: file called C<inventory.sqlite>, rename it to C<inventory.sql> before passing
  628: it to C<DataSource>.
  629: 
  630: =item B<The table name is always lowercased>
  631: 
  632: The constructor lowercases the C<table> argument before using it.  Passing
  633: C<table =E<gt> 'Sales'> and C<table =E<gt> 'sales'> both look for
  634: C<sales.csv> (or C<sales.sql>, etc.).  The matching is case-insensitive on the
  635: table name but B<case-sensitive on the directory path>.
  636: 
  637: =item B<CSV files with the wrong separator appear as one giant field per row>
  638: 
  639: C<Database::Abstraction> defaults to C<!> (exclamation mark) as its field
  640: separator.  A standard comma-separated CSV file will look like one big field
  641: per row (for example, C<1,Widget A,North,100>) because the library never sees
  642: the commas as separators.  C<DataSource> fixes this automatically by reading
  643: the first line of the file and detecting the actual separator.  If you bypass
  644: C<DataSource> and call C<Database::Abstraction> directly, you B<must> pass
  645: C<sep_char =E<gt> ','> yourself.
  646: 
  647: =item B<A table with no "entry" column returns zero rows (without DataSource)>
  648: 
  649: C<Database::Abstraction> uses C<entry> as its default primary-key column name.
  650: When slurping a CSV, it discards any row where C<$row-E<gt>{entry}> is
  651: undefined.  Because most CSV files do not have an C<entry> column, B<all rows
  652: are silently discarded>.  C<DataSource> prevents this by reading the actual
  653: first column name from the CSV header and passing it as C<id>, and also by
  654: setting C<no_entry =E<gt> 1> so all rows are kept as an ordered array.
  655: 
  656: =item B<columns() returns undef for SQLite and XML files>
  657: 
  658: C<columns()> only returns an arrayref for file formats where the header order
  659: is visible before data is read (CSV and PSV).  For SQLite and XML files it
  660: returns C<undef>.  Always check: C<if ($source-E<gt>columns) { ... }>.  The
  661: controller falls back to putting C<id_column> first and then sorting the rest
  662: alphabetically when C<columns()> is C<undef>.
  663: 
  664: =item B<XML elements named "name", "id", or "key" cause parse failures>
  665: 
  666: C<XML::Simple> (used by C<Database::Abstraction> for XML files) automatically
  667: turns a child element called C<name>, C<id>, or C<key> into a hash key instead
  668: of keeping it as an array element.  This breaks the expected data structure.
  669: Use different element names in your XML: for example, C<E<lt>skuE<gt>>,
  670: C<E<lt>labelE<gt>>, or C<E<lt>codeE<gt>> instead of C<E<lt>idE<gt>> and
  671: C<E<lt>nameE<gt>>.
  672: 
  673:   <!-- WRONG: these element names trigger XMLin key-folding -->
  674:   <items>
  675:     <item><id>1</id><name>Widget</name></item>
  676:   </items>
  677: 
  678:   <!-- CORRECT: use neutral element names -->
  679:   <items>
  680:     <item><sku>1</sku><label>Widget</label></item>
  681:   </items>
  682: 
  683: =item B<fetch_all returns an empty arrayref, not undef, for an empty table>
  684: 
  685: When a table exists but contains no data rows, C<fetch_all> returns C<[]> (an
  686: empty arrayref), not C<undef>.  Check with C<scalar @{$records}>, not with
  687: C<defined $records> or C<$records>.
  688: 
  689: =back
  690: 
  691: =head1 LIMITATIONS
  692: 
  693: =over 4
  694: 
  695: =item *
  696: 
  697: Only read operations are supported.  Write-back is not in scope.
  698: 
  699: =item *
  700: 
  701: One C<DataSource> instance corresponds to exactly one table.  Multi-table
  702: left joins are composed at the controller layer by C<Dashboard::_left_join>;
  703: C<Database::Join> (Phase 2) is not yet in use.
  704: 
  705: =item *
  706: 
  707: The ephemeral backend class is generated into a package namespace
  708: (C<Database::BI::_DB::*>) that persists for the lifetime of the process.
  709: Instantiating two C<DataSource> objects for the same table name reuses
  710: the same ephemeral class.
  711: 
  712: =item *
  713: 
  714: The C<i18n> object, if supplied, must implement C<maketext($key, @args)>
  715: compatible with L<Locale::Maketext>.
  716: 
  717: =back
