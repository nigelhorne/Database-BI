  153: =head1 DESCRIPTION
  154: 
  155: C<Database::BI::Model::DataSource> is a thin, table-agnostic adapter that
  156: wraps L<Database::Abstraction> and exposes three accessors (C<fetch_all>,
  157: C<columns>, C<id_column>) used by the controller.
  158: 
  159: L<Database::Abstraction> is a read-only ORM that discovers data files
  160: (CSV, PSV, TSV, SQLite, XML, etc.) automatically from a directory based on the
  161: calling class name.  C<DataSource> generates an ephemeral subclass at
  162: construction time so callers never interact with L<Database::Abstraction>
  163: directly.  To swap the backend for L<Database::Join> in Phase 2, only the
  164: C<open_table> helper in C<Database::BI> needs to change; the controller and
  165: C<DataSource> are untouched.
  166: 
  167: C<_detect_file_info> peeks at the first header line of CSV/PSV/TSV files to
  168: extract the correct separator character, the primary-key column name, and
  169: the full ordered column list.  Without this, two silent L<Database::Abstraction>
  170: defaults corrupt every result: C<sep_char> defaults to C<'!'> (turning a
  171: comma-separated file into a single-field table) and C<id> defaults to
  172: C<'entry'> (causing every row to be discarded when no C<entry> column
  173: exists).
  174: 
  175: Result filtering (C<eq>, C<contains>, C<gt>, etc.) is performed at the
  176: controller layer by C<Dashboard::_apply_filter_spec> after C<fetch_all>
  177: returns.  C<DataSource> itself is filter-unaware.
  178: 
  179: All user-visible strings and exception messages are keyed through the
  180: C<%MESSAGES> dictionary and routed via C<_msg()>, making every diagnostic
  181: replaceable by an i18n object at instantiation time.
  182: 
  183: =cut

  185: =head1 ENCODING
  186: 
  187: =head2 What is safe to put in cell values
  188: 
  189: Cell values (the actual data inside rows) are passed through as Perl
  190: character strings exactly as C<Database::Abstraction> and the underlying
  191: DBI driver return them.  Full Unicode -- including non-ASCII letters,
  192: accented characters, CJK ideographs, and emoji -- is supported in cell
  193: values, provided the source file is encoded in UTF-8 (or the encoding
  194: declared in its HTTP headers for URL-backed tables).
  195: 
  196: =head2 What must stay ASCII
  197: 
  198: The following structural items must contain B<only ASCII characters>:
  199: 
  200: =over 4
  201: 
  202: =item C<table> constructor argument
  203: 
  204: The bare file stem used to look up the file on disk.  Non-ASCII characters
  205: are not valid SQL identifiers and will be silently replaced with underscores
  206: (C<_>) by the sanitization step in C<new()>.
  207: 
  208: =item Column header names (CSV / TSV / PSV first line)
  209: 
  210: Column names are used as hash keys and as SQL identifiers inside
  211: C<Database::Abstraction>.  Non-ASCII headers cause C<DBD::CSV> to
  212: fail or produce garbage keys.  If your source file has non-ASCII
  213: column headers, rename them before opening via C<DataSource>.
  214: 
  215: =item C<host> argument
  216: 
  217: The hostname or C<user@hostname> string for SFTP access.  Must match
  218: C<[A-Za-z0-9._@-]>; anything outside that character set is rejected by
  219: the host-validation regex and produces C<error_backend_init>.
  220: 
  221: =back
  222: 
  223: =head2 URL-backed tables
  224: 
  225: URL-backed tables (the C<url =E<gt>> constructor path) are fetched with
  226: L<LWP::UserAgent::Cached>.  If the remote server declares a charset in its
  227: HTTP headers or in an HTML C<meta> tag, L<Database::Abstraction> uses it
  228: to decode the response body.  If the charset declaration is absent or wrong,
  229: cell values may arrive as raw bytes rather than character strings, and
  230: multi-byte sequences will look garbled.
  231: 
  232: =head2 File-backed tables (CSV / TSV / PSV)
  233: 
  234: For files smaller than 16 KB, L<Text::xSV::Slurp> reads bytes and returns
  235: them without re-encoding; for larger files the L<DBD::CSV> path is used
  236: instead.  In both cases C<DataSource> forces the slurp path (by passing
  237: C<max_slurp_size =E<gt> -s $file>) so that column names with spaces are
  238: preserved as-is.  The caller (the Mojolicious controller) is responsible
  239: for setting the correct C<Content-Type: text/html; charset=UTF-8> response
  240: header.
  241: 
  242: =cut

  387: C<internal_table> selects a named table inside a multi-table SQLite file.
  388: When omitted, C<DataSource> auto-selects the first user table whose name
  389: matches the filename stem; if no match, it picks the first table found.
  390: Supplying a name that does not exist in the file croaks C<error_table_not_found>.
  391: 
  392: C<column_order> is for a caller that knows the columns' order better than the
  393: backend does.  A SQLite backend lists its columns alphabetically, so an
  394: extract of an accelerated dataset passes the order its file had.  It is used
  395: only when the file itself gives no order (SQLite, XML), and is trusted, not
  396: checked against the columns the backend has.
  397: 
  398: Accepts a flat key/value list, a hashref, or positional arguments via
  399: C<Params::Get>.
  400: 
  401: When C<host> is provided, C<directory> is treated as a path on the remote
  402: host and is not checked with C<-d> locally.  C<DataSource> downloads the
  403: file via SFTP (L<Net::SFTP::Foreign>) to a process-local temporary directory
  404: and then processes the local copy.  The temporary directory persists for the
  405: lifetime of the C<DataSource> object and is cleaned up automatically on
  406: destruction.
  407: 
  408: When C<file_ext> is provided together with C<host>, it is used as the first
  409: candidate extension when probing the remote host for the file.  If the
  410: downloaded file does not have a standard extension (one of C<csv>, C<tsv>,
  411: C<psv>, C<xlsx>, C<xls>, C<sql>, C<sqlite>, C<sqlite3>, C<db>, C<xml>),
  412: the file content is sniffed (SQLite magic bytes, XML preamble, or first-line
  413: field separator) and the file is renamed to the correct standard extension
  414: before further processing.

 2353: =head1 COMMON PITFALLS
 2354: 
 2355: These are the most common mistakes when using C<DataSource>.
 2356: 
 2357: =over 4
 2358: 
 2359: =item B<SQLite databases may use .sql, .sqlite, or .sqlite3 as their file extension>
 2360: 
 2361: C<DataSource> recognises C<.sql>, C<.sqlite>, and C<.sqlite3> as SQLite
 2362: database files.  It does B<not> recognise C<.db3>.  If you have a file called
 2363: C<inventory.db3>, rename it to C<inventory.sql> before passing it to
 2364: C<DataSource>.
 2365: 
 2366: =item B<The table name is always lowercased>
 2367: 
 2368: The constructor lowercases the C<table> argument before using it.  Passing
 2369: C<table =E<gt> 'Sales'> and C<table =E<gt> 'sales'> both look for
 2370: C<sales.csv> (or C<sales.sql>, etc.).  The matching is case-insensitive on the
 2371: table name but B<case-sensitive on the directory path>.
 2372: 
 2373: =item B<CSV files with the wrong separator appear as one giant field per row>
 2374: 
 2375: C<Database::Abstraction> defaults to C<!> (exclamation mark) as its field
 2376: separator.  A standard comma-separated CSV file will look like one big field
 2377: per row (for example, C<1,Widget A,North,100>) because the library never sees
 2378: the commas as separators.  C<DataSource> fixes this automatically by reading
 2379: the first line of the file and detecting the actual separator.  If you bypass
 2380: C<DataSource> and call C<Database::Abstraction> directly, you B<must> pass
 2381: C<sep_char =E<gt> ','> yourself.
 2382: 
 2383: =item B<A table with no "entry" column returns zero rows (without DataSource)>
 2384: 
 2385: C<Database::Abstraction> uses C<entry> as its default primary-key column name.
 2386: When slurping a CSV, it discards any row where C<$row-E<gt>{entry}> is
 2387: undefined.  Because most CSV files do not have an C<entry> column, B<all rows
 2388: are silently discarded>.  C<DataSource> prevents this by reading the actual
 2389: first column name from the CSV header and passing it as C<id>, and also by
 2390: setting C<no_entry =E<gt> 1> so all rows are kept as an ordered array.
 2391: 
 2392: =item B<columns() returns undef for SQLite and XML files>
 2393: 
 2394: C<columns()> only returns an arrayref for file formats where the header order
 2395: is visible before data is read (CSV, TSV and PSV).  For SQLite and XML files it
 2396: returns C<undef>.  Always check: C<if ($source-E<gt>columns) { ... }>.  The
 2397: controller falls back to putting C<id_column> first and then sorting the rest
 2398: alphabetically when C<columns()> is C<undef>.
 2399: 
 2400: =item B<XML elements named "name", "id", or "key" cause parse failures>
 2401: 
 2402: C<XML::Simple> (used by C<Database::Abstraction> for XML files) automatically
 2403: turns a child element called C<name>, C<id>, or C<key> into a hash key instead
 2404: of keeping it as an array element.  This breaks the expected data structure.
 2405: Use different element names in your XML: for example, C<E<lt>skuE<gt>>,
 2406: C<E<lt>labelE<gt>>, or C<E<lt>codeE<gt>> instead of C<E<lt>idE<gt>> and
 2407: C<E<lt>nameE<gt>>.
 2408: 
 2409:   <!-- WRONG: these element names trigger XMLin key-folding -->
 2410:   <items>
 2411:     <item><id>1</id><name>Widget</name></item>
 2412:   </items>
 2413: 
 2414:   <!-- CORRECT: use neutral element names -->
 2415:   <items>
 2416:     <item><sku>1</sku><label>Widget</label></item>
 2417:   </items>
 2418: 
 2419: =item B<fetch_all returns an empty arrayref, not undef, for an empty table>
 2420: 
 2421: When a table exists but contains no data rows, C<fetch_all> returns C<[]> (an
 2422: empty arrayref), not C<undef>.  Check with C<scalar @{$records}>, not with
 2423: C<defined $records> or C<$records>.
 2424: 
 2425: =item B<0-byte CSV/TSV/PSV files bypass Database::Abstraction entirely>
 2426: 
 2427: When C<_detect_file_info> opens a CSV, TSV or PSV file and the first C<readline>
 2428: returns C<undef> (the file is 0 bytes), it returns a C<{ _file_is_empty =E<gt>
 2429: 1 }> sentinel instead of the normal C<{ id, sep_char, columns, file_size }>
 2430: hashref.  C<_init_backend> detects this sentinel and skips
 2431: C<Database::Abstraction> construction; C<fetch_all> returns C<[]> immediately.
 2432: B<No DBI connection is created for 0-byte files.>  If you mock or spy on DBI
 2433: handles and open a 0-byte CSV, the mock will never fire - this is expected
 2434: behaviour, not a mock misconfiguration.
 2435: 
 2436: =item B<Remote files require Net::SFTP::Foreign; one connection per open>
 2437: 
 2438: When C<host> is set, C<DataSource> makes one SFTP connection per C<new()>
 2439: call.  It tries the extension list in order (the C<file_ext> hint first,
 2440: if provided, then the full standard-extension list) and downloads the first
 2441: file it finds.  If no file is found under any tried extension, C<new()>
 2442: croaks C<error_backend_init>.  B<Connections are not pooled or reused>
 2443: between C<DataSource> instances.
 2444: 
 2445: If the remote file has a non-standard extension (e.g. C<.log>, C<.dat>),
 2446: the content is sniffed: SQLite magic bytes map to C<.db>, an XML preamble
 2447: to C<.xml>, a tab-delimited first line to C<.tsv>, a pipe-delimited line to
 2448: C<.psv>, and everything else to C<.csv>.  The temp file is then renamed to
 2449: the detected extension before further processing.
 2450: 
 2451: =item B<Multi-table SQLite: opening without internal_table silently picks the first table>
 2452: 
 2453: When a SQLite file contains more than one user-defined table and you call
 2454: C<new()> without C<internal_table>, C<DataSource> auto-selects the first
 2455: table whose name matches the filename stem; if there is no match, it picks
 2456: whatever C<sqlite_master> lists first, skipping any whose name is not a safe
 2457: identifier (letters, digits, underscore).  This is B<silent> -- you get data
 2458: from a table you may not have intended to open.
 2459: 
 2460: Always check C<sqlite_tables()> after construction if you are dealing
 2461: with a SQLite file that might have multiple tables:
 2462: 
 2463:     my $tbl_list = $source->sqlite_tables;
 2464:     if ($tbl_list && @{$tbl_list} > 1) {
 2465:         # warn the user or redirect to the schema browser
 2466:     }
 2467: 
 2468: =item B<The symlink used for .db-extension SQLite files is named .sql, not .db>
 2469: 
 2470: C<Database::Abstraction> does not use its DBI/SQLite backend for files
 2471: with a C<.db> extension -- it falls through to the CSV reader, which tries
 2472: to read a SQLite binary file as text and fails with a parse error.
 2473: 
 2474: When C<DataSource> detects a SQLite C<.db> file, it creates a
 2475: temporary symlink named C<E<lt>tableE<gt>.sql> (not C<.db>) pointing to the
 2476: original C<.db> file.  SQLite follows symlinks transparently, so the data is
 2477: read correctly.  If you ever audit temporary directories and see C<*.sql>
 2478: symlinks pointing at C<*.db> files, this is expected and intentional.
 2479: 
 2480: =item B<DBD::CSV silently lowercases column names for files larger than 16 KB>
 2481: 
 2482: C<Database::Abstraction> uses C<Text::xSV::Slurp> for files up to 16 KB and
 2483: DBD::CSV for larger ones.  The DBD::CSV path lowercases column names and
 2484: replaces spaces with underscores (C<Account Number> becomes
 2485: C<account_number>), which causes a C<"disallowed key"> error at render time
 2486: when the template iterates the original column names.  C<DataSource> avoids
 2487: this by always passing C<max_slurp_size =E<gt> -s $path> to
 2488: C<Database::Abstraction>, forcing the slurp path regardless of file size.
 2489: If you call C<Database::Abstraction> directly, you B<must> pass this option
 2490: yourself for any file whose column names contain spaces or mixed case.
 2491: 
 2492: =back

 2663: =head1 STATE DIAGRAM
 2664: 
 2665: The lifecycle of a single C<DataSource> object from creation to destruction.
 2666: Each state is stable until the trigger event listed to its right fires.
 2667: 
 2668:     +------------------+
 2669:     |     [START]      |  -- new() called
 2670:     +------------------+
 2671:              |
 2672:              v
 2673:     +------------------+  File source: _detect_file_info + _init_backend run
 2674:     |   INITIALISING   |  (SFTP download, BerkeleyDB probe, SQLite
 2675:     |                  |   sqlite_master probe, CSV header parse, XLSX parse).
 2676:     |                  |  URL or Redis source: the backend object is built, and
 2677:     |                  |  nothing is fetched or connected to until the first read.
 2678:     +------------------+
 2679:           /     \
 2680:          /       \
 2681:         v         v
 2682:   +-----------+  +-----------+
 2683:   |  ERROR    |  |   READY   |
 2684:   | (croaks;  |  |           |
 2685:   | no object)|  |           |
 2686:   +-----------+  +-----------+
 2687:                        |
 2688:                        |  fetch_all() or selectall_arrayref(), from READY,
 2689:                        |  DATA RETURNED or FETCH ERROR
 2690:                        |
 2691:        +---------------+-------------------+------------------+
 2692:        | cache configured, | no cache, or  | _file_is_empty   |
 2693:        | a call for the    | a narrowed    |                  |
 2694:        | whole table       | query         |                  |
 2695:        v                   |               |                  |
 2696:   +---------------+        |               |                  |
 2697:   | CACHE CHECK   |        |               |                  |
 2698:   +---------------+        |               |                  |
 2699:      |         |           |               |                  |
 2700:      | hit     | miss, or  |               |                  |
 2701:      |         | no key    |               |                  |
 2702:      |         v           v               |                  |
 2703:      |    +---------------------+          |                  |
 2704:      |    |     FETCHING        |  backend read; the result   |
 2705:      |    |                     |  is stored in the cache if  |
 2706:      |    |                     |  it was looked up there     |
 2707:      |    +---------------------+          |                  |
 2708:      |         |            |              |                  |
 2709:      |         | answered   | failed       |                  |
 2710:      |         |            v              |                  |
 2711:      |         |      +-------------+      |                  |
 2712:      |         |      | FETCH ERROR |      |                  |
 2713:      |         |      | (croaks;    |      |                  |
 2714:      |         |      | object and  |      |                  |
 2715:      |         |      | cache sound)|      |                  |
 2716:      |         |      +-------------+      |                  |
 2717:      v         v                           v                  v
 2718:   +---------------------------------------------------------------+
 2719:   |                        DATA RETURNED                          |
 2720:   +---------------------------------------------------------------+
 2721: 
 2722:     DATA RETURNED delivers an arrayref of hashrefs to the caller, with one
 2723:     exception: selectall_arrayref with no rows to answer with (a table with none,
 2724:     or a narrowed query that matches none) usually answers undef, where fetch_all
 2725:     answers [].
 2726: 
 2727:     A "call for the whole table" is fetch_all, or selectall_arrayref with no
 2728:     arguments, or with only a sort_by on a column that is not a safe identifier and
 2729:     perhaps a limit and offset (DataSource sorts and pages those itself, over the
 2730:     whole table).  Any other arguments
 2731:     make a narrowed query, which is neither looked up in the cache nor stored in
 2732:     it, because its result is not the table.
 2733: 
 2734:     The cache has no key to look under when the file has gone since new(): no
 2735:     lookup is made and nothing is stored, and the read goes on to FETCHING.
 2736: 
 2737:     FETCH ERROR comes from the backend failing, a table with no file (which new()
 2738:     does not notice), a URL that cannot be fetched or does not answer with rows,
 2739:     or a Redis server that cannot be reached.  Unlike ERROR there is an object, and
 2740:     the next read starts again.
 2741: 
 2742:     Other reads (columns, count, aggregate, schema, updated and the like) go to the
 2743:     backend directly, without the cache, and do not change the state.
 2744: 
 2745:     Special cases branching from INITIALISING:
 2746: 
 2747:     1. A 0-byte CSV, TSV or PSV, one with a blank first line, or an XLSX with a
 2748:        blank first worksheet
 2749:        -> _file_is_empty flag set, no backend -> READY (fetch_all and
 2750:           selectall_arrayref return [] instantly, and count returns 0)
 2751:        A 0-byte SQLite file is not this case: it has no tables -> ERROR
 2752: 
 2753:     2. Header-less CSV, TSV or PSV
 2754:        -> copy with a header written to a temporary directory -> READY
 2755:           (Database::Abstraction reads the copy)
 2756: 
 2757:     3. SQLite without internal_table
 2758:        -> _sqlite_tables set -> READY
 2759:        -> caller inspects sqlite_tables() and may redirect to /tables
 2760:           before calling fetch_all (which would open the auto-selected table:
 2761:           the one named after the file, else the first by name that can be opened)
 2762: 
 2763:     4. SQLite WITH internal_table
 2764:        -> a table it does not have, or one with an unsafe name -> ERROR
 2765:        -> otherwise _sqlite_tables set, plus a symlink if the table's name is not
 2766:           the file's -> READY -> fetch_all opens that table
 2767: 
 2768:     5. SFTP remote file
 2769:        -> Net::SFTP::Foreign::get() -> local tmpdir -> normal init -> READY
 2770:        -> tmpdir kept alive via $self->{_remote_tmpdir} until DESTROY
 2771: 
 2772:     Object lifetime ends when $self goes out of scope:
 2773: 
 2774:     +---------------+
 2775:     |   DESTROY     |  File::Temp tmpdirs auto-cleaned (symlinks removed,
 2776:     |               |  copies removed, SFTP tmpdir removed)
 2777:     +---------------+
 2778: 
 2779:     Valid state transitions summary:
 2780: 
 2781:     [START]          -> INITIALISING     (new() invoked)
 2782:     INITIALISING     -> ERROR            (croak on bad args, SFTP failure, no safe id, no SQLite tables, a file that will not open, etc.)
 2783:     INITIALISING     -> READY            (all checks passed)
 2784:     READY            -> FETCHING         (no cache configured, or a narrowed query)
 2785:     READY            -> DATA RETURNED    (fetch_all / selectall_arrayref, _file_is_empty fast-path)
 2786:     READY            -> CACHE CHECK      (a call for the whole table, cache configured)
 2787:     CACHE CHECK      -> DATA RETURNED    (cache hit)
 2788:     CACHE CHECK      -> FETCHING         (cache miss, or no key to look under)
 2789:     FETCHING         -> DATA RETURNED    (backend answered)
 2790:     FETCHING         -> FETCH ERROR      (backend failed; croaks)
 2791:     DATA RETURNED    -> DATA RETURNED    (next call, _file_is_empty fast-path)
 2792:     DATA RETURNED    -> CACHE CHECK      (next call for the whole table, cache configured)
 2793:     DATA RETURNED    -> FETCHING         (next call, no cache, or a narrowed query)
 2794:     FETCH ERROR      -> CACHE CHECK      (next call for the whole table, cache configured)
 2795:     FETCH ERROR      -> FETCHING         (next call, no cache, or a narrowed query)
 2796:     READY / DATA RETURNED / FETCH ERROR -> DESTROY     ($self goes out of scope)
