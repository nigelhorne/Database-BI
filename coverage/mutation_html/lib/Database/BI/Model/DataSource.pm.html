  153: =head1 DESCRIPTION
  154: 
  155: C<Database::BI::Model::DataSource> is a thin, table-agnostic adapter that
  156: wraps L<Database::Abstraction> and exposes three accessors (C<fetch_all>,
  157: C<columns>, C<id_column>) used by the controller.
  158: 
  159: L<Database::Abstraction> is a read-only ORM that discovers data files
  160: (CSV, PSV, TSV, SQLite, XML, etc.) automatically from a directory based on the
  161: calling class name.  C<DataSource> generates an ephemeral subclass at
  162: construction time so callers never interact with L<Database::Abstraction>
  163: directly.  To swap the backend for L<Database::Join> in Phase 2, only the
  164: C<open_table> helper in C<Database::BI> needs to change; the controller and
  165: C<DataSource> are untouched.
  166: 
  167: C<_detect_file_info> peeks at the first header line of CSV/PSV/TSV files to
  168: extract the correct separator character, the primary-key column name, and
  169: the full ordered column list.  Without this, two silent L<Database::Abstraction>
  170: defaults corrupt every result: C<sep_char> defaults to C<'!'> (turning a
  171: comma-separated file into a single-field table) and C<id> defaults to
  172: C<'entry'> (causing every row to be discarded when no C<entry> column
  173: exists).
  174: 
  175: Result filtering (C<eq>, C<contains>, C<gt>, etc.) is performed at the
  176: controller layer by C<Dashboard::_apply_filter_spec> after C<fetch_all>
  177: returns.  C<DataSource> itself is filter-unaware.
  178: 
  179: All user-visible strings and exception messages are keyed through the
  180: C<%MESSAGES> dictionary and routed via C<_msg()>, making every diagnostic
  181: replaceable by an i18n object at instantiation time.
  182: 
  183: =cut

  185: =head1 ENCODING
  186: 
  187: =head2 What is safe to put in cell values
  188: 
  189: Cell values (the actual data inside rows) are passed through as Perl
  190: character strings exactly as C<Database::Abstraction> and the underlying
  191: DBI driver return them.  Full Unicode -- including non-ASCII letters,
  192: accented characters, CJK ideographs, and emoji -- is supported in cell
  193: values, provided the source file is encoded in UTF-8 (or the encoding
  194: declared in its HTTP headers for URL-backed tables).
  195: 
  196: =head2 What must stay ASCII
  197: 
  198: The following structural items must contain B<only ASCII characters>:
  199: 
  200: =over 4
  201: 
  202: =item C<table> constructor argument
  203: 
  204: The bare file stem used to look up the file on disk.  Non-ASCII characters
  205: are not valid SQL identifiers and will be silently replaced with underscores
  206: (C<_>) by the sanitization step in C<new()>.
  207: 
  208: =item Column header names (CSV / TSV / PSV first line)
  209: 
  210: Column names are used as hash keys and as SQL identifiers inside
  211: C<Database::Abstraction>.  Non-ASCII headers cause C<DBD::CSV> to
  212: fail or produce garbage keys.  If your source file has non-ASCII
  213: column headers, rename them before opening via C<DataSource>.
  214: 
  215: =item C<host> argument
  216: 
  217: The hostname or C<user@hostname> string for SFTP access.  Must match
  218: C<[A-Za-z0-9._@-]>; anything outside that character set is rejected by
  219: the host-validation regex and produces C<error_backend_init>.
  220: 
  221: =back
  222: 
  223: =head2 URL-backed tables
  224: 
  225: URL-backed tables (the C<url =E<gt>> constructor path) are fetched with
  226: L<LWP::UserAgent::Cached>.  If the remote server declares a charset in its
  227: HTTP headers or in an HTML C<meta> tag, L<Database::Abstraction> uses it
  228: to decode the response body.  If the charset declaration is absent or wrong,
  229: cell values may arrive as raw bytes rather than character strings, and
  230: multi-byte sequences will look garbled.
  231: 
  232: =head2 File-backed tables (CSV / TSV / PSV)
  233: 
  234: For files smaller than 16 KB, L<Text::xSV::Slurp> reads bytes and returns
  235: them without re-encoding; for larger files the L<DBD::CSV> path is used
  236: instead.  In both cases C<DataSource> forces the slurp path (by passing
  237: C<max_slurp_size =E<gt> -s $file>) so that column names with spaces are
  238: preserved as-is.  The caller (the Mojolicious controller) is responsible
  239: for setting the correct C<Content-Type: text/html; charset=UTF-8> response
  240: header.

 2127: =head1 COMMON PITFALLS
 2128: 
 2129: These are the most common mistakes when using C<DataSource>.
 2130: 
 2131: =over 4
 2132: 
 2133: =item B<SQLite databases may use .sql, .sqlite, or .sqlite3 as their file extension>
 2134: 
 2135: C<DataSource> recognises C<.sql>, C<.sqlite>, and C<.sqlite3> as SQLite
 2136: database files.  It does B<not> recognise C<.db3>.  If you have a file called
 2137: C<inventory.db3>, rename it to C<inventory.sql> before passing it to
 2138: C<DataSource>.
 2139: 
 2140: =item B<The table name is always lowercased>
 2141: 
 2142: The constructor lowercases the C<table> argument before using it.  Passing
 2143: C<table =E<gt> 'Sales'> and C<table =E<gt> 'sales'> both look for
 2144: C<sales.csv> (or C<sales.sql>, etc.).  The matching is case-insensitive on the
 2145: table name but B<case-sensitive on the directory path>.
 2146: 
 2147: =item B<CSV files with the wrong separator appear as one giant field per row>
 2148: 
 2149: C<Database::Abstraction> defaults to C<!> (exclamation mark) as its field
 2150: separator.  A standard comma-separated CSV file will look like one big field
 2151: per row (for example, C<1,Widget A,North,100>) because the library never sees
 2152: the commas as separators.  C<DataSource> fixes this automatically by reading
 2153: the first line of the file and detecting the actual separator.  If you bypass
 2154: C<DataSource> and call C<Database::Abstraction> directly, you B<must> pass
 2155: C<sep_char =E<gt> ','> yourself.
 2156: 
 2157: =item B<A table with no "entry" column returns zero rows (without DataSource)>
 2158: 
 2159: C<Database::Abstraction> uses C<entry> as its default primary-key column name.
 2160: When slurping a CSV, it discards any row where C<$row-E<gt>{entry}> is
 2161: undefined.  Because most CSV files do not have an C<entry> column, B<all rows
 2162: are silently discarded>.  C<DataSource> prevents this by reading the actual
 2163: first column name from the CSV header and passing it as C<id>, and also by
 2164: setting C<no_entry =E<gt> 1> so all rows are kept as an ordered array.
 2165: 
 2166: =item B<columns() returns undef for SQLite and XML files>
 2167: 
 2168: C<columns()> only returns an arrayref for file formats where the header order
 2169: is visible before data is read (CSV, TSV and PSV).  For SQLite and XML files it
 2170: returns C<undef>.  Always check: C<if ($source-E<gt>columns) { ... }>.  The
 2171: controller falls back to putting C<id_column> first and then sorting the rest
 2172: alphabetically when C<columns()> is C<undef>.
 2173: 
 2174: =item B<XML elements named "name", "id", or "key" cause parse failures>
 2175: 
 2176: C<XML::Simple> (used by C<Database::Abstraction> for XML files) automatically
 2177: turns a child element called C<name>, C<id>, or C<key> into a hash key instead
 2178: of keeping it as an array element.  This breaks the expected data structure.
 2179: Use different element names in your XML: for example, C<E<lt>skuE<gt>>,
 2180: C<E<lt>labelE<gt>>, or C<E<lt>codeE<gt>> instead of C<E<lt>idE<gt>> and
 2181: C<E<lt>nameE<gt>>.
 2182: 
 2183:   <!-- WRONG: these element names trigger XMLin key-folding -->
 2184:   <items>
 2185:     <item><id>1</id><name>Widget</name></item>
 2186:   </items>
 2187: 
 2188:   <!-- CORRECT: use neutral element names -->
 2189:   <items>
 2190:     <item><sku>1</sku><label>Widget</label></item>
 2191:   </items>
 2192: 
 2193: =item B<fetch_all returns an empty arrayref, not undef, for an empty table>
 2194: 
 2195: When a table exists but contains no data rows, C<fetch_all> returns C<[]> (an
 2196: empty arrayref), not C<undef>.  Check with C<scalar @{$records}>, not with
 2197: C<defined $records> or C<$records>.
 2198: 
 2199: =item B<0-byte CSV/TSV/PSV files bypass Database::Abstraction entirely>
 2200: 
 2201: When C<_detect_file_info> opens a CSV, TSV or PSV file and the first C<readline>
 2202: returns C<undef> (the file is 0 bytes), it returns a C<{ _file_is_empty =E<gt>
 2203: 1 }> sentinel instead of the normal C<{ id, sep_char, columns, file_size }>
 2204: hashref.  C<_init_backend> detects this sentinel and skips
 2205: C<Database::Abstraction> construction; C<fetch_all> returns C<[]> immediately.
 2206: B<No DBI connection is created for 0-byte files.>  If you mock or spy on DBI
 2207: handles and open a 0-byte CSV, the mock will never fire - this is expected
 2208: behaviour, not a mock misconfiguration.
 2209: 
 2210: =item B<Remote files require Net::SFTP::Foreign; one connection per open>
 2211: 
 2212: When C<host> is set, C<DataSource> makes one SFTP connection per C<new()>
 2213: call.  It tries the extension list in order (the C<file_ext> hint first,
 2214: if provided, then the full standard-extension list) and downloads the first
 2215: file it finds.  If no file is found under any tried extension, C<new()>
 2216: croaks C<error_backend_init>.  B<Connections are not pooled or reused>
 2217: between C<DataSource> instances.
 2218: 
 2219: If the remote file has a non-standard extension (e.g. C<.log>, C<.dat>),
 2220: the content is sniffed: SQLite magic bytes map to C<.db>, an XML preamble
 2221: to C<.xml>, a tab-delimited first line to C<.tsv>, a pipe-delimited line to
 2222: C<.psv>, and everything else to C<.csv>.  The temp file is then renamed to
 2223: the detected extension before further processing.
 2224: 
 2225: =item B<Multi-table SQLite: opening without internal_table silently picks the first table>
 2226: 
 2227: When a SQLite file contains more than one user-defined table and you call
 2228: C<new()> without C<internal_table>, C<DataSource> auto-selects the first
 2229: table whose name matches the filename stem; if there is no match, it picks
 2230: whatever C<sqlite_master> lists first, skipping any whose name is not a safe
 2231: identifier (letters, digits, underscore).  This is B<silent> -- you get data
 2232: from a table you may not have intended to open.
 2233: 
 2234: Always check C<sqlite_tables()> after construction if you are dealing
 2235: with a SQLite file that might have multiple tables:
 2236: 
 2237:     my $tbl_list = $source->sqlite_tables;
 2238:     if ($tbl_list && @{$tbl_list} > 1) {
 2239:         # warn the user or redirect to the schema browser
 2240:     }
 2241: 
 2242: =item B<The symlink used for .db-extension SQLite files is named .sql, not .db>
 2243: 
 2244: C<Database::Abstraction> does not use its DBI/SQLite backend for files
 2245: with a C<.db> extension -- it falls through to the CSV reader, which tries
 2246: to read a SQLite binary file as text and fails with a parse error.
 2247: 
 2248: When C<DataSource> detects a multi-table SQLite C<.db> file, it creates a
 2249: temporary symlink named C<E<lt>tableE<gt>.sql> (not C<.db>) pointing to the
 2250: original C<.db> file.  SQLite follows symlinks transparently, so the data is
 2251: read correctly.  If you ever audit temporary directories and see C<*.sql>
 2252: symlinks pointing at C<*.db> files, this is expected and intentional.
 2253: 
 2254: =item B<DBD::CSV silently lowercases column names for files larger than 16 KB>
 2255: 
 2256: C<Database::Abstraction> uses C<Text::xSV::Slurp> for files up to 16 KB and
 2257: DBD::CSV for larger ones.  The DBD::CSV path lowercases column names and
 2258: replaces spaces with underscores (C<Account Number> becomes
 2259: C<account_number>), which causes a C<"disallowed key"> error at render time
 2260: when the template iterates the original column names.  C<DataSource> avoids
 2261: this by always passing C<max_slurp_size =E<gt> -s $path> to
 2262: C<Database::Abstraction>, forcing the slurp path regardless of file size.
 2263: If you call C<Database::Abstraction> directly, you B<must> pass this option
 2264: yourself for any file whose column names contain spaces or mixed case.
 2265: 
 2266: =back

 2268: =head1 LIMITATIONS
 2269: 
 2270: =over 4
 2271: 
 2272: =item *
 2273: 
 2274: Only read operations are supported.  Write-back is not in scope.
 2275: 
 2276: =item *
 2277: 
 2278: One C<DataSource> instance corresponds to exactly one table.  Multi-table
 2279: joins are now delegated to C<Database::Join> (see L<Database::Join>), which
 2280: accepts C<DataSource> objects directly as component databases via the
 2281: C<selectall_arrayref> and C<columns> methods this class exposes.
 2282: 
 2283: =item *
 2284: 
 2285: The ephemeral backend class is generated into a package namespace
 2286: (C<Database::BI::_DB::*>) that persists for the lifetime of the process.
 2287: Instantiating two C<DataSource> objects for the same table name reuses
 2288: the same ephemeral class.
 2289: 
 2290: =item *
 2291: 
 2292: The C<i18n> object, if supplied, must implement C<maketext($key, @args)>
 2293: compatible with L<Locale::Maketext>.

 2444:     +------------------+
 2445:              |
 2446:              v
 2447:     +------------------+  _detect_file_info + _init_backend run
 2448:     |   INITIALISING   |  (SFTP download, BerkeleyDB probe, SQLite
 2449:     |                  |   sqlite_master probe, CSV header parse,
 2450:     |                  |   XLSX parse, or URL fetch)
 2451:     +------------------+
 2452:           /     \
 2453:          /       \
 2454:         v         v
 2455:   +----------+  +-----------+
 2456:   |  ERROR   |  |   READY   |
 2457:   | (croaks) |  |           |
 2458:   +----------+  +-----------+
 2459:                  |         |
 2460:                  |         |
 2461:     fetch_all()  |         |  selectall_arrayref()
 2462:     called       |         |  called
 2463:                  v         v
 2464:          +---------------+
 2465:          |   FETCHING    |  DBI query or pre-loaded data returned;
 2466:          |               |  result stored in CHI cache (if configured)
 2467:          +---------------+
 2468:                  |
 2469:                  v
 2470:          +---------------+
 2471:          | DATA RETURNED |  arrayref of hashrefs delivered to caller
 2472:          +---------------+
 2473:                  |
