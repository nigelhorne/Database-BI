  498: Database::BI::Model::DataSource - Table-agnostic adapter around Database::Abstraction
  499: 
  500: =head1 VERSION

  502: This document describes Database::BI::Model::DataSource version 0.01.
  503:

  573: =head1 DESCRIPTION
  574: 
  575: C<Database::BI::Model::DataSource> is a thin, table-agnostic adapter that
  576: wraps L<Database::Abstraction> and exposes three accessors (C<fetch_all>,
  577: C<columns>, C<id_column>) used by the controller.
  578: 
  579: L<Database::Abstraction> is a read-only ORM that discovers data files
  580: (CSV, PSV, SQLite, XML, etc.) automatically from a directory based on the
  581: calling class name.  C<DataSource> generates an ephemeral subclass at
  582: construction time so callers never interact with L<Database::Abstraction>
  583: directly.  To swap the backend for L<Database::Join> in Phase 2, only the
  584: C<open_table> helper in C<Database::BI> needs to change; the controller and
  585: C<DataSource> are untouched.
  586: 
  587: C<_detect_file_info> peeks at the first header line of CSV/PSV files to
  588: extract the correct separator character, the primary-key column name, and
  589: the full ordered column list.  Without this, two silent L<Database::Abstraction>
  590: defaults corrupt every result: C<sep_char> defaults to C<'!'> (turning a
  591: comma-separated file into a single-field table) and C<id> defaults to
  592: C<'entry'> (causing every row to be discarded when no C<entry> column
  593: exists).
  594: 
  595: Result filtering (C<eq>, C<contains>, C<gt>, etc.) is performed at the
  596: controller layer by C<Dashboard::_apply_filter_spec> after C<fetch_all>
  597: returns.  C<DataSource> itself is filter-unaware.
  598: 
  599: All user-visible strings and exception messages are keyed through the
  600: C<%MESSAGES> dictionary and routed via C<_msg()>, making every diagnostic
  601: replaceable by an i18n object at instantiation time.
  602: 
  603: =head1 COMMON PITFALLS
  604: 
  605: These are the most common mistakes when using C<DataSource>.
  606: 
  607: =over 4
  608: 
  609: =item B<SQLite databases must use .sql as their file extension>
  610: 
  611: C<Database::Abstraction> looks for SQLite databases with the C<.sql> extension.
  612: It does B<not> recognise C<.sqlite>, C<.sqlite3>, or C<.db3>.  If you have a
  613: file called C<inventory.sqlite>, rename it to C<inventory.sql> before passing
  614: it to C<DataSource>.
  615: 
  616: =item B<The table name is always lowercased>
  617: 
  618: The constructor lowercases the C<table> argument before using it.  Passing
  619: C<table =E<gt> 'Sales'> and C<table =E<gt> 'sales'> both look for
  620: C<sales.csv> (or C<sales.sql>, etc.).  The matching is case-insensitive on the
  621: table name but B<case-sensitive on the directory path>.
  622: 
  623: =item B<CSV files with the wrong separator appear as one giant field per row>
  624: 
  625: C<Database::Abstraction> defaults to C<!> (exclamation mark) as its field
  626: separator.  A standard comma-separated CSV file will look like one big field
  627: per row (for example, C<1,Widget A,North,100>) because the library never sees
  628: the commas as separators.  C<DataSource> fixes this automatically by reading
  629: the first line of the file and detecting the actual separator.  If you bypass
  630: C<DataSource> and call C<Database::Abstraction> directly, you B<must> pass
  631: C<sep_char =E<gt> ','> yourself.
  632: 
  633: =item B<A table with no "entry" column returns zero rows (without DataSource)>
  634: 
  635: C<Database::Abstraction> uses C<entry> as its default primary-key column name.
  636: When slurping a CSV, it discards any row where C<$row-E<gt>{entry}> is
  637: undefined.  Because most CSV files do not have an C<entry> column, B<all rows
  638: are silently discarded>.  C<DataSource> prevents this by reading the actual
  639: first column name from the CSV header and passing it as C<id>, and also by
  640: setting C<no_entry =E<gt> 1> so all rows are kept as an ordered array.
  641: 
  642: =item B<columns() returns undef for SQLite and XML files>
  643: 
  644: C<columns()> only returns an arrayref for file formats where the header order
  645: is visible before data is read (CSV and PSV).  For SQLite and XML files it
  646: returns C<undef>.  Always check: C<if ($source-E<gt>columns) { ... }>.  The
  647: controller falls back to putting C<id_column> first and then sorting the rest
  648: alphabetically when C<columns()> is C<undef>.
  649: 
  650: =item B<XML elements named "name", "id", or "key" cause parse failures>
  651: 
  652: C<XML::Simple> (used by C<Database::Abstraction> for XML files) automatically
  653: turns a child element called C<name>, C<id>, or C<key> into a hash key instead
  654: of keeping it as an array element.  This breaks the expected data structure.
  655: Use different element names in your XML: for example, C<E<lt>skuE<gt>>,
  656: C<E<lt>labelE<gt>>, or C<E<lt>codeE<gt>> instead of C<E<lt>idE<gt>> and
  657: C<E<lt>nameE<gt>>.
  658: 
  659:   <!-- WRONG: these element names trigger XMLin key-folding -->
  660:   <items>
  661:     <item><id>1</id><name>Widget</name></item>
  662:   </items>
  663: 
  664:   <!-- CORRECT: use neutral element names -->
  665:   <items>
  666:     <item><sku>1</sku><label>Widget</label></item>
  667:   </items>
  668: 
  669: =item B<fetch_all returns an empty arrayref, not undef, for an empty table>
  670: 
  671: When a table exists but contains no data rows, C<fetch_all> returns C<[]> (an
  672: empty arrayref), not C<undef>.  Check with C<scalar @{$records}>, not with
  673: C<defined $records> or C<$records>.
  674: 
  675: =back

  677: =head1 LIMITATIONS
  678: 
  679: =over 4
  680: 
  681: =item *
  682: 
  683: Only read operations are supported.  Write-back is not in scope.
  684: 
  685: =item *
  686: 
  687: One C<DataSource> instance corresponds to exactly one table.  Multi-table
  688: left joins are composed at the controller layer by C<Dashboard::_left_join>;
  689: C<Database::Join> (Phase 2) is not yet in use.
  690: 
  691: =item *
  692: 
  693: The ephemeral backend class is generated into a package namespace
  694: (C<Database::BI::_DB::*>) that persists for the lifetime of the process.
  695: Instantiating two C<DataSource> objects for the same table name reuses
  696: the same ephemeral class.
  697: 
  698: =item *
  699: 
  700: The C<i18n> object, if supplied, must implement C<maketext($key, @args)>
  701: compatible with L<Locale::Maketext>.
  702: 
  703: =back
