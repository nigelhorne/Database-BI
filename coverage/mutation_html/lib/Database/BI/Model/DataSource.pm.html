  153: =head1 DESCRIPTION
  154: 
  155: C<Database::BI::Model::DataSource> is a thin, table-agnostic adapter that
  156: wraps L<Database::Abstraction> and exposes three accessors (C<fetch_all>,
  157: C<columns>, C<id_column>) used by the controller.
  158: 
  159: L<Database::Abstraction> is a read-only ORM that discovers data files
  160: (CSV, PSV, TSV, SQLite, XML, etc.) automatically from a directory based on the
  161: calling class name.  C<DataSource> generates an ephemeral subclass at
  162: construction time so callers never interact with L<Database::Abstraction>
  163: directly.  To swap the backend for L<Database::Join> in Phase 2, only the
  164: C<open_table> helper in C<Database::BI> needs to change; the controller and
  165: C<DataSource> are untouched.
  166: 
  167: C<_detect_file_info> peeks at the first header line of CSV/PSV/TSV files to
  168: extract the correct separator character, the primary-key column name, and
  169: the full ordered column list.  Without this, two silent L<Database::Abstraction>
  170: defaults corrupt every result: C<sep_char> defaults to C<'!'> (turning a
  171: comma-separated file into a single-field table) and C<id> defaults to
  172: C<'entry'> (causing every row to be discarded when no C<entry> column
  173: exists).
  174: 
  175: Result filtering (C<eq>, C<contains>, C<gt>, etc.) is performed at the
  176: controller layer by C<Dashboard::_apply_filter_spec> after C<fetch_all>
  177: returns.  C<DataSource> itself is filter-unaware.
  178: 
  179: All user-visible strings and exception messages are keyed through the
  180: C<%MESSAGES> dictionary and routed via C<_msg()>, making every diagnostic
  181: replaceable by an i18n object at instantiation time.
  182: 
  183: =cut

  185: =head1 ENCODING
  186: 
  187: =head2 What is safe to put in cell values
  188: 
  189: Cell values (the actual data inside rows) are passed through as Perl
  190: character strings exactly as C<Database::Abstraction> and the underlying
  191: DBI driver return them.  Full Unicode -- including non-ASCII letters,
  192: accented characters, CJK ideographs, and emoji -- is supported in cell
  193: values, provided the source file is encoded in UTF-8 (or the encoding
  194: declared in its HTTP headers for URL-backed tables).
  195: 
  196: =head2 What must stay ASCII
  197: 
  198: The following structural items must contain B<only ASCII characters>:
  199: 
  200: =over 4
  201: 
  202: =item C<table> constructor argument
  203: 
  204: The bare file stem used to look up the file on disk.  Non-ASCII characters
  205: are not valid SQL identifiers and will be silently replaced with underscores
  206: (C<_>) by the sanitization step in C<new()>.
  207: 
  208: =item Column header names (CSV / TSV / PSV first line)
  209: 
  210: Column names are used as hash keys and as SQL identifiers inside
  211: C<Database::Abstraction>.  Non-ASCII headers cause C<DBD::CSV> to
  212: fail or produce garbage keys.  If your source file has non-ASCII
  213: column headers, rename them before opening via C<DataSource>.
  214: 
  215: =item C<host> argument
  216: 
  217: The hostname or C<user@hostname> string for SFTP access.  Must match
  218: C<[A-Za-z0-9._@-]>; anything outside that character set is rejected by
  219: the host-validation regex and produces C<error_backend_init>.
  220: 
  221: =back
  222: 
  223: =head2 URL-backed tables
  224: 
  225: URL-backed tables (the C<url =E<gt>> constructor path) are fetched with
  226: L<LWP::UserAgent::Cached>.  If the remote server declares a charset in its
  227: HTTP headers or in an HTML C<meta> tag, L<Database::Abstraction> uses it
  228: to decode the response body.  If the charset declaration is absent or wrong,
  229: cell values may arrive as raw bytes rather than character strings, and
  230: multi-byte sequences will look garbled.
  231: 
  232: =head2 File-backed tables (CSV / TSV / PSV)
  233: 
  234: For files smaller than 16 KB, L<Text::xSV::Slurp> reads bytes and returns
  235: them without re-encoding; for larger files the L<DBD::CSV> path is used
  236: instead.  In both cases C<DataSource> forces the slurp path (by passing
  237: C<max_slurp_size =E<gt> -s $file>) so that column names with spaces are
  238: preserved as-is.  The caller (the Mojolicious controller) is responsible
  239: for setting the correct C<Content-Type: text/html; charset=UTF-8> response
  240: header.
  241: 
  242: =cut

 1961: =head1 COMMON PITFALLS
 1962: 
 1963: These are the most common mistakes when using C<DataSource>.
 1964: 
 1965: =over 4
 1966: 
 1967: =item B<SQLite databases may use .sql, .sqlite, or .sqlite3 as their file extension>
 1968: 
 1969: C<DataSource> recognises C<.sql>, C<.sqlite>, and C<.sqlite3> as SQLite
 1970: database files.  It does B<not> recognise C<.db3>.  If you have a file called
 1971: C<inventory.db3>, rename it to C<inventory.sql> before passing it to
 1972: C<DataSource>.
 1973: 
 1974: =item B<The table name is always lowercased>
 1975: 
 1976: The constructor lowercases the C<table> argument before using it.  Passing
 1977: C<table =E<gt> 'Sales'> and C<table =E<gt> 'sales'> both look for
 1978: C<sales.csv> (or C<sales.sql>, etc.).  The matching is case-insensitive on the
 1979: table name but B<case-sensitive on the directory path>.
 1980: 
 1981: =item B<CSV files with the wrong separator appear as one giant field per row>
 1982: 
 1983: C<Database::Abstraction> defaults to C<!> (exclamation mark) as its field
 1984: separator.  A standard comma-separated CSV file will look like one big field
 1985: per row (for example, C<1,Widget A,North,100>) because the library never sees
 1986: the commas as separators.  C<DataSource> fixes this automatically by reading
 1987: the first line of the file and detecting the actual separator.  If you bypass
 1988: C<DataSource> and call C<Database::Abstraction> directly, you B<must> pass
 1989: C<sep_char =E<gt> ','> yourself.
 1990: 
 1991: =item B<A table with no "entry" column returns zero rows (without DataSource)>
 1992: 
 1993: C<Database::Abstraction> uses C<entry> as its default primary-key column name.
 1994: When slurping a CSV, it discards any row where C<$row-E<gt>{entry}> is
 1995: undefined.  Because most CSV files do not have an C<entry> column, B<all rows
 1996: are silently discarded>.  C<DataSource> prevents this by reading the actual
 1997: first column name from the CSV header and passing it as C<id>, and also by
 1998: setting C<no_entry =E<gt> 1> so all rows are kept as an ordered array.
 1999: 
 2000: =item B<columns() returns undef for SQLite and XML files>
 2001: 
 2002: C<columns()> only returns an arrayref for file formats where the header order
 2003: is visible before data is read (CSV, TSV and PSV).  For SQLite and XML files it
 2004: returns C<undef>.  Always check: C<if ($source-E<gt>columns) { ... }>.  The
 2005: controller falls back to putting C<id_column> first and then sorting the rest
 2006: alphabetically when C<columns()> is C<undef>.
 2007: 
 2008: =item B<XML elements named "name", "id", or "key" cause parse failures>
 2009: 
 2010: C<XML::Simple> (used by C<Database::Abstraction> for XML files) automatically
 2011: turns a child element called C<name>, C<id>, or C<key> into a hash key instead
 2012: of keeping it as an array element.  This breaks the expected data structure.
 2013: Use different element names in your XML: for example, C<E<lt>skuE<gt>>,
 2014: C<E<lt>labelE<gt>>, or C<E<lt>codeE<gt>> instead of C<E<lt>idE<gt>> and
 2015: C<E<lt>nameE<gt>>.
 2016: 
 2017:   <!-- WRONG: these element names trigger XMLin key-folding -->
 2018:   <items>
 2019:     <item><id>1</id><name>Widget</name></item>
 2020:   </items>
 2021: 
 2022:   <!-- CORRECT: use neutral element names -->
 2023:   <items>
 2024:     <item><sku>1</sku><label>Widget</label></item>
 2025:   </items>
 2026: 
 2027: =item B<fetch_all returns an empty arrayref, not undef, for an empty table>
 2028: 
 2029: When a table exists but contains no data rows, C<fetch_all> returns C<[]> (an
 2030: empty arrayref), not C<undef>.  Check with C<scalar @{$records}>, not with
 2031: C<defined $records> or C<$records>.
 2032: 
 2033: =item B<0-byte CSV/TSV/PSV files bypass Database::Abstraction entirely>
 2034: 
 2035: When C<_detect_file_info> opens a CSV, TSV or PSV file and the first C<readline>
 2036: returns C<undef> (the file is 0 bytes), it returns a C<{ _file_is_empty =E<gt>
 2037: 1 }> sentinel instead of the normal C<{ id, sep_char, columns, file_size }>
 2038: hashref.  C<_init_backend> detects this sentinel and skips
 2039: C<Database::Abstraction> construction; C<fetch_all> returns C<[]> immediately.
 2040: B<No DBI connection is created for 0-byte files.>  If you mock or spy on DBI
 2041: handles and open a 0-byte CSV, the mock will never fire - this is expected
 2042: behaviour, not a mock misconfiguration.
 2043: 
 2044: =item B<Remote files require Net::SFTP::Foreign; one connection per open>
 2045: 
 2046: When C<host> is set, C<DataSource> makes one SFTP connection per C<new()>
 2047: call.  It tries the extension list in order (the C<file_ext> hint first,
 2048: if provided, then the full standard-extension list) and downloads the first
 2049: file it finds.  If no file is found under any tried extension, C<new()>
 2050: croaks C<error_backend_init>.  B<Connections are not pooled or reused>
 2051: between C<DataSource> instances.
 2052: 
 2053: If the remote file has a non-standard extension (e.g. C<.log>, C<.dat>),
 2054: the content is sniffed: SQLite magic bytes map to C<.db>, an XML preamble
 2055: to C<.xml>, a tab-delimited first line to C<.tsv>, a pipe-delimited line to
 2056: C<.psv>, and everything else to C<.csv>.  The temp file is then renamed to
 2057: the detected extension before further processing.
 2058: 
 2059: =item B<Multi-table SQLite: opening without internal_table silently picks the first table>
 2060: 
 2061: When a SQLite file contains more than one user-defined table and you call
 2062: C<new()> without C<internal_table>, C<DataSource> auto-selects the first
 2063: table whose name matches the filename stem; if there is no match, it picks
 2064: whatever C<sqlite_master> lists first.  This is B<silent> -- you get data
 2065: from a table you may not have intended to open.
 2066: 
 2067: Always check C<sqlite_tables()> after construction if you are dealing
 2068: with a SQLite file that might have multiple tables:
 2069: 
 2070:     my $tbl_list = $source->sqlite_tables;
 2071:     if ($tbl_list && @{$tbl_list} > 1) {
 2072:         # warn the user or redirect to the schema browser
 2073:     }
 2074: 
 2075: =item B<The symlink used for .db-extension SQLite files is named .sql, not .db>
 2076: 
 2077: C<Database::Abstraction> does not use its DBI/SQLite backend for files
 2078: with a C<.db> extension -- it falls through to the CSV reader, which tries
 2079: to read a SQLite binary file as text and fails with a parse error.
 2080: 
 2081: When C<DataSource> detects a multi-table SQLite C<.db> file, it creates a
 2082: temporary symlink named C<E<lt>tableE<gt>.sql> (not C<.db>) pointing to the
 2083: original C<.db> file.  SQLite follows symlinks transparently, so the data is
 2084: read correctly.  If you ever audit temporary directories and see C<*.sql>
 2085: symlinks pointing at C<*.db> files, this is expected and intentional.
 2086: 
 2087: =item B<DBD::CSV silently lowercases column names for files larger than 16 KB>
 2088: 
 2089: C<Database::Abstraction> uses C<Text::xSV::Slurp> for files up to 16 KB and
 2090: DBD::CSV for larger ones.  The DBD::CSV path lowercases column names and
 2091: replaces spaces with underscores (C<Account Number> becomes
 2092: C<account_number>), which causes a C<"disallowed key"> error at render time
 2093: when the template iterates the original column names.  C<DataSource> avoids
 2094: this by always passing C<max_slurp_size =E<gt> -s $path> to
 2095: C<Database::Abstraction>, forcing the slurp path regardless of file size.
 2096: If you call C<Database::Abstraction> directly, you B<must> pass this option
 2097: yourself for any file whose column names contain spaces or mixed case.
