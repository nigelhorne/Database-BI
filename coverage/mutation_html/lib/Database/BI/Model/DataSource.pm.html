  117: =head1 DESCRIPTION
  118: 
  119: C<Database::BI::Model::DataSource> is a thin, table-agnostic adapter that
  120: wraps L<Database::Abstraction> and exposes three accessors (C<fetch_all>,
  121: C<columns>, C<id_column>) used by the controller.
  122: 
  123: L<Database::Abstraction> is a read-only ORM that discovers data files
  124: (CSV, PSV, TSV, SQLite, XML, etc.) automatically from a directory based on the
  125: calling class name.  C<DataSource> generates an ephemeral subclass at
  126: construction time so callers never interact with L<Database::Abstraction>
  127: directly.  To swap the backend for L<Database::Join> in Phase 2, only the
  128: C<open_table> helper in C<Database::BI> needs to change; the controller and
  129: C<DataSource> are untouched.
  130: 
  131: C<_detect_file_info> peeks at the first header line of CSV/PSV/TSV files to
  132: extract the correct separator character, the primary-key column name, and
  133: the full ordered column list.  Without this, two silent L<Database::Abstraction>
  134: defaults corrupt every result: C<sep_char> defaults to C<'!'> (turning a
  135: comma-separated file into a single-field table) and C<id> defaults to
  136: C<'entry'> (causing every row to be discarded when no C<entry> column
  137: exists).
  138: 
  139: Result filtering (C<eq>, C<contains>, C<gt>, etc.) is performed at the
  140: controller layer by C<Dashboard::_apply_filter_spec> after C<fetch_all>
  141: returns.  C<DataSource> itself is filter-unaware.
  142: 
  143: All user-visible strings and exception messages are keyed through the
  144: C<%MESSAGES> dictionary and routed via C<_msg()>, making every diagnostic
  145: replaceable by an i18n object at instantiation time.
  146: 
  147: =head2 UTF-8 and Encoding
  148: 
  149: C<DataSource> passes cell values through as Perl character strings exactly
  150: as L<Database::Abstraction> and the underlying DBI driver return them.
  151: For CSV, TSV and PSV files smaller than 16 KB, L<Text::xSV::Slurp> is used and
  152: bytes are returned without re-encoding; for larger files the L<DBD::CSV>
  153: path is used.  In both cases the caller (the controller) is responsible
  154: for setting the correct C<Content-Type> header.
  155: 
  156: The C<table> argument and all column names must be B<ASCII-only>
  157: identifiers.  Full Unicode is supported inside B<cell values> -- the
  158: restriction applies only to structural metadata (column headers, table
  159: name), not to the data itself.
  160: 
  161: URL-backed tables (the C<url =E<gt>> constructor path) are fetched with
  162: L<LWP::UserAgent::Cached>.  If the remote server declares a charset in
  163: its HTTP headers or HTML meta tag, L<Database::Abstraction> uses it to
  164: decode the response body.  If the declaration is absent or wrong, cell
  165: values may contain raw bytes rather than character strings.

 1293: =head1 COMMON PITFALLS
 1294: 
 1295: These are the most common mistakes when using C<DataSource>.
 1296: 
 1297: =over 4
 1298: 
 1299: =item B<SQLite databases may use .sql, .sqlite, or .sqlite3 as their file extension>
 1300: 
 1301: C<DataSource> recognises C<.sql>, C<.sqlite>, and C<.sqlite3> as SQLite
 1302: database files.  It does B<not> recognise C<.db3>.  If you have a file called
 1303: C<inventory.db3>, rename it to C<inventory.sql> before passing it to
 1304: C<DataSource>.
 1305: 
 1306: =item B<The table name is always lowercased>
 1307: 
 1308: The constructor lowercases the C<table> argument before using it.  Passing
 1309: C<table =E<gt> 'Sales'> and C<table =E<gt> 'sales'> both look for
 1310: C<sales.csv> (or C<sales.sql>, etc.).  The matching is case-insensitive on the
 1311: table name but B<case-sensitive on the directory path>.
 1312: 
 1313: =item B<CSV files with the wrong separator appear as one giant field per row>
 1314: 
 1315: C<Database::Abstraction> defaults to C<!> (exclamation mark) as its field
 1316: separator.  A standard comma-separated CSV file will look like one big field
 1317: per row (for example, C<1,Widget A,North,100>) because the library never sees
 1318: the commas as separators.  C<DataSource> fixes this automatically by reading
 1319: the first line of the file and detecting the actual separator.  If you bypass
 1320: C<DataSource> and call C<Database::Abstraction> directly, you B<must> pass
 1321: C<sep_char =E<gt> ','> yourself.
 1322: 
 1323: =item B<A table with no "entry" column returns zero rows (without DataSource)>
 1324: 
 1325: C<Database::Abstraction> uses C<entry> as its default primary-key column name.
 1326: When slurping a CSV, it discards any row where C<$row-E<gt>{entry}> is
 1327: undefined.  Because most CSV files do not have an C<entry> column, B<all rows
 1328: are silently discarded>.  C<DataSource> prevents this by reading the actual
 1329: first column name from the CSV header and passing it as C<id>, and also by
 1330: setting C<no_entry =E<gt> 1> so all rows are kept as an ordered array.
 1331: 
 1332: =item B<columns() returns undef for SQLite and XML files>
 1333: 
 1334: C<columns()> only returns an arrayref for file formats where the header order
 1335: is visible before data is read (CSV, TSV and PSV).  For SQLite and XML files it
 1336: returns C<undef>.  Always check: C<if ($source-E<gt>columns) { ... }>.  The
 1337: controller falls back to putting C<id_column> first and then sorting the rest
 1338: alphabetically when C<columns()> is C<undef>.
 1339: 
 1340: =item B<XML elements named "name", "id", or "key" cause parse failures>
 1341: 
 1342: C<XML::Simple> (used by C<Database::Abstraction> for XML files) automatically
 1343: turns a child element called C<name>, C<id>, or C<key> into a hash key instead
 1344: of keeping it as an array element.  This breaks the expected data structure.
 1345: Use different element names in your XML: for example, C<E<lt>skuE<gt>>,
 1346: C<E<lt>labelE<gt>>, or C<E<lt>codeE<gt>> instead of C<E<lt>idE<gt>> and
 1347: C<E<lt>nameE<gt>>.
 1348: 
 1349:   <!-- WRONG: these element names trigger XMLin key-folding -->
 1350:   <items>
 1351:     <item><id>1</id><name>Widget</name></item>
 1352:   </items>
 1353: 
 1354:   <!-- CORRECT: use neutral element names -->
 1355:   <items>
 1356:     <item><sku>1</sku><label>Widget</label></item>
 1357:   </items>
 1358: 
 1359: =item B<fetch_all returns an empty arrayref, not undef, for an empty table>
 1360: 
 1361: When a table exists but contains no data rows, C<fetch_all> returns C<[]> (an
 1362: empty arrayref), not C<undef>.  Check with C<scalar @{$records}>, not with
 1363: C<defined $records> or C<$records>.
 1364: 
 1365: =item B<0-byte CSV/TSV/PSV files bypass Database::Abstraction entirely>
 1366: 
 1367: When C<_detect_file_info> opens a CSV, TSV or PSV file and the first C<readline>
 1368: returns C<undef> (the file is 0 bytes), it returns a C<{ _file_is_empty =E<gt>
 1369: 1 }> sentinel instead of the normal C<{ id, sep_char, columns, file_size }>
 1370: hashref.  C<_init_backend> detects this sentinel and skips
 1371: C<Database::Abstraction> construction; C<fetch_all> returns C<[]> immediately.
 1372: B<No DBI connection is created for 0-byte files.>  If you mock or spy on DBI
 1373: handles and open a 0-byte CSV, the mock will never fire - this is expected
 1374: behaviour, not a mock misconfiguration.
 1375: 
 1376: =item B<Remote files require Net::SFTP::Foreign; one connection per open>
 1377: 
 1378: When C<host> is set, C<DataSource> makes one SFTP connection per C<new()>
 1379: call.  It tries the extension list in order (the C<file_ext> hint first,
 1380: if provided, then the full standard-extension list) and downloads the first
 1381: file it finds.  If no file is found under any tried extension, C<new()>
 1382: croaks C<error_backend_init>.  B<Connections are not pooled or reused>
 1383: between C<DataSource> instances.
 1384: 
 1385: If the remote file has a non-standard extension (e.g. C<.log>, C<.dat>),
 1386: the content is sniffed: SQLite magic bytes map to C<.db>, an XML preamble
 1387: to C<.xml>, a tab-delimited first line to C<.tsv>, a pipe-delimited line to
 1388: C<.psv>, and everything else to C<.csv>.  The temp file is then renamed to
 1389: the detected extension before further processing.
 1390: 
 1391: =item B<DBD::CSV silently lowercases column names for files larger than 16 KB>
 1392: 
 1393: C<Database::Abstraction> uses C<Text::xSV::Slurp> for files up to 16 KB and
 1394: DBD::CSV for larger ones.  The DBD::CSV path lowercases column names and
 1395: replaces spaces with underscores (C<Account Number> becomes
 1396: C<account_number>), which causes a C<"disallowed key"> error at render time
 1397: when the template iterates the original column names.  C<DataSource> avoids
 1398: this by always passing C<max_slurp_size =E<gt> -s $path> to
 1399: C<Database::Abstraction>, forcing the slurp path regardless of file size.
 1400: If you call C<Database::Abstraction> directly, you B<must> pass this option
 1401: yourself for any file whose column names contain spaces or mixed case.
 1402: 
 1403: =back

 1405: =head1 LIMITATIONS
 1406: 
 1407: =over 4
 1408: 
 1409: =item *
 1410: 
 1411: Only read operations are supported.  Write-back is not in scope.
 1412: 
 1413: =item *
 1414: 
 1415: One C<DataSource> instance corresponds to exactly one table.  Multi-table
 1416: joins are now delegated to C<Database::Join> (see L<Database::Join>), which
 1417: accepts C<DataSource> objects directly as component databases via the
 1418: C<selectall_arrayref> and C<columns> methods this class exposes.
 1419: 
 1420: =item *
 1421: 
 1422: The ephemeral backend class is generated into a package namespace
 1423: (C<Database::BI::_DB::*>) that persists for the lifetime of the process.
 1424: Instantiating two C<DataSource> objects for the same table name reuses
 1425: the same ephemeral class.
 1426: 
 1427: =item *
 1428: 
 1429: The C<i18n> object, if supplied, must implement C<maketext($key, @args)>
 1430: compatible with L<Locale::Maketext>.
 1431: 
 1432: =back
