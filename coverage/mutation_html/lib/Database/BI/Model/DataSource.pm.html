  554: =head1 VERSION

  627: =head1 DESCRIPTION
  628: 
  629: C<Database::BI::Model::DataSource> is a thin, table-agnostic adapter that
  630: wraps L<Database::Abstraction> and exposes three accessors (C<fetch_all>,
  631: C<columns>, C<id_column>) used by the controller.
  632: 
  633: L<Database::Abstraction> is a read-only ORM that discovers data files
  634: (CSV, PSV, SQLite, XML, etc.) automatically from a directory based on the
  635: calling class name.  C<DataSource> generates an ephemeral subclass at
  636: construction time so callers never interact with L<Database::Abstraction>
  637: directly.  To swap the backend for L<Database::Join> in Phase 2, only the
  638: C<open_table> helper in C<Database::BI> needs to change; the controller and
  639: C<DataSource> are untouched.
  640: 
  641: C<_detect_file_info> peeks at the first header line of CSV/PSV files to
  642: extract the correct separator character, the primary-key column name, and
  643: the full ordered column list.  Without this, two silent L<Database::Abstraction>
  644: defaults corrupt every result: C<sep_char> defaults to C<'!'> (turning a
  645: comma-separated file into a single-field table) and C<id> defaults to
  646: C<'entry'> (causing every row to be discarded when no C<entry> column
  647: exists).
  648: 
  649: Result filtering (C<eq>, C<contains>, C<gt>, etc.) is performed at the
  650: controller layer by C<Dashboard::_apply_filter_spec> after C<fetch_all>
  651: returns.  C<DataSource> itself is filter-unaware.
  652: 
  653: All user-visible strings and exception messages are keyed through the
  654: C<%MESSAGES> dictionary and routed via C<_msg()>, making every diagnostic
  655: replaceable by an i18n object at instantiation time.
  656: 
  657: =head1 COMMON PITFALLS
  658: 
  659: These are the most common mistakes when using C<DataSource>.
  660: 
  661: =over 4
  662: 
  663: =item B<SQLite databases must use .sql as their file extension>
  664: 
  665: C<Database::Abstraction> looks for SQLite databases with the C<.sql> extension.
  666: It does B<not> recognise C<.sqlite>, C<.sqlite3>, or C<.db3>.  If you have a
  667: file called C<inventory.sqlite>, rename it to C<inventory.sql> before passing
  668: it to C<DataSource>.
  669: 
  670: =item B<The table name is always lowercased>
  671: 
  672: The constructor lowercases the C<table> argument before using it.  Passing
  673: C<table =E<gt> 'Sales'> and C<table =E<gt> 'sales'> both look for
  674: C<sales.csv> (or C<sales.sql>, etc.).  The matching is case-insensitive on the
  675: table name but B<case-sensitive on the directory path>.
  676: 
  677: =item B<CSV files with the wrong separator appear as one giant field per row>
  678: 
  679: C<Database::Abstraction> defaults to C<!> (exclamation mark) as its field
  680: separator.  A standard comma-separated CSV file will look like one big field
  681: per row (for example, C<1,Widget A,North,100>) because the library never sees
  682: the commas as separators.  C<DataSource> fixes this automatically by reading
  683: the first line of the file and detecting the actual separator.  If you bypass
  684: C<DataSource> and call C<Database::Abstraction> directly, you B<must> pass
  685: C<sep_char =E<gt> ','> yourself.
  686: 
  687: =item B<A table with no "entry" column returns zero rows (without DataSource)>
  688: 
  689: C<Database::Abstraction> uses C<entry> as its default primary-key column name.
  690: When slurping a CSV, it discards any row where C<$row-E<gt>{entry}> is
  691: undefined.  Because most CSV files do not have an C<entry> column, B<all rows
  692: are silently discarded>.  C<DataSource> prevents this by reading the actual
  693: first column name from the CSV header and passing it as C<id>, and also by
  694: setting C<no_entry =E<gt> 1> so all rows are kept as an ordered array.
  695: 
  696: =item B<columns() returns undef for SQLite and XML files>
  697: 
  698: C<columns()> only returns an arrayref for file formats where the header order
  699: is visible before data is read (CSV and PSV).  For SQLite and XML files it
  700: returns C<undef>.  Always check: C<if ($source-E<gt>columns) { ... }>.  The
  701: controller falls back to putting C<id_column> first and then sorting the rest
  702: alphabetically when C<columns()> is C<undef>.
  703: 
  704: =item B<XML elements named "name", "id", or "key" cause parse failures>
  705: 
  706: C<XML::Simple> (used by C<Database::Abstraction> for XML files) automatically
  707: turns a child element called C<name>, C<id>, or C<key> into a hash key instead
  708: of keeping it as an array element.  This breaks the expected data structure.
  709: Use different element names in your XML: for example, C<E<lt>skuE<gt>>,
  710: C<E<lt>labelE<gt>>, or C<E<lt>codeE<gt>> instead of C<E<lt>idE<gt>> and
  711: C<E<lt>nameE<gt>>.
  712: 
  713:   <!-- WRONG: these element names trigger XMLin key-folding -->
  714:   <items>
  715:     <item><id>1</id><name>Widget</name></item>
  716:   </items>
  717: 
  718:   <!-- CORRECT: use neutral element names -->
  719:   <items>
  720:     <item><sku>1</sku><label>Widget</label></item>
  721:   </items>
  722: 
  723: =item B<fetch_all returns an empty arrayref, not undef, for an empty table>
  724: 
  725: When a table exists but contains no data rows, C<fetch_all> returns C<[]> (an
  726: empty arrayref), not C<undef>.  Check with C<scalar @{$records}>, not with
  727: C<defined $records> or C<$records>.
  728: 
  729: =back

  731: =head1 LIMITATIONS
  732: 
  733: =over 4
  734: 
  735: =item *
  736: 
  737: Only read operations are supported.  Write-back is not in scope.
  738: 
  739: =item *
  740: 
  741: One C<DataSource> instance corresponds to exactly one table.  Multi-table
  742: left joins are composed at the controller layer by C<Dashboard::_left_join>;
  743: C<Database::Join> (Phase 2) is not yet in use.
  744: 
  745: =item *
  746: 
  747: The ephemeral backend class is generated into a package namespace
  748: (C<Database::BI::_DB::*>) that persists for the lifetime of the process.
  749: Instantiating two C<DataSource> objects for the same table name reuses
  750: the same ephemeral class.
  751: 
  752: =item *
  753: 
  754: The C<i18n> object, if supplied, must implement C<maketext($key, @args)>
  755: compatible with L<Locale::Maketext>.
  756: 
  757: =back
