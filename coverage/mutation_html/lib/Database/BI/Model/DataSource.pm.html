  160: =head1 DESCRIPTION
  161: 
  162: C<Database::BI::Model::DataSource> is a thin, table-agnostic adapter that
  163: wraps L<Database::Abstraction> and exposes three accessors (C<fetch_all>,
  164: C<columns>, C<id_column>) used by the controller.
  165: 
  166: L<Database::Abstraction> is a read-only ORM that discovers data files
  167: (CSV, PSV, TSV, SQLite, XML, etc.) automatically from a directory based on the
  168: calling class name.  C<DataSource> generates an ephemeral subclass at
  169: construction time so callers never interact with L<Database::Abstraction>
  170: directly.  To swap the backend for L<Database::Join> in Phase 2, only the
  171: C<open_table> helper in C<Database::BI> needs to change; the controller and
  172: C<DataSource> are untouched.
  173: 
  174: C<_detect_file_info> peeks at the first header line of CSV/PSV/TSV files to
  175: extract the correct separator character, the primary-key column name, and
  176: the full ordered column list.  Without this, two silent L<Database::Abstraction>
  177: defaults corrupt every result: C<sep_char> defaults to C<'!'> (turning a
  178: comma-separated file into a single-field table) and C<id> defaults to
  179: C<'entry'> (causing every row to be discarded when no C<entry> column
  180: exists).
  181: 
  182: Result filtering (C<eq>, C<contains>, C<gt>, etc.) is performed at the
  183: controller layer by C<Dashboard::_apply_filter_spec> after C<fetch_all>
  184: returns.  C<DataSource> itself is filter-unaware.
  185: 
  186: All user-visible strings and exception messages are keyed through the
  187: C<%MESSAGES> dictionary and routed via C<_msg()>, making every diagnostic
  188: replaceable by an i18n object at instantiation time.
  189: 
  190: =cut

  192: =head1 ENCODING
  193: 
  194: =head2 What is safe to put in cell values
  195: 
  196: Cell values (the actual data inside rows) are passed through as Perl
  197: character strings exactly as C<Database::Abstraction> and the underlying
  198: DBI driver return them.  Full Unicode -- including non-ASCII letters,
  199: accented characters, CJK ideographs, and emoji -- is supported in cell
  200: values, provided the source file is encoded in UTF-8 (or the encoding
  201: declared in its HTTP headers for URL-backed tables).
  202: 
  203: =head2 What must stay ASCII
  204: 
  205: The following structural items must contain B<only ASCII characters>:
  206: 
  207: =over 4
  208: 
  209: =item C<table> constructor argument
  210: 
  211: The bare file stem used to look up the file on disk.  Non-ASCII characters
  212: are not valid SQL identifiers and will be silently replaced with underscores
  213: (C<_>) by the sanitization step in C<new()>.
  214: 
  215: =item Column header names (CSV / TSV / PSV first line)
  216: 
  217: Column names are used as hash keys and as SQL identifiers inside
  218: C<Database::Abstraction>.  Non-ASCII headers cause C<DBD::CSV> to
  219: fail or produce garbage keys.  If your source file has non-ASCII
  220: column headers, rename them before opening via C<DataSource>.
  221: 
  222: =item C<host> argument
  223: 
  224: The hostname or C<user@hostname> string for SFTP access.  Must match
  225: C<[A-Za-z0-9._@-]>; anything outside that character set is rejected by
  226: the host-validation regex and produces C<error_backend_init>.
  227: 
  228: =back
  229: 
  230: =head2 URL-backed tables
  231: 
  232: URL-backed tables (the C<url =E<gt>> constructor path) are fetched with
  233: L<Database::BI::SafeUA>, which refuses (C<403>, so the read croaks
  234: C<error_fetch_failed>) any request or redirect whose host resolves to this
  235: machine, a private network or a link-local address such as a cloud metadata
  236: service, and connects to the address it checked.  C<private_hosts =E<gt> [...]>
  237: names the hosts (exact, or C<*.suffix>) that may resolve privately: an
  238: intranet.  If the remote server declares a charset in its
  239: HTTP headers or in an HTML C<meta> tag, L<Database::Abstraction> uses it
  240: to decode the response body.  If the charset declaration is absent or wrong,
  241: cell values may arrive as raw bytes rather than character strings, and
  242: multi-byte sequences will look garbled.
  243: 
  244: =head2 File-backed tables (CSV / TSV / PSV)
  245: 
  246: For files smaller than 16 KB, L<Text::xSV::Slurp> reads bytes and returns
  247: them without re-encoding; for larger files the L<DBD::CSV> path is used
  248: instead.  In both cases C<DataSource> forces the slurp path (by passing
  249: C<max_slurp_size =E<gt> -s $file>) so that column names with spaces are
  250: preserved as-is.  The caller (the Mojolicious controller) is responsible
  251: for setting the correct C<Content-Type: text/html; charset=UTF-8> response
  252: header.
  253: 
  254: =cut

  405: 
  406: C<internal_table> selects a named table inside a multi-table SQLite file.
  407: When omitted, C<DataSource> auto-selects the first user table whose name
  408: matches the filename stem; if no match, it picks the first table found.
  409: Supplying a name that does not exist in the file croaks C<error_table_not_found>.
  410: 
  411: A C<.json> file is read as a table when it is a list of objects, an object
  412: of objects (each key a row, kept in a column C<id>, or C<key> when the rows
  413: have an C<id>), or an object holding lists of objects.  Each such list is a
  414: table, as a SQLite file's are: C<internal_table> names one, the first in the
  415: file is read without it, and C<sqlite_tables> lists them.  A cell holding an
  416: object or a list is shown as its JSON text, C<true> and C<false> as words and
  417: C<null> as an empty cell; the columns are in the order the file first names
  418: them.  A C<.csv> (or any other format's file) beside it with the same name is
  419: the one read.  Not JSON croaks C<error_json_invalid>; JSON with no table in
  420: it, C<error_json_no_rows>; a list it does not have, C<error_json_list_not_found>.
  421: 
  422: C<column_order> is for a caller that knows the columns' order better than the
  423: backend does.  A SQLite backend lists its columns alphabetically, so an
  424: extract of an accelerated dataset passes the order its file had.  It is used
  425: only when the file itself gives no order (SQLite, XML), and is trusted, not
  426: checked against the columns the backend has.
  427: 
  428: Accepts a flat key/value list, a hashref, or positional arguments via
  429: C<Params::Get>.
  430: 
  431: When C<host> is provided, C<directory> is treated as a path on the remote
  432: host and is not checked with C<-d> locally.  C<DataSource> downloads the
  433: file via SFTP (L<Net::SFTP::Foreign>) to a process-local temporary directory
  434: and then processes the local copy.  The temporary directory persists for the
  435: lifetime of the C<DataSource> object and is cleaned up automatically on
  436: destruction.

  438: When C<file_ext> is provided together with C<host>, it is used as the first
  439: candidate extension when probing the remote host for the file.  If the

 2740: =head1 COMMON PITFALLS
 2741: 
 2742: These are the most common mistakes when using C<DataSource>.
 2743: 
 2744: =over 4
 2745: 
 2746: =item B<SQLite databases may use .sql, .sqlite, or .sqlite3 as their file extension>
 2747: 
 2748: C<DataSource> recognises C<.sql>, C<.sqlite>, and C<.sqlite3> as SQLite
 2749: database files.  It does B<not> recognise C<.db3>.  If you have a file called
 2750: C<inventory.db3>, rename it to C<inventory.sql> before passing it to
 2751: C<DataSource>.
 2752: 
 2753: =item B<The table name is always lowercased>
 2754: 
 2755: The constructor lowercases the C<table> argument before using it.  Passing
 2756: C<table =E<gt> 'Sales'> and C<table =E<gt> 'sales'> both look for
 2757: C<sales.csv> (or C<sales.sql>, etc.).  The matching is case-insensitive on the
 2758: table name but B<case-sensitive on the directory path>.
 2759: 
 2760: =item B<CSV files with the wrong separator appear as one giant field per row>
 2761: 
 2762: C<Database::Abstraction> defaults to C<!> (exclamation mark) as its field
 2763: separator.  A standard comma-separated CSV file will look like one big field
 2764: per row (for example, C<1,Widget A,North,100>) because the library never sees
 2765: the commas as separators.  C<DataSource> fixes this automatically by reading
 2766: the first line of the file and detecting the actual separator.  If you bypass
 2767: C<DataSource> and call C<Database::Abstraction> directly, you B<must> pass
 2768: C<sep_char =E<gt> ','> yourself.
 2769: 
 2770: =item B<A table with no "entry" column returns zero rows (without DataSource)>
 2771: 
 2772: C<Database::Abstraction> uses C<entry> as its default primary-key column name.
 2773: When slurping a CSV, it discards any row where C<$row-E<gt>{entry}> is
 2774: undefined.  Because most CSV files do not have an C<entry> column, B<all rows
 2775: are silently discarded>.  C<DataSource> prevents this by reading the actual
 2776: first column name from the CSV header and passing it as C<id>, and also by
 2777: setting C<no_entry =E<gt> 1> so all rows are kept as an ordered array.
 2778: 
 2779: =item B<columns() returns undef for SQLite and XML files>
 2780: 
 2781: C<columns()> only returns an arrayref for file formats where the header order
 2782: is visible before data is read (CSV, TSV and PSV).  For SQLite and XML files it
 2783: returns C<undef>.  Always check: C<if ($source-E<gt>columns) { ... }>.  The
 2784: controller falls back to putting C<id_column> first and then sorting the rest
 2785: alphabetically when C<columns()> is C<undef>.
 2786: 
 2787: =item B<XML elements named "name", "id", or "key" cause parse failures>
 2788: 
 2789: C<XML::Simple> (used by C<Database::Abstraction> for XML files) automatically
 2790: turns a child element called C<name>, C<id>, or C<key> into a hash key instead
 2791: of keeping it as an array element.  This breaks the expected data structure.
 2792: Use different element names in your XML: for example, C<E<lt>skuE<gt>>,
 2793: C<E<lt>labelE<gt>>, or C<E<lt>codeE<gt>> instead of C<E<lt>idE<gt>> and
 2794: C<E<lt>nameE<gt>>.
 2795: 
 2796:   <!-- WRONG: these element names trigger XMLin key-folding -->
 2797:   <items>
 2798:     <item><id>1</id><name>Widget</name></item>
 2799:   </items>
 2800: 
 2801:   <!-- CORRECT: use neutral element names -->
 2802:   <items>
 2803:     <item><sku>1</sku><label>Widget</label></item>
 2804:   </items>
 2805: 
 2806: =item B<fetch_all returns an empty arrayref, not undef, for an empty table>
 2807: 
 2808: When a table exists but contains no data rows, C<fetch_all> returns C<[]> (an
 2809: empty arrayref), not C<undef>.  Check with C<scalar @{$records}>, not with
 2810: C<defined $records> or C<$records>.
 2811: 
 2812: =item B<0-byte CSV/TSV/PSV files bypass Database::Abstraction entirely>
 2813: 
 2814: When C<_detect_file_info> opens a CSV, TSV or PSV file and the first C<readline>
 2815: returns C<undef> (the file is 0 bytes), it returns a C<{ _file_is_empty =E<gt>
 2816: 1 }> sentinel instead of the normal C<{ id, sep_char, columns, file_size }>
 2817: hashref.  C<_init_backend> detects this sentinel and skips
 2818: C<Database::Abstraction> construction; C<fetch_all> returns C<[]> immediately.
 2819: B<No DBI connection is created for 0-byte files.>  If you mock or spy on DBI
 2820: handles and open a 0-byte CSV, the mock will never fire - this is expected
 2821: behaviour, not a mock misconfiguration.
 2822: 
 2823: =item B<Remote files require Net::SFTP::Foreign; one connection per open>
 2824: 
 2825: When C<host> is set, C<DataSource> makes one SFTP connection per C<new()>
 2826: call.  It tries the extension list in order (the C<file_ext> hint first,
 2827: if provided, then the full standard-extension list) and downloads the first
 2828: file it finds.  If no file is found under any tried extension, C<new()>
 2829: croaks C<error_backend_init>.  B<Connections are not pooled or reused>
 2830: between C<DataSource> instances.
 2831: 
 2832: If the remote file has a non-standard extension (e.g. C<.log>, C<.dat>),
 2833: the content is sniffed: SQLite magic bytes map to C<.db>, an XML preamble
 2834: to C<.xml>, a tab-delimited first line to C<.tsv>, a pipe-delimited line to
 2835: C<.psv>, and everything else to C<.csv>.  The temp file is then renamed to
 2836: the detected extension before further processing.
 2837: 
 2838: =item B<Multi-table SQLite: opening without internal_table silently picks the first table>
 2839: 
 2840: When a SQLite file contains more than one user-defined table and you call
 2841: C<new()> without C<internal_table>, C<DataSource> auto-selects the first
 2842: table whose name matches the filename stem; if there is no match, it picks
 2843: whatever C<sqlite_master> lists first, skipping any whose name is not a safe
 2844: identifier (letters, digits, underscore).  This is B<silent> -- you get data
 2845: from a table you may not have intended to open.
 2846: 
 2847: Always check C<sqlite_tables()> after construction if you are dealing
 2848: with a SQLite file that might have multiple tables:
 2849: 
 2850:     my $tbl_list = $source->sqlite_tables;
 2851:     if ($tbl_list && @{$tbl_list} > 1) {
 2852:         # warn the user or redirect to the schema browser
 2853:     }
 2854: 
 2855: =item B<The symlink used for .db-extension SQLite files is named .sql, not .db>
 2856: 
 2857: C<Database::Abstraction> does not use its DBI/SQLite backend for files
 2858: with a C<.db> extension -- it falls through to the CSV reader, which tries
 2859: to read a SQLite binary file as text and fails with a parse error.
 2860: 
 2861: When C<DataSource> detects a SQLite C<.db> file, it creates a
 2862: temporary symlink named C<E<lt>tableE<gt>.sql> (not C<.db>) pointing to the
 2863: original C<.db> file.  SQLite follows symlinks transparently, so the data is
 2864: read correctly.  If you ever audit temporary directories and see C<*.sql>
 2865: symlinks pointing at C<*.db> files, this is expected and intentional.
 2866: 
 2867: =item B<DBD::CSV silently lowercases column names for files larger than 16 KB>
 2868: 
 2869: C<Database::Abstraction> uses C<Text::xSV::Slurp> for files up to 16 KB and
 2870: DBD::CSV for larger ones.  The DBD::CSV path lowercases column names and
 2871: replaces spaces with underscores (C<Account Number> becomes
 2872: C<account_number>), which causes a C<"disallowed key"> error at render time
 2873: when the template iterates the original column names.  C<DataSource> avoids
 2874: this by always passing C<max_slurp_size =E<gt> -s $path> to
 2875: C<Database::Abstraction>, forcing the slurp path regardless of file size.
 2876: If you call C<Database::Abstraction> directly, you B<must> pass this option
 2877: yourself for any file whose column names contain spaces or mixed case.
 2878: 
 2879: =back

 3051: =head1 STATE DIAGRAM
 3052: 
 3053: The lifecycle of a single C<DataSource> object from creation to destruction.
 3054: Each state is stable until the trigger event listed to its right fires.
 3055: 
 3056:     +------------------+
 3057:     |     [START]      |  -- new() called
 3058:     +------------------+
 3059:              |
 3060:              v
 3061:     +------------------+  File source: _detect_file_info + _init_backend run
 3062:     |   INITIALISING   |  (SFTP download, BerkeleyDB probe, SQLite
 3063:     |                  |   sqlite_master probe, CSV header parse, XLSX parse).
 3064:     |                  |  URL or Redis source: the backend object is built, and
 3065:     |                  |  nothing is fetched or connected to until the first read.
 3066:     +------------------+
 3067:           /     \
 3068:          /       \
 3069:         v         v
 3070:   +-----------+  +-----------+
 3071:   |  ERROR    |  |   READY   |
 3072:   | (croaks;  |  |           |
 3073:   | no object)|  |           |
 3074:   +-----------+  +-----------+
 3075:                        |
 3076:                        |  fetch_all() or selectall_arrayref(), from READY,
 3077:                        |  DATA RETURNED or FETCH ERROR
 3078:                        |
 3079:        +---------------+-------------------+------------------+
 3080:        | cache configured, | no cache, or  | _file_is_empty   |
 3081:        | a call for the    | a narrowed    |                  |
 3082:        | whole table       | query         |                  |
 3083:        v                   |               |                  |
 3084:   +---------------+        |               |                  |
 3085:   | CACHE CHECK   |        |               |                  |
 3086:   +---------------+        |               |                  |
 3087:      |         |           |               |                  |
 3088:      | hit     | miss, or  |               |                  |
 3089:      |         | no key    |               |                  |
 3090:      |         v           v               |                  |
 3091:      |    +---------------------+          |                  |
 3092:      |    |     FETCHING        |  backend read; the result   |
 3093:      |    |                     |  is stored in the cache if  |
 3094:      |    |                     |  it was looked up there     |
 3095:      |    +---------------------+          |                  |
 3096:      |         |            |              |                  |
 3097:      |         | answered   | failed       |                  |
 3098:      |         |            v              |                  |
 3099:      |         |      +-------------+      |                  |
 3100:      |         |      | FETCH ERROR |      |                  |
 3101:      |         |      | (croaks;    |      |                  |
 3102:      |         |      | object and  |      |                  |
 3103:      |         |      | cache sound)|      |                  |
 3104:      |         |      +-------------+      |                  |
 3105:      v         v                           v                  v
 3106:   +---------------------------------------------------------------+
 3107:   |                        DATA RETURNED                          |
 3108:   +---------------------------------------------------------------+
 3109: 
 3110:     DATA RETURNED delivers an arrayref of hashrefs to the caller, with one
 3111:     exception: selectall_arrayref with no rows to answer with (a table with none,
 3112:     or a narrowed query that matches none) usually answers undef, where fetch_all
 3113:     answers [].
 3114: 
 3115:     A "call for the whole table" is fetch_all, or selectall_arrayref with no
 3116:     arguments, or with only a sort_by on a column that is not a safe identifier and
 3117:     perhaps a limit and offset (DataSource sorts and pages those itself, over the
 3118:     whole table).  Any other arguments
 3119:     make a narrowed query, which is neither looked up in the cache nor stored in
 3120:     it, because its result is not the table.
 3121: 
 3122:     The cache has no key to look under when the file has gone since new(): no
 3123:     lookup is made and nothing is stored, and the read goes on to FETCHING.
 3124: 
 3125:     FETCH ERROR comes from the backend failing, a table with no file (which new()
 3126:     does not notice), a URL that cannot be fetched or does not answer with rows,
 3127:     or a Redis server that cannot be reached.  Unlike ERROR there is an object, and
 3128:     the next read starts again.
 3129: 
 3130:     Other reads (columns, count, aggregate, schema, updated and the like) go to the
 3131:     backend directly, without the cache, and do not change the state.
 3132: 
 3133:     Special cases branching from INITIALISING:
 3134: 
 3135:     1. A 0-byte CSV, TSV or PSV, one with a blank first line, or an XLSX with a
 3136:        blank first worksheet
 3137:        -> _file_is_empty flag set, no backend -> READY (fetch_all and
 3138:           selectall_arrayref return [] instantly, and count returns 0)
 3139:        A 0-byte SQLite file is not this case: it has no tables -> ERROR
 3140: 
 3141:     2. Header-less CSV, TSV or PSV
 3142:        -> copy with a header written to a temporary directory -> READY
 3143:           (Database::Abstraction reads the copy)
 3144: 
 3145:     3. SQLite without internal_table
 3146:        -> _sqlite_tables set -> READY
 3147:        -> caller inspects sqlite_tables() and may redirect to /tables
 3148:           before calling fetch_all (which would open the auto-selected table:
 3149:           the one named after the file, else the first by name that can be opened)
 3150: 
 3151:     4. SQLite WITH internal_table
 3152:        -> a table it does not have, or one with an unsafe name -> ERROR
 3153:        -> otherwise _sqlite_tables set, plus a symlink if the table's name is not
 3154:           the file's -> READY -> fetch_all opens that table
 3155: 
 3156:     5. JSON file
 3157:        -> a flat copy (a list of rows, nested values as JSON text) written
 3158:           to a temporary directory -> READY (Database::Abstraction reads it)
 3159:        -> an object holding lists of objects: _sqlite_tables set to their
 3160:           names, the first read unless internal_table names another (a name
 3161:           it does not have -> ERROR); no rows -> the _file_is_empty case
 3162:        -> not JSON, or no table in it -> ERROR
 3163: 
 3164:     6. SFTP remote file
 3165:        -> Net::SFTP::Foreign::get() -> local tmpdir -> normal init -> READY
 3166:        -> tmpdir kept alive via $self->{_remote_tmpdir} until DESTROY
 3167: 
 3168:     Object lifetime ends when $self goes out of scope:
 3169: 
 3170:     +---------------+
 3171:     |   DESTROY     |  File::Temp tmpdirs auto-cleaned (symlinks removed,
 3172:     |               |  copies removed, SFTP tmpdir removed)
 3173:     +---------------+
 3174: 
 3175:     Valid state transitions summary:
 3176: 
 3177:     [START]          -> INITIALISING     (new() invoked)
 3178:     INITIALISING     -> ERROR            (croak on bad args, SFTP failure, no safe id, no SQLite tables, a file that will not open, etc.)
 3179:     INITIALISING     -> READY            (all checks passed)
 3180:     READY            -> FETCHING         (no cache configured, or a narrowed query)
 3181:     READY            -> DATA RETURNED    (fetch_all / selectall_arrayref, _file_is_empty fast-path)
 3182:     READY            -> CACHE CHECK      (a call for the whole table, cache configured)
 3183:     CACHE CHECK      -> DATA RETURNED    (cache hit)
 3184:     CACHE CHECK      -> FETCHING         (cache miss, or no key to look under)
 3185:     FETCHING         -> DATA RETURNED    (backend answered)
 3186:     FETCHING         -> FETCH ERROR      (backend failed; croaks)
 3187:     DATA RETURNED    -> DATA RETURNED    (next call, _file_is_empty fast-path)
 3188:     DATA RETURNED    -> CACHE CHECK      (next call for the whole table, cache configured)
 3189:     DATA RETURNED    -> FETCHING         (next call, no cache, or a narrowed query)
 3190:     FETCH ERROR      -> CACHE CHECK      (next call for the whole table, cache configured)
 3191:     FETCH ERROR      -> FETCHING         (next call, no cache, or a narrowed query)
 3192:     READY / DATA RETURNED / FETCH ERROR -> DESTROY     ($self goes out of scope)
