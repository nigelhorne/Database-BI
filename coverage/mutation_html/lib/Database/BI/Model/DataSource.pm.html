  117: =head1 DESCRIPTION
  118: 
  119: C<Database::BI::Model::DataSource> is a thin, table-agnostic adapter that
  120: wraps L<Database::Abstraction> and exposes three accessors (C<fetch_all>,
  121: C<columns>, C<id_column>) used by the controller.
  122: 
  123: L<Database::Abstraction> is a read-only ORM that discovers data files
  124: (CSV, PSV, TSV, SQLite, XML, etc.) automatically from a directory based on the
  125: calling class name.  C<DataSource> generates an ephemeral subclass at
  126: construction time so callers never interact with L<Database::Abstraction>
  127: directly.  To swap the backend for L<Database::Join> in Phase 2, only the
  128: C<open_table> helper in C<Database::BI> needs to change; the controller and
  129: C<DataSource> are untouched.
  130: 
  131: C<_detect_file_info> peeks at the first header line of CSV/PSV/TSV files to
  132: extract the correct separator character, the primary-key column name, and
  133: the full ordered column list.  Without this, two silent L<Database::Abstraction>
  134: defaults corrupt every result: C<sep_char> defaults to C<'!'> (turning a
  135: comma-separated file into a single-field table) and C<id> defaults to
  136: C<'entry'> (causing every row to be discarded when no C<entry> column
  137: exists).
  138: 
  139: Result filtering (C<eq>, C<contains>, C<gt>, etc.) is performed at the
  140: controller layer by C<Dashboard::_apply_filter_spec> after C<fetch_all>
  141: returns.  C<DataSource> itself is filter-unaware.
  142: 
  143: All user-visible strings and exception messages are keyed through the
  144: C<%MESSAGES> dictionary and routed via C<_msg()>, making every diagnostic
  145: replaceable by an i18n object at instantiation time.
  146: 
  147: =head2 UTF-8 and Encoding
  148: 
  149: C<DataSource> passes cell values through as Perl character strings exactly
  150: as L<Database::Abstraction> and the underlying DBI driver return them.
  151: For CSV, TSV and PSV files smaller than 16 KB, L<Text::xSV::Slurp> is used and
  152: bytes are returned without re-encoding; for larger files the L<DBD::CSV>
  153: path is used.  In both cases the caller (the controller) is responsible
  154: for setting the correct C<Content-Type> header.
  155: 
  156: The C<table> argument and all column names must be B<ASCII-only>
  157: identifiers.  Full Unicode is supported inside B<cell values> -- the
  158: restriction applies only to structural metadata (column headers, table
  159: name), not to the data itself.
  160: 
  161: URL-backed tables (the C<url =E<gt>> constructor path) are fetched with
  162: L<LWP::UserAgent::Cached>.  If the remote server declares a charset in
  163: its HTTP headers or HTML meta tag, L<Database::Abstraction> uses it to
  164: decode the response body.  If the declaration is absent or wrong, cell
  165: values may contain raw bytes rather than character strings.

 1164: =head1 COMMON PITFALLS
 1165: 
 1166: These are the most common mistakes when using C<DataSource>.
 1167: 
 1168: =over 4
 1169: 
 1170: =item B<SQLite databases must use .sql as their file extension>
 1171: 
 1172: C<Database::Abstraction> looks for SQLite databases with the C<.sql> extension.
 1173: It does B<not> recognise C<.sqlite>, C<.sqlite3>, or C<.db3>.  If you have a
 1174: file called C<inventory.sqlite>, rename it to C<inventory.sql> before passing
 1175: it to C<DataSource>.
 1176: 
 1177: =item B<The table name is always lowercased>
 1178: 
 1179: The constructor lowercases the C<table> argument before using it.  Passing
 1180: C<table =E<gt> 'Sales'> and C<table =E<gt> 'sales'> both look for
 1181: C<sales.csv> (or C<sales.sql>, etc.).  The matching is case-insensitive on the
 1182: table name but B<case-sensitive on the directory path>.
 1183: 
 1184: =item B<CSV files with the wrong separator appear as one giant field per row>
 1185: 
 1186: C<Database::Abstraction> defaults to C<!> (exclamation mark) as its field
 1187: separator.  A standard comma-separated CSV file will look like one big field
 1188: per row (for example, C<1,Widget A,North,100>) because the library never sees
 1189: the commas as separators.  C<DataSource> fixes this automatically by reading
 1190: the first line of the file and detecting the actual separator.  If you bypass
 1191: C<DataSource> and call C<Database::Abstraction> directly, you B<must> pass
 1192: C<sep_char =E<gt> ','> yourself.
 1193: 
 1194: =item B<A table with no "entry" column returns zero rows (without DataSource)>
 1195: 
 1196: C<Database::Abstraction> uses C<entry> as its default primary-key column name.
 1197: When slurping a CSV, it discards any row where C<$row-E<gt>{entry}> is
 1198: undefined.  Because most CSV files do not have an C<entry> column, B<all rows
 1199: are silently discarded>.  C<DataSource> prevents this by reading the actual
 1200: first column name from the CSV header and passing it as C<id>, and also by
 1201: setting C<no_entry =E<gt> 1> so all rows are kept as an ordered array.
 1202: 
 1203: =item B<columns() returns undef for SQLite and XML files>
 1204: 
 1205: C<columns()> only returns an arrayref for file formats where the header order
 1206: is visible before data is read (CSV, TSV and PSV).  For SQLite and XML files it
 1207: returns C<undef>.  Always check: C<if ($source-E<gt>columns) { ... }>.  The
 1208: controller falls back to putting C<id_column> first and then sorting the rest
 1209: alphabetically when C<columns()> is C<undef>.
 1210: 
 1211: =item B<XML elements named "name", "id", or "key" cause parse failures>
 1212: 
 1213: C<XML::Simple> (used by C<Database::Abstraction> for XML files) automatically
 1214: turns a child element called C<name>, C<id>, or C<key> into a hash key instead
 1215: of keeping it as an array element.  This breaks the expected data structure.
 1216: Use different element names in your XML: for example, C<E<lt>skuE<gt>>,
 1217: C<E<lt>labelE<gt>>, or C<E<lt>codeE<gt>> instead of C<E<lt>idE<gt>> and
 1218: C<E<lt>nameE<gt>>.
 1219: 
 1220:   <!-- WRONG: these element names trigger XMLin key-folding -->
 1221:   <items>
 1222:     <item><id>1</id><name>Widget</name></item>
 1223:   </items>
 1224: 
 1225:   <!-- CORRECT: use neutral element names -->
 1226:   <items>
 1227:     <item><sku>1</sku><label>Widget</label></item>
 1228:   </items>
 1229: 
 1230: =item B<fetch_all returns an empty arrayref, not undef, for an empty table>
 1231: 
 1232: When a table exists but contains no data rows, C<fetch_all> returns C<[]> (an
 1233: empty arrayref), not C<undef>.  Check with C<scalar @{$records}>, not with
 1234: C<defined $records> or C<$records>.
 1235: 
 1236: =item B<0-byte CSV/TSV/PSV files bypass Database::Abstraction entirely>
 1237: 
 1238: When C<_detect_file_info> opens a CSV, TSV or PSV file and the first C<readline>
 1239: returns C<undef> (the file is 0 bytes), it returns a C<{ _file_is_empty =E<gt>
 1240: 1 }> sentinel instead of the normal C<{ id, sep_char, columns, file_size }>
 1241: hashref.  C<_init_backend> detects this sentinel and skips
 1242: C<Database::Abstraction> construction; C<fetch_all> returns C<[]> immediately.
 1243: B<No DBI connection is created for 0-byte files.>  If you mock or spy on DBI
 1244: handles and open a 0-byte CSV, the mock will never fire â€” this is expected
 1245: behaviour, not a mock misconfiguration.
