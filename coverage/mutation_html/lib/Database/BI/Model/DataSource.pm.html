  153: =head1 DESCRIPTION
  154: 
  155: C<Database::BI::Model::DataSource> is a thin, table-agnostic adapter that
  156: wraps L<Database::Abstraction> and exposes three accessors (C<fetch_all>,
  157: C<columns>, C<id_column>) used by the controller.
  158: 
  159: L<Database::Abstraction> is a read-only ORM that discovers data files
  160: (CSV, PSV, TSV, SQLite, XML, etc.) automatically from a directory based on the
  161: calling class name.  C<DataSource> generates an ephemeral subclass at
  162: construction time so callers never interact with L<Database::Abstraction>
  163: directly.  To swap the backend for L<Database::Join> in Phase 2, only the
  164: C<open_table> helper in C<Database::BI> needs to change; the controller and
  165: C<DataSource> are untouched.
  166: 
  167: C<_detect_file_info> peeks at the first header line of CSV/PSV/TSV files to
  168: extract the correct separator character, the primary-key column name, and
  169: the full ordered column list.  Without this, two silent L<Database::Abstraction>
  170: defaults corrupt every result: C<sep_char> defaults to C<'!'> (turning a
  171: comma-separated file into a single-field table) and C<id> defaults to
  172: C<'entry'> (causing every row to be discarded when no C<entry> column
  173: exists).
  174: 
  175: Result filtering (C<eq>, C<contains>, C<gt>, etc.) is performed at the
  176: controller layer by C<Dashboard::_apply_filter_spec> after C<fetch_all>
  177: returns.  C<DataSource> itself is filter-unaware.
  178: 
  179: All user-visible strings and exception messages are keyed through the
  180: C<%MESSAGES> dictionary and routed via C<_msg()>, making every diagnostic
  181: replaceable by an i18n object at instantiation time.

 1699: =head2 fetch_all
 1700: 
 1701: Returns every record in the table as an arrayref of hashrefs (one hashref
 1702: per row; keys are the column names).
 1703: 
 1704: This is the primary data-retrieval method.  It is equivalent to calling
 1705: C<selectall_arrayref> with no arguments and normalising the result to an
 1706: arrayref.  Prefer C<selectall_arrayref> when passing to C<Database::Join>
 1707: (it is the method that C<Database::Join> calls internally).
 1708: 
 1709: Filtering (C<eq>, C<contains>, C<gt>, C<lt>, etc.) is applied at the
 1710: controller layer by C<Dashboard::_apply_filter_spec> after C<fetch_all>
 1711: returns.  C<DataSource> itself is filter-unaware.
 1712: 
 1713: Three fast-path shortcuts are checked before touching the DBI backend,
 1714: in this order:
 1715: 
 1716: =over 4
 1717: 
 1718: =item 1.
 1719: 
 1720: C<_file_is_empty> is set (0-byte or blank-first-line file) -- returns C<[]>
 1721: immediately, no DBI connection.
 1722: 
 1723: =item 2.
 1724: 
 1725: C<_file_data> is set (pre-parsed header-less CSV, XLSX, or BerkeleyDB data) --
 1726: returns the in-memory arrayref directly.
 1727: 
 1728: =item 3.
 1729: 
 1730: A matching CHI cache entry exists -- returns the cached arrayref without
 1731: calling C<Database::Abstraction>.
 1732: 
 1733: =back

 1736: 
 1737: =head4 INPUT
 1738: 
 1739: None.  Filtering is applied at the controller layer, not inside C<DataSource>.

 1742: 
 1743:     ARRAYREF of HASHREF   # one hashref per row; keys are column names

 1759: =head2 selectall_arrayref
 1760: 
 1761: C<Database::Abstraction>-compatible alias that allows a C<DataSource> object
 1762: to be passed directly to C<Database::Join> as a component database.
 1763: 
 1764: When called with no arguments (the normal path for a full-table scan),
 1765: results are served from the CHI cache when available.  When called with
 1766: arguments (e.g. C<limit =E<gt> N, offset =E<gt> M> for server-side
 1767: pagination), the cache is bypassed -- narrowed results must not pollute
 1768: the full-table cache entry.
 1769: 
 1770: Three fast-path shortcuts are checked before touching the DBI backend:
 1771: 
 1772: =over 4
 1773: 
 1774: =item 1.
 1775: 
 1776: C<_file_is_empty> is set -- returns C<[]> immediately.
 1777: 
 1778: =item 2.
 1779: 
 1780: C<_file_data> is set (pre-parsed headerless CSV / XLSX / BerkeleyDB) -- returns
 1781: the in-memory rows directly.
 1782: 
 1783: =item 3.
 1784: 
 1785: A matching CHI cache entry exists for the full-table scan -- returns the
 1786: cached arrayref.
 1787: 
 1788: =back
 1789: 
 1790: =head3 API SPECIFICATION
 1791: 
 1792: =head4 INPUT
 1793: 
 1794: Optional flat key/value list passed through to C<Database::Abstraction>:
 1795: 
 1796:     limit  => N    # return at most N rows (used by pagination)
 1797:     offset => M    # skip the first M rows (used by pagination)
 1798: 
 1799: When no arguments are given, the full table is returned (and cached).

 1802: 
 1803:     ARRAYREF of HASHREF   # one hashref per row; keys are column names
 1804:     []                    # empty arrayref when the file is empty or no rows match

 1806: =head3 MESSAGES
 1807: 
 1808: None.  Errors from the DBI backend propagate as uncaught exceptions; wrap
 1809: calls in C<eval> if you need to recover.

 1900: =head2 count
 1901: 
 1902: Returns the total number of rows in the table.
 1903: 
 1904: For pre-parsed sources (header-less CSV, XLSX, BerkeleyDB) the count comes
 1905: from the already-loaded in-memory slice and is instant (no I/O).  For
 1906: empty-file sentinels it returns C<0> immediately.  For all DBI-backed
 1907: sources (SQLite, large CSV via DBD::CSV) it delegates to
 1908: C<Database::Abstraction::count()>, which issues a
 1909: C<SELECT COUNT(*) FROM E<lt>tableE<gt>> query against the file.
 1910: 
 1911: B<Warning: do not call C<count()> on a very large SQLite file> if you
 1912: only need to know whether a next page exists.  The pagination controller
 1913: uses the N+1 trick (fetch C<per_page + 1> rows via C<limit/offset>)
 1914: specifically to avoid a C<COUNT(*)> on multi-gigabyte databases, which
 1915: can block the server for minutes.

 1944: =head1 COMMON PITFALLS
 1945: 
 1946: These are the most common mistakes when using C<DataSource>.
 1947: 
 1948: =over 4
 1949: 
 1950: =item B<SQLite databases may use .sql, .sqlite, or .sqlite3 as their file extension>
 1951: 
 1952: C<DataSource> recognises C<.sql>, C<.sqlite>, and C<.sqlite3> as SQLite
 1953: database files.  It does B<not> recognise C<.db3>.  If you have a file called
 1954: C<inventory.db3>, rename it to C<inventory.sql> before passing it to
 1955: C<DataSource>.
 1956: 
 1957: =item B<The table name is always lowercased>
 1958: 
 1959: The constructor lowercases the C<table> argument before using it.  Passing
 1960: C<table =E<gt> 'Sales'> and C<table =E<gt> 'sales'> both look for
 1961: C<sales.csv> (or C<sales.sql>, etc.).  The matching is case-insensitive on the
 1962: table name but B<case-sensitive on the directory path>.
 1963: 
 1964: =item B<CSV files with the wrong separator appear as one giant field per row>
 1965: 
 1966: C<Database::Abstraction> defaults to C<!> (exclamation mark) as its field
 1967: separator.  A standard comma-separated CSV file will look like one big field
 1968: per row (for example, C<1,Widget A,North,100>) because the library never sees
 1969: the commas as separators.  C<DataSource> fixes this automatically by reading
 1970: the first line of the file and detecting the actual separator.  If you bypass
 1971: C<DataSource> and call C<Database::Abstraction> directly, you B<must> pass
 1972: C<sep_char =E<gt> ','> yourself.
 1973: 
 1974: =item B<A table with no "entry" column returns zero rows (without DataSource)>
 1975: 
 1976: C<Database::Abstraction> uses C<entry> as its default primary-key column name.
 1977: When slurping a CSV, it discards any row where C<$row-E<gt>{entry}> is
 1978: undefined.  Because most CSV files do not have an C<entry> column, B<all rows
 1979: are silently discarded>.  C<DataSource> prevents this by reading the actual
 1980: first column name from the CSV header and passing it as C<id>, and also by
 1981: setting C<no_entry =E<gt> 1> so all rows are kept as an ordered array.
 1982: 
 1983: =item B<columns() returns undef for SQLite and XML files>
 1984: 
 1985: C<columns()> only returns an arrayref for file formats where the header order
 1986: is visible before data is read (CSV, TSV and PSV).  For SQLite and XML files it
 1987: returns C<undef>.  Always check: C<if ($source-E<gt>columns) { ... }>.  The
 1988: controller falls back to putting C<id_column> first and then sorting the rest
 1989: alphabetically when C<columns()> is C<undef>.
 1990: 
 1991: =item B<XML elements named "name", "id", or "key" cause parse failures>
 1992: 
 1993: C<XML::Simple> (used by C<Database::Abstraction> for XML files) automatically
 1994: turns a child element called C<name>, C<id>, or C<key> into a hash key instead
 1995: of keeping it as an array element.  This breaks the expected data structure.
 1996: Use different element names in your XML: for example, C<E<lt>skuE<gt>>,
 1997: C<E<lt>labelE<gt>>, or C<E<lt>codeE<gt>> instead of C<E<lt>idE<gt>> and
 1998: C<E<lt>nameE<gt>>.
 1999: 
 2000:   <!-- WRONG: these element names trigger XMLin key-folding -->
 2001:   <items>
 2002:     <item><id>1</id><name>Widget</name></item>
 2003:   </items>
 2004: 
 2005:   <!-- CORRECT: use neutral element names -->
 2006:   <items>
 2007:     <item><sku>1</sku><label>Widget</label></item>
 2008:   </items>
 2009: 
 2010: =item B<fetch_all returns an empty arrayref, not undef, for an empty table>
 2011: 
 2012: When a table exists but contains no data rows, C<fetch_all> returns C<[]> (an
 2013: empty arrayref), not C<undef>.  Check with C<scalar @{$records}>, not with
 2014: C<defined $records> or C<$records>.
 2015: 
 2016: =item B<0-byte CSV/TSV/PSV files bypass Database::Abstraction entirely>
 2017: 
 2018: When C<_detect_file_info> opens a CSV, TSV or PSV file and the first C<readline>
 2019: returns C<undef> (the file is 0 bytes), it returns a C<{ _file_is_empty =E<gt>
 2020: 1 }> sentinel instead of the normal C<{ id, sep_char, columns, file_size }>
 2021: hashref.  C<_init_backend> detects this sentinel and skips
 2022: C<Database::Abstraction> construction; C<fetch_all> returns C<[]> immediately.
 2023: B<No DBI connection is created for 0-byte files.>  If you mock or spy on DBI
 2024: handles and open a 0-byte CSV, the mock will never fire - this is expected
 2025: behaviour, not a mock misconfiguration.
 2026: 
 2027: =item B<Remote files require Net::SFTP::Foreign; one connection per open>
 2028: 
 2029: When C<host> is set, C<DataSource> makes one SFTP connection per C<new()>
 2030: call.  It tries the extension list in order (the C<file_ext> hint first,
 2031: if provided, then the full standard-extension list) and downloads the first
 2032: file it finds.  If no file is found under any tried extension, C<new()>
 2033: croaks C<error_backend_init>.  B<Connections are not pooled or reused>
 2034: between C<DataSource> instances.
 2035: 
 2036: If the remote file has a non-standard extension (e.g. C<.log>, C<.dat>),
 2037: the content is sniffed: SQLite magic bytes map to C<.db>, an XML preamble
 2038: to C<.xml>, a tab-delimited first line to C<.tsv>, a pipe-delimited line to
 2039: C<.psv>, and everything else to C<.csv>.  The temp file is then renamed to
 2040: the detected extension before further processing.
 2041: 
 2042: =item B<Multi-table SQLite: opening without internal_table silently picks the first table>
 2043: 
 2044: When a SQLite file contains more than one user-defined table and you call
 2045: C<new()> without C<internal_table>, C<DataSource> auto-selects the first
 2046: table whose name matches the filename stem; if there is no match, it picks
 2047: whatever C<sqlite_master> lists first.  This is B<silent> -- you get data
 2048: from a table you may not have intended to open.
 2049: 
 2050: Always check C<sqlite_tables()> after construction if you are dealing
 2051: with a SQLite file that might have multiple tables:
 2052: 
 2053:     my $tbl_list = $source->sqlite_tables;
 2054:     if ($tbl_list && @{$tbl_list} > 1) {
 2055:         # warn the user or redirect to the schema browser
 2056:     }
 2057: 
 2058: =item B<The symlink used for .db-extension SQLite files is named .sql, not .db>
 2059: 
 2060: C<Database::Abstraction> does not use its DBI/SQLite backend for files
 2061: with a C<.db> extension -- it falls through to the CSV reader, which tries
 2062: to read a SQLite binary file as text and fails with a parse error.
 2063: 
 2064: When C<DataSource> detects a multi-table SQLite C<.db> file, it creates a
 2065: temporary symlink named C<E<lt>tableE<gt>.sql> (not C<.db>) pointing to the
 2066: original C<.db> file.  SQLite follows symlinks transparently, so the data is
 2067: read correctly.  If you ever audit temporary directories and see C<*.sql>
 2068: symlinks pointing at C<*.db> files, this is expected and intentional.
 2069: 
 2070: =item B<DBD::CSV silently lowercases column names for files larger than 16 KB>
 2071: 
 2072: C<Database::Abstraction> uses C<Text::xSV::Slurp> for files up to 16 KB and
 2073: DBD::CSV for larger ones.  The DBD::CSV path lowercases column names and
 2074: replaces spaces with underscores (C<Account Number> becomes
 2075: C<account_number>), which causes a C<"disallowed key"> error at render time
 2076: when the template iterates the original column names.  C<DataSource> avoids
 2077: this by always passing C<max_slurp_size =E<gt> -s $path> to
 2078: C<Database::Abstraction>, forcing the slurp path regardless of file size.
 2079: If you call C<Database::Abstraction> directly, you B<must> pass this option
 2080: yourself for any file whose column names contain spaces or mixed case.
 2081: 
 2082: =back

 2260:     +------------------+

 2262:              v

 2264:     |   INITIALISING   |  (SFTP download, BerkeleyDB probe, SQLite
 2265:     |                  |   sqlite_master probe, CSV header parse,
 2266:     |                  |   XLSX parse, or URL fetch)
 2267:     +------------------+
 2268:           /     \
 2269:          /       \
 2270:         v         v
 2271:   +----------+  +-----------+
 2272:   |  ERROR   |  |   READY   |
 2273:   | (croaks) |  |           |
 2274:   +----------+  +-----------+
 2275:                  |         |
 2276:                  |         |
 2277:     fetch_all()  |         |  selectall_arrayref()
 2278:     called       |         |  called
 2279:                  v         v
 2280:          +---------------+
 2281:          |   FETCHING    |  DBI query or pre-loaded data returned;
 2282:          |               |  result stored in CHI cache (if configured)
 2283:          +---------------+
 2284:                  |
 2285:                  v
 2286:          +---------------+
 2287:          | DATA RETURNED |  arrayref of hashrefs delivered to caller
 2288:          +---------------+
 2289:                  |

 2291:                  v

 2297:     Special cases branching from INITIALISING:
 2298: 
 2299:     1. File is 0 bytes or blank first line
 2300:        -> _file_is_empty flag set -> READY (fetch_all returns [] instantly)
 2301: 
 2302:     2. Header-less CSV / XLSX / BerkeleyDB
 2303:        -> _file_data pre-loaded -> READY (fetch_all returns pre-loaded rows)
 2304: 
 2305:     3. Multi-table SQLite without internal_table
 2306:        -> _sqlite_tables set -> READY
 2307:        -> caller inspects sqlite_tables() and may redirect to /tables
 2308:           before calling fetch_all (which would open the auto-selected table)
 2309: 
 2310:     4. Multi-table SQLite WITH internal_table
 2311:        -> symlink created for named table -> READY -> fetch_all opens that table
 2312: 
 2313:     5. SFTP remote file
 2314:        -> Net::SFTP::Foreign::get() -> local tmpdir -> normal init -> READY
 2315:        -> tmpdir kept alive via $self->{_remote_tmpdir} until DESTROY
 2316: 
 2317:     Object lifetime ends when $self goes out of scope:
 2318: 
 2319:     +---------------+
 2320:     |   DESTROY     |  File::Temp tmpdirs auto-cleaned (symlinks removed,
 2321:     |               |  SFTP tmpdir removed)
 2322:     +---------------+
 2323: 
 2324:     Valid state transitions summary:
 2325: 
 2326:     [START]          -> INITIALISING     (new() invoked)
 2327:     INITIALISING     -> ERROR            (croak on bad args, SFTP failure,
 2328:                                           no safe id, no SQLite tables, etc.)
 2329:     INITIALISING     -> READY            (all checks passed)
 2330:     READY            -> FETCHING         (fetch_all / selectall_arrayref, cache miss)
 2331:     READY            -> DATA RETURNED    (fetch_all, _file_is_empty or _file_data fast-path)

 2333:     CACHE CHECK      -> DATA RETURNED    (cache hit)

 2337:     DATA RETURNED    -> FETCHING         (next call, no cache)
 2338:     READY / DATA RETURNED -> DESTROY     ($self goes out of scope)
