  506: 
  507: Database::BI::Model::DataSource - Table-agnostic adapter around Database::Abstraction
  508: 
  509: =head1 VERSION
  510: 
  511: Version 0.003.0
  512: 
  513: =head1 SYNOPSIS
  514: 
  515: B<Read all rows from a CSV file:>
  516: 
  517:     use Database::BI::Model::DataSource;
  518: 
  519:     my $source = Database::BI::Model::DataSource->new(
  520:         directory => '/path/to/data',
  521:         table     => 'sales',           # looks for data/sales.csv, .psv, .sql, .xml, etc.
  522:     );
  523: 
  524:     my $records = $source->fetch_all;   # arrayref of hashrefs -- one hashref per row
  525: 
  526:     for my $row (@{$records}) {
  527:         printf "Product: %s, Amount: %s\n", $row->{product}, $row->{amount};
  528:     }
  529: 
  530: B<Get column names in the original file order (CSV/PSV only):>
  531: 
  532:     my $cols = $source->columns;        # returns undef for SQLite and XML
  533:     if ($cols) {
  534:         print join(', ', @{$cols}), "\n";
  535:     }
  536: 
  537: B<Find out which column is the primary key:>
  538: 
  539:     print "Primary key column: ", $source->id_column, "\n";
  540: 
  541: B<Open a SQLite file (.sql extension):>
  542: 
  543:     my $source = Database::BI::Model::DataSource->new(
  544:         directory => '/var/data',
  545:         table     => 'inventory',       # looks for /var/data/inventory.sql
  546:     );
  547: 
  548: B<Open a pipe-separated file (.psv extension):>
  549: 
  550:     my $source = Database::BI::Model::DataSource->new(
  551:         directory => '/var/data',
  552:         table     => 'products',        # looks for /var/data/products.psv
  553:     );
  554: 
  555: B<Use a custom i18n object to translate error messages:>
  556: 
  557:     # The i18n object must have a maketext($key, @args) method.
  558:     my $source = Database::BI::Model::DataSource->new(
  559:         directory => '/path/to/data',
  560:         table     => 'sales',
  561:         i18n      => My::I18N::Handle->new,
  562:     );
  563: 
  564: B<Handle errors gracefully:>
  565: 
  566:     my $source = eval {
  567:         Database::BI::Model::DataSource->new(
  568:             directory => $dir,
  569:             table     => $table,
  570:         );
  571:     };
  572:     if ($@) {
  573:         carp "Could not open table: $@";
  574:         # $@ contains a translated message from %MESSAGES
  575:     }
  576: 
  577:     my $records = eval { $source->fetch_all };
  578:     if ($@) {
  579:         carp "Could not read records: $@";
  580:     }
  581: 
  582: =head1 DESCRIPTION
  583: 
  584: C<Database::BI::Model::DataSource> is a thin, table-agnostic adapter that
  585: wraps L<Database::Abstraction> and exposes three accessors (C<fetch_all>,
  586: C<columns>, C<id_column>) used by the controller.
  587: 
  588: L<Database::Abstraction> is a read-only ORM that discovers data files
  589: (CSV, PSV, SQLite, XML, etc.) automatically from a directory based on the
  590: calling class name.  C<DataSource> generates an ephemeral subclass at
  591: construction time so callers never interact with L<Database::Abstraction>
  592: directly.  To swap the backend for L<Database::Join> in Phase 2, only the
  593: C<open_table> helper in C<Database::BI> needs to change; the controller and
  594: C<DataSource> are untouched.
  595: 
  596: C<_detect_file_info> peeks at the first header line of CSV/PSV files to
  597: extract the correct separator character, the primary-key column name, and
  598: the full ordered column list.  Without this, two silent L<Database::Abstraction>
  599: defaults corrupt every result: C<sep_char> defaults to C<'!'> (turning a
  600: comma-separated file into a single-field table) and C<id> defaults to
  601: C<'entry'> (causing every row to be discarded when no C<entry> column
  602: exists).
  603: 
  604: Result filtering (C<eq>, C<contains>, C<gt>, etc.) is performed at the
  605: controller layer by C<Dashboard::_apply_filter_spec> after C<fetch_all>
  606: returns.  C<DataSource> itself is filter-unaware.
  607: 
  608: All user-visible strings and exception messages are keyed through the
  609: C<%MESSAGES> dictionary and routed via C<_msg()>, making every diagnostic
  610: replaceable by an i18n object at instantiation time.
  611: 
  612: =head1 COMMON PITFALLS
  613: 
  614: These are the most common mistakes when using C<DataSource>.
  615: 
  616: =over 4
  617: 
  618: =item B<SQLite databases must use .sql as their file extension>
  619: 
  620: C<Database::Abstraction> looks for SQLite databases with the C<.sql> extension.
  621: It does B<not> recognise C<.sqlite>, C<.sqlite3>, or C<.db3>.  If you have a
  622: file called C<inventory.sqlite>, rename it to C<inventory.sql> before passing
  623: it to C<DataSource>.
  624: 
  625: =item B<The table name is always lowercased>
  626: 
  627: The constructor lowercases the C<table> argument before using it.  Passing
  628: C<table =E<gt> 'Sales'> and C<table =E<gt> 'sales'> both look for
  629: C<sales.csv> (or C<sales.sql>, etc.).  The matching is case-insensitive on the
  630: table name but B<case-sensitive on the directory path>.
  631: 
  632: =item B<CSV files with the wrong separator appear as one giant field per row>
  633: 
  634: C<Database::Abstraction> defaults to C<!> (exclamation mark) as its field
  635: separator.  A standard comma-separated CSV file will look like one big field
  636: per row (for example, C<1,Widget A,North,100>) because the library never sees
  637: the commas as separators.  C<DataSource> fixes this automatically by reading
  638: the first line of the file and detecting the actual separator.  If you bypass
  639: C<DataSource> and call C<Database::Abstraction> directly, you B<must> pass
  640: C<sep_char =E<gt> ','> yourself.
  641: 
  642: =item B<A table with no "entry" column returns zero rows (without DataSource)>
  643: 
  644: C<Database::Abstraction> uses C<entry> as its default primary-key column name.
  645: When slurping a CSV, it discards any row where C<$row-E<gt>{entry}> is
  646: undefined.  Because most CSV files do not have an C<entry> column, B<all rows
  647: are silently discarded>.  C<DataSource> prevents this by reading the actual
  648: first column name from the CSV header and passing it as C<id>, and also by
  649: setting C<no_entry =E<gt> 1> so all rows are kept as an ordered array.
  650: 
  651: =item B<columns() returns undef for SQLite and XML files>
  652: 
  653: C<columns()> only returns an arrayref for file formats where the header order
  654: is visible before data is read (CSV and PSV).  For SQLite and XML files it
  655: returns C<undef>.  Always check: C<if ($source-E<gt>columns) { ... }>.  The
  656: controller falls back to putting C<id_column> first and then sorting the rest
  657: alphabetically when C<columns()> is C<undef>.
  658: 
  659: =item B<XML elements named "name", "id", or "key" cause parse failures>
  660: 
  661: C<XML::Simple> (used by C<Database::Abstraction> for XML files) automatically
  662: turns a child element called C<name>, C<id>, or C<key> into a hash key instead
  663: of keeping it as an array element.  This breaks the expected data structure.
  664: Use different element names in your XML: for example, C<E<lt>skuE<gt>>,
  665: C<E<lt>labelE<gt>>, or C<E<lt>codeE<gt>> instead of C<E<lt>idE<gt>> and
  666: C<E<lt>nameE<gt>>.
  667: 
  668:   <!-- WRONG: these element names trigger XMLin key-folding -->
  669:   <items>
  670:     <item><id>1</id><name>Widget</name></item>
  671:   </items>
  672: 
  673:   <!-- CORRECT: use neutral element names -->
  674:   <items>
  675:     <item><sku>1</sku><label>Widget</label></item>
  676:   </items>
  677: 
  678: =item B<fetch_all returns an empty arrayref, not undef, for an empty table>
  679: 
  680: When a table exists but contains no data rows, C<fetch_all> returns C<[]> (an
  681: empty arrayref), not C<undef>.  Check with C<scalar @{$records}>, not with
  682: C<defined $records> or C<$records>.
  683: 
  684: =back
  685: 
  686: =head1 LIMITATIONS
  687: 
  688: =over 4
  689: 
  690: =item *
  691: 
  692: Only read operations are supported.  Write-back is not in scope.
  693: 
  694: =item *
  695: 
  696: One C<DataSource> instance corresponds to exactly one table.  Multi-table
  697: left joins are composed at the controller layer by C<Dashboard::_left_join>;
  698: C<Database::Join> (Phase 2) is not yet in use.
  699: 
  700: =item *
  701: 
  702: The ephemeral backend class is generated into a package namespace
  703: (C<Database::BI::_DB::*>) that persists for the lifetime of the process.
  704: Instantiating two C<DataSource> objects for the same table name reuses
  705: the same ephemeral class.
  706: 
  707: =item *
  708: 
  709: The C<i18n> object, if supplied, must implement C<maketext($key, @args)>
  710: compatible with L<Locale::Maketext>.
  711: 
  712: =back
  713:
