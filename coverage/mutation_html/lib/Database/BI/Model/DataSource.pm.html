  153: =head1 DESCRIPTION
  154: 
  155: C<Database::BI::Model::DataSource> is a thin, table-agnostic adapter that
  156: wraps L<Database::Abstraction> and exposes three accessors (C<fetch_all>,
  157: C<columns>, C<id_column>) used by the controller.
  158: 
  159: L<Database::Abstraction> is a read-only ORM that discovers data files
  160: (CSV, PSV, TSV, SQLite, XML, etc.) automatically from a directory based on the
  161: calling class name.  C<DataSource> generates an ephemeral subclass at
  162: construction time so callers never interact with L<Database::Abstraction>
  163: directly.  To swap the backend for L<Database::Join> in Phase 2, only the
  164: C<open_table> helper in C<Database::BI> needs to change; the controller and
  165: C<DataSource> are untouched.
  166: 
  167: C<_detect_file_info> peeks at the first header line of CSV/PSV/TSV files to
  168: extract the correct separator character, the primary-key column name, and
  169: the full ordered column list.  Without this, two silent L<Database::Abstraction>
  170: defaults corrupt every result: C<sep_char> defaults to C<'!'> (turning a
  171: comma-separated file into a single-field table) and C<id> defaults to
  172: C<'entry'> (causing every row to be discarded when no C<entry> column
  173: exists).
  174: 
  175: Result filtering (C<eq>, C<contains>, C<gt>, etc.) is performed at the
  176: controller layer by C<Dashboard::_apply_filter_spec> after C<fetch_all>
  177: returns.  C<DataSource> itself is filter-unaware.
  178: 
  179: All user-visible strings and exception messages are keyed through the
  180: C<%MESSAGES> dictionary and routed via C<_msg()>, making every diagnostic
  181: replaceable by an i18n object at instantiation time.

 1721: =head2 count
 1722: 
 1723: Returns the total number of rows in the table.
 1724: 
 1725: For pre-parsed sources (header-less CSV, XLSX, BerkeleyDB) the count comes
 1726: from the already-loaded in-memory slice and is instant (no I/O).  For
 1727: empty-file sentinels it returns C<0> immediately.  For all DBI-backed
 1728: sources (SQLite, large CSV via DBD::CSV) it delegates to
 1729: C<Database::Abstraction::count()>, which issues a
 1730: C<SELECT COUNT(*) FROM E<lt>tableE<gt>> query against the file.
 1731: 
 1732: B<Warning: do not call C<count()> on a very large SQLite file> if you
 1733: only need to know whether a next page exists.  The pagination controller
 1734: uses the N+1 trick (fetch C<per_page + 1> rows via C<limit/offset>)
 1735: specifically to avoid a C<COUNT(*)> on multi-gigabyte databases, which
 1736: can block the server for minutes.

 1765: =head1 COMMON PITFALLS
 1766: 
 1767: These are the most common mistakes when using C<DataSource>.
 1768: 
 1769: =over 4
 1770: 
 1771: =item B<SQLite databases may use .sql, .sqlite, or .sqlite3 as their file extension>
 1772: 
 1773: C<DataSource> recognises C<.sql>, C<.sqlite>, and C<.sqlite3> as SQLite
 1774: database files.  It does B<not> recognise C<.db3>.  If you have a file called
 1775: C<inventory.db3>, rename it to C<inventory.sql> before passing it to
 1776: C<DataSource>.
 1777: 
 1778: =item B<The table name is always lowercased>
 1779: 
 1780: The constructor lowercases the C<table> argument before using it.  Passing
 1781: C<table =E<gt> 'Sales'> and C<table =E<gt> 'sales'> both look for
 1782: C<sales.csv> (or C<sales.sql>, etc.).  The matching is case-insensitive on the
 1783: table name but B<case-sensitive on the directory path>.
 1784: 
 1785: =item B<CSV files with the wrong separator appear as one giant field per row>
 1786: 
 1787: C<Database::Abstraction> defaults to C<!> (exclamation mark) as its field
 1788: separator.  A standard comma-separated CSV file will look like one big field
 1789: per row (for example, C<1,Widget A,North,100>) because the library never sees
 1790: the commas as separators.  C<DataSource> fixes this automatically by reading
 1791: the first line of the file and detecting the actual separator.  If you bypass
 1792: C<DataSource> and call C<Database::Abstraction> directly, you B<must> pass
 1793: C<sep_char =E<gt> ','> yourself.
 1794: 
 1795: =item B<A table with no "entry" column returns zero rows (without DataSource)>
 1796: 
 1797: C<Database::Abstraction> uses C<entry> as its default primary-key column name.
 1798: When slurping a CSV, it discards any row where C<$row-E<gt>{entry}> is
 1799: undefined.  Because most CSV files do not have an C<entry> column, B<all rows
 1800: are silently discarded>.  C<DataSource> prevents this by reading the actual
 1801: first column name from the CSV header and passing it as C<id>, and also by
 1802: setting C<no_entry =E<gt> 1> so all rows are kept as an ordered array.
 1803: 
 1804: =item B<columns() returns undef for SQLite and XML files>
 1805: 
 1806: C<columns()> only returns an arrayref for file formats where the header order
 1807: is visible before data is read (CSV, TSV and PSV).  For SQLite and XML files it
 1808: returns C<undef>.  Always check: C<if ($source-E<gt>columns) { ... }>.  The
 1809: controller falls back to putting C<id_column> first and then sorting the rest
 1810: alphabetically when C<columns()> is C<undef>.
 1811: 
 1812: =item B<XML elements named "name", "id", or "key" cause parse failures>
 1813: 
 1814: C<XML::Simple> (used by C<Database::Abstraction> for XML files) automatically
 1815: turns a child element called C<name>, C<id>, or C<key> into a hash key instead
 1816: of keeping it as an array element.  This breaks the expected data structure.
 1817: Use different element names in your XML: for example, C<E<lt>skuE<gt>>,
 1818: C<E<lt>labelE<gt>>, or C<E<lt>codeE<gt>> instead of C<E<lt>idE<gt>> and
 1819: C<E<lt>nameE<gt>>.
 1820: 
 1821:   <!-- WRONG: these element names trigger XMLin key-folding -->
 1822:   <items>
 1823:     <item><id>1</id><name>Widget</name></item>
 1824:   </items>
 1825: 
 1826:   <!-- CORRECT: use neutral element names -->
 1827:   <items>
 1828:     <item><sku>1</sku><label>Widget</label></item>
 1829:   </items>
 1830: 
 1831: =item B<fetch_all returns an empty arrayref, not undef, for an empty table>
 1832: 
 1833: When a table exists but contains no data rows, C<fetch_all> returns C<[]> (an
 1834: empty arrayref), not C<undef>.  Check with C<scalar @{$records}>, not with
 1835: C<defined $records> or C<$records>.
 1836: 
 1837: =item B<0-byte CSV/TSV/PSV files bypass Database::Abstraction entirely>
 1838: 
 1839: When C<_detect_file_info> opens a CSV, TSV or PSV file and the first C<readline>
 1840: returns C<undef> (the file is 0 bytes), it returns a C<{ _file_is_empty =E<gt>
 1841: 1 }> sentinel instead of the normal C<{ id, sep_char, columns, file_size }>
 1842: hashref.  C<_init_backend> detects this sentinel and skips
 1843: C<Database::Abstraction> construction; C<fetch_all> returns C<[]> immediately.
 1844: B<No DBI connection is created for 0-byte files.>  If you mock or spy on DBI
 1845: handles and open a 0-byte CSV, the mock will never fire - this is expected
 1846: behaviour, not a mock misconfiguration.
 1847: 
 1848: =item B<Remote files require Net::SFTP::Foreign; one connection per open>
 1849: 
 1850: When C<host> is set, C<DataSource> makes one SFTP connection per C<new()>
 1851: call.  It tries the extension list in order (the C<file_ext> hint first,
 1852: if provided, then the full standard-extension list) and downloads the first
 1853: file it finds.  If no file is found under any tried extension, C<new()>
 1854: croaks C<error_backend_init>.  B<Connections are not pooled or reused>
 1855: between C<DataSource> instances.
 1856: 
 1857: If the remote file has a non-standard extension (e.g. C<.log>, C<.dat>),
 1858: the content is sniffed: SQLite magic bytes map to C<.db>, an XML preamble
 1859: to C<.xml>, a tab-delimited first line to C<.tsv>, a pipe-delimited line to
 1860: C<.psv>, and everything else to C<.csv>.  The temp file is then renamed to
 1861: the detected extension before further processing.
 1862: 
 1863: =item B<Multi-table SQLite: opening without internal_table silently picks the first table>
 1864: 
 1865: When a SQLite file contains more than one user-defined table and you call
 1866: C<new()> without C<internal_table>, C<DataSource> auto-selects the first
 1867: table whose name matches the filename stem; if there is no match, it picks
 1868: whatever C<sqlite_master> lists first.  This is B<silent> -- you get data
 1869: from a table you may not have intended to open.
 1870: 
 1871: Always check C<sqlite_tables()> after construction if you are dealing
 1872: with a SQLite file that might have multiple tables:
 1873: 
 1874:     my $tbl_list = $source->sqlite_tables;
 1875:     if ($tbl_list && @{$tbl_list} > 1) {
 1876:         # warn the user or redirect to the schema browser
 1877:     }
 1878: 
 1879: =item B<The symlink used for .db-extension SQLite files is named .sql, not .db>
 1880: 
 1881: C<Database::Abstraction> does not use its DBI/SQLite backend for files
 1882: with a C<.db> extension -- it falls through to the CSV reader, which tries
 1883: to read a SQLite binary file as text and fails with a parse error.
 1884: 
 1885: When C<DataSource> detects a multi-table SQLite C<.db> file, it creates a
 1886: temporary symlink named C<E<lt>tableE<gt>.sql> (not C<.db>) pointing to the
 1887: original C<.db> file.  SQLite follows symlinks transparently, so the data is
 1888: read correctly.  If you ever audit temporary directories and see C<*.sql>
 1889: symlinks pointing at C<*.db> files, this is expected and intentional.
 1890: 
 1891: =item B<DBD::CSV silently lowercases column names for files larger than 16 KB>
 1892: 
 1893: C<Database::Abstraction> uses C<Text::xSV::Slurp> for files up to 16 KB and
 1894: DBD::CSV for larger ones.  The DBD::CSV path lowercases column names and
 1895: replaces spaces with underscores (C<Account Number> becomes
 1896: C<account_number>), which causes a C<"disallowed key"> error at render time
 1897: when the template iterates the original column names.  C<DataSource> avoids
 1898: this by always passing C<max_slurp_size =E<gt> -s $path> to
 1899: C<Database::Abstraction>, forcing the slurp path regardless of file size.
 1900: If you call C<Database::Abstraction> directly, you B<must> pass this option
 1901: yourself for any file whose column names contain spaces or mixed case.
 1902: 
 1903: =back

 1905: =head1 LIMITATIONS
 1906: 
 1907: =over 4
 1908: 
 1909: =item *
 1910: 
 1911: Only read operations are supported.  Write-back is not in scope.
 1912: 
 1913: =item *
 1914: 
 1915: One C<DataSource> instance corresponds to exactly one table.  Multi-table
 1916: joins are now delegated to C<Database::Join> (see L<Database::Join>), which
 1917: accepts C<DataSource> objects directly as component databases via the
 1918: C<selectall_arrayref> and C<columns> methods this class exposes.
 1919: 
 1920: =item *
 1921: 
 1922: The ephemeral backend class is generated into a package namespace
 1923: (C<Database::BI::_DB::*>) that persists for the lifetime of the process.
 1924: Instantiating two C<DataSource> objects for the same table name reuses
 1925: the same ephemeral class.
 1926: 
 1927: =item *
 1928: 
 1929: The C<i18n> object, if supplied, must implement C<maketext($key, @args)>
 1930: compatible with L<Locale::Maketext>.

 2089:           /     \
 2090:          /       \

 2093:   |  ERROR   |  |   READY   |
