   94: =head1 DESCRIPTION
   95: 
   96: C<Database::BI::Model::DataSource> is a thin, table-agnostic adapter that
   97: wraps L<Database::Abstraction> and exposes three accessors (C<fetch_all>,
   98: C<columns>, C<id_column>) used by the controller.
   99: 
  100: L<Database::Abstraction> is a read-only ORM that discovers data files
  101: (CSV, PSV, SQLite, XML, etc.) automatically from a directory based on the
  102: calling class name.  C<DataSource> generates an ephemeral subclass at
  103: construction time so callers never interact with L<Database::Abstraction>
  104: directly.  To swap the backend for L<Database::Join> in Phase 2, only the
  105: C<open_table> helper in C<Database::BI> needs to change; the controller and
  106: C<DataSource> are untouched.
  107: 
  108: C<_detect_file_info> peeks at the first header line of CSV/PSV files to
  109: extract the correct separator character, the primary-key column name, and
  110: the full ordered column list.  Without this, two silent L<Database::Abstraction>
  111: defaults corrupt every result: C<sep_char> defaults to C<'!'> (turning a
  112: comma-separated file into a single-field table) and C<id> defaults to
  113: C<'entry'> (causing every row to be discarded when no C<entry> column
  114: exists).
  115: 
  116: Result filtering (C<eq>, C<contains>, C<gt>, etc.) is performed at the
  117: controller layer by C<Dashboard::_apply_filter_spec> after C<fetch_all>
  118: returns.  C<DataSource> itself is filter-unaware.
  119: 
  120: All user-visible strings and exception messages are keyed through the

 1111: =head1 COMMON PITFALLS
 1112: 
 1113: These are the most common mistakes when using C<DataSource>.
 1114: 
 1115: =over 4
 1116: 
 1117: =item B<SQLite databases must use .sql as their file extension>
 1118: 
 1119: C<Database::Abstraction> looks for SQLite databases with the C<.sql> extension.
 1120: It does B<not> recognise C<.sqlite>, C<.sqlite3>, or C<.db3>.  If you have a
 1121: file called C<inventory.sqlite>, rename it to C<inventory.sql> before passing
 1122: it to C<DataSource>.
 1123: 
 1124: =item B<The table name is always lowercased>
 1125: 
 1126: The constructor lowercases the C<table> argument before using it.  Passing
 1127: C<table =E<gt> 'Sales'> and C<table =E<gt> 'sales'> both look for
 1128: C<sales.csv> (or C<sales.sql>, etc.).  The matching is case-insensitive on the
 1129: table name but B<case-sensitive on the directory path>.
 1130: 
 1131: =item B<CSV files with the wrong separator appear as one giant field per row>
 1132: 
 1133: C<Database::Abstraction> defaults to C<!> (exclamation mark) as its field
 1134: separator.  A standard comma-separated CSV file will look like one big field
 1135: per row (for example, C<1,Widget A,North,100>) because the library never sees
 1136: the commas as separators.  C<DataSource> fixes this automatically by reading
 1137: the first line of the file and detecting the actual separator.  If you bypass
 1138: C<DataSource> and call C<Database::Abstraction> directly, you B<must> pass
 1139: C<sep_char =E<gt> ','> yourself.
 1140: 
 1141: =item B<A table with no "entry" column returns zero rows (without DataSource)>
 1142: 
 1143: C<Database::Abstraction> uses C<entry> as its default primary-key column name.
 1144: When slurping a CSV, it discards any row where C<$row-E<gt>{entry}> is
 1145: undefined.  Because most CSV files do not have an C<entry> column, B<all rows
 1146: are silently discarded>.  C<DataSource> prevents this by reading the actual
 1147: first column name from the CSV header and passing it as C<id>, and also by
 1148: setting C<no_entry =E<gt> 1> so all rows are kept as an ordered array.
 1149: 
 1150: =item B<columns() returns undef for SQLite and XML files>
 1151: 
 1152: C<columns()> only returns an arrayref for file formats where the header order
 1153: is visible before data is read (CSV and PSV).  For SQLite and XML files it
 1154: returns C<undef>.  Always check: C<if ($source-E<gt>columns) { ... }>.  The
 1155: controller falls back to putting C<id_column> first and then sorting the rest
 1156: alphabetically when C<columns()> is C<undef>.
 1157: 
 1158: =item B<XML elements named "name", "id", or "key" cause parse failures>
 1159: 
 1160: C<XML::Simple> (used by C<Database::Abstraction> for XML files) automatically
 1161: turns a child element called C<name>, C<id>, or C<key> into a hash key instead
 1162: of keeping it as an array element.  This breaks the expected data structure.
 1163: Use different element names in your XML: for example, C<E<lt>skuE<gt>>,
 1164: C<E<lt>labelE<gt>>, or C<E<lt>codeE<gt>> instead of C<E<lt>idE<gt>> and
 1165: C<E<lt>nameE<gt>>.
 1166: 
 1167:   <!-- WRONG: these element names trigger XMLin key-folding -->
 1168:   <items>
 1169:     <item><id>1</id><name>Widget</name></item>
 1170:   </items>
 1171: 
 1172:   <!-- CORRECT: use neutral element names -->
 1173:   <items>
 1174:     <item><sku>1</sku><label>Widget</label></item>
 1175:   </items>
 1176: 
 1177: =item B<fetch_all returns an empty arrayref, not undef, for an empty table>
 1178: 
 1179: When a table exists but contains no data rows, C<fetch_all> returns C<[]> (an
 1180: empty arrayref), not C<undef>.  Check with C<scalar @{$records}>, not with
 1181: C<defined $records> or C<$records>.
 1182: 
 1183: =item B<0-byte CSV/PSV files bypass Database::Abstraction entirely>
 1184: 
 1185: When C<_detect_file_info> opens a CSV or PSV file and the first C<readline>
 1186: returns C<undef> (the file is 0 bytes), it returns a C<{ _file_is_empty =E<gt>
 1187: 1 }> sentinel instead of the normal C<{ id, sep_char, columns, file_size }>
 1188: hashref.  C<_init_backend> detects this sentinel and skips
 1189: C<Database::Abstraction> construction; C<fetch_all> returns C<[]> immediately.
 1190: B<No DBI connection is created for 0-byte files.>  If you mock or spy on DBI
 1191: handles and open a 0-byte CSV, the mock will never fire â€” this is expected
 1192: behaviour, not a mock misconfiguration.
