   94: =head1 DESCRIPTION
   95: 
   96: C<Database::BI::Model::DataSource> is a thin, table-agnostic adapter that
   97: wraps L<Database::Abstraction> and exposes three accessors (C<fetch_all>,
   98: C<columns>, C<id_column>) used by the controller.
   99: 
  100: L<Database::Abstraction> is a read-only ORM that discovers data files
  101: (CSV, PSV, SQLite, XML, etc.) automatically from a directory based on the
  102: calling class name.  C<DataSource> generates an ephemeral subclass at
  103: construction time so callers never interact with L<Database::Abstraction>
  104: directly.  To swap the backend for L<Database::Join> in Phase 2, only the
  105: C<open_table> helper in C<Database::BI> needs to change; the controller and
  106: C<DataSource> are untouched.
  107: 
  108: C<_detect_file_info> peeks at the first header line of CSV/PSV files to
  109: extract the correct separator character, the primary-key column name, and
  110: the full ordered column list.  Without this, two silent L<Database::Abstraction>
  111: defaults corrupt every result: C<sep_char> defaults to C<'!'> (turning a
  112: comma-separated file into a single-field table) and C<id> defaults to
  113: C<'entry'> (causing every row to be discarded when no C<entry> column
  114: exists).
  115: 
  116: Result filtering (C<eq>, C<contains>, C<gt>, etc.) is performed at the
  117: controller layer by C<Dashboard::_apply_filter_spec> after C<fetch_all>
  118: returns.  C<DataSource> itself is filter-unaware.
  119: 
  120: All user-visible strings and exception messages are keyed through the
  121: C<%MESSAGES> dictionary and routed via C<_msg()>, making every diagnostic
  122: replaceable by an i18n object at instantiation time.

 1046: =head1 COMMON PITFALLS
 1047: 
 1048: These are the most common mistakes when using C<DataSource>.
 1049: 
 1050: =over 4
 1051: 
 1052: =item B<SQLite databases must use .sql as their file extension>
 1053: 
 1054: C<Database::Abstraction> looks for SQLite databases with the C<.sql> extension.
 1055: It does B<not> recognise C<.sqlite>, C<.sqlite3>, or C<.db3>.  If you have a
 1056: file called C<inventory.sqlite>, rename it to C<inventory.sql> before passing
 1057: it to C<DataSource>.
 1058: 
 1059: =item B<The table name is always lowercased>
 1060: 
 1061: The constructor lowercases the C<table> argument before using it.  Passing
 1062: C<table =E<gt> 'Sales'> and C<table =E<gt> 'sales'> both look for
 1063: C<sales.csv> (or C<sales.sql>, etc.).  The matching is case-insensitive on the
 1064: table name but B<case-sensitive on the directory path>.
 1065: 
 1066: =item B<CSV files with the wrong separator appear as one giant field per row>
 1067: 
 1068: C<Database::Abstraction> defaults to C<!> (exclamation mark) as its field
 1069: separator.  A standard comma-separated CSV file will look like one big field
 1070: per row (for example, C<1,Widget A,North,100>) because the library never sees
 1071: the commas as separators.  C<DataSource> fixes this automatically by reading
 1072: the first line of the file and detecting the actual separator.  If you bypass
 1073: C<DataSource> and call C<Database::Abstraction> directly, you B<must> pass
 1074: C<sep_char =E<gt> ','> yourself.
 1075: 
 1076: =item B<A table with no "entry" column returns zero rows (without DataSource)>
 1077: 
 1078: C<Database::Abstraction> uses C<entry> as its default primary-key column name.
 1079: When slurping a CSV, it discards any row where C<$row-E<gt>{entry}> is
 1080: undefined.  Because most CSV files do not have an C<entry> column, B<all rows
 1081: are silently discarded>.  C<DataSource> prevents this by reading the actual
 1082: first column name from the CSV header and passing it as C<id>, and also by
 1083: setting C<no_entry =E<gt> 1> so all rows are kept as an ordered array.
 1084: 
 1085: =item B<columns() returns undef for SQLite and XML files>
 1086: 
 1087: C<columns()> only returns an arrayref for file formats where the header order
 1088: is visible before data is read (CSV and PSV).  For SQLite and XML files it
 1089: returns C<undef>.  Always check: C<if ($source-E<gt>columns) { ... }>.  The
 1090: controller falls back to putting C<id_column> first and then sorting the rest
 1091: alphabetically when C<columns()> is C<undef>.
 1092: 
 1093: =item B<XML elements named "name", "id", or "key" cause parse failures>
 1094: 
 1095: C<XML::Simple> (used by C<Database::Abstraction> for XML files) automatically
 1096: turns a child element called C<name>, C<id>, or C<key> into a hash key instead
 1097: of keeping it as an array element.  This breaks the expected data structure.
 1098: Use different element names in your XML: for example, C<E<lt>skuE<gt>>,
 1099: C<E<lt>labelE<gt>>, or C<E<lt>codeE<gt>> instead of C<E<lt>idE<gt>> and
 1100: C<E<lt>nameE<gt>>.
 1101: 
 1102:   <!-- WRONG: these element names trigger XMLin key-folding -->
 1103:   <items>
 1104:     <item><id>1</id><name>Widget</name></item>
 1105:   </items>
 1106: 
 1107:   <!-- CORRECT: use neutral element names -->
 1108:   <items>
 1109:     <item><sku>1</sku><label>Widget</label></item>
 1110:   </items>
 1111: 
 1112: =item B<fetch_all returns an empty arrayref, not undef, for an empty table>
 1113: 
 1114: When a table exists but contains no data rows, C<fetch_all> returns C<[]> (an
 1115: empty arrayref), not C<undef>.  Check with C<scalar @{$records}>, not with
 1116: C<defined $records> or C<$records>.
 1117: 
 1118: =item B<0-byte CSV/PSV files bypass Database::Abstraction entirely>
 1119: 
 1120: When C<_detect_file_info> opens a CSV or PSV file and the first C<readline>
 1121: returns C<undef> (the file is 0 bytes), it returns a C<{ _file_is_empty =E<gt>
 1122: 1 }> sentinel instead of the normal C<{ id, sep_char, columns, file_size }>
 1123: hashref.  C<_init_backend> detects this sentinel and skips
 1124: C<Database::Abstraction> construction; C<fetch_all> returns C<[]> immediately.
 1125: B<No DBI connection is created for 0-byte files.>  If you mock or spy on DBI
 1126: handles and open a 0-byte CSV, the mock will never fire â€” this is expected
 1127: behaviour, not a mock misconfiguration.
 1128: 
 1129: =back

 1131: =head1 LIMITATIONS
 1132: 
 1133: =over 4
 1134: 
 1135: =item *
 1136: 
 1137: Only read operations are supported.  Write-back is not in scope.
 1138: 
 1139: =item *
 1140: 
 1141: One C<DataSource> instance corresponds to exactly one table.  Multi-table
 1142: joins are now delegated to C<Database::Join> (see L<Database::Join>), which
 1143: accepts C<DataSource> objects directly as component databases via the
 1144: C<selectall_arrayref> and C<columns> methods this class exposes.
 1145: 
 1146: =item *
 1147: 
 1148: The ephemeral backend class is generated into a package namespace
 1149: (C<Database::BI::_DB::*>) that persists for the lifetime of the process.
 1150: Instantiating two C<DataSource> objects for the same table name reuses
 1151: the same ephemeral class.
 1152: 
 1153: =item *
 1154: 
 1155: The C<i18n> object, if supplied, must implement C<maketext($key, @args)>
 1156: compatible with L<Locale::Maketext>.

 1158: =back
