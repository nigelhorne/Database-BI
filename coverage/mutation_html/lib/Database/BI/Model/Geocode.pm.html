  262: =head1 DESCRIPTION
  263: 
  264: The geocoder is a L<Geo::Coder::List> chain:
  265: 
  266:     Geo::Coder::List->new()
  267:         ->push(Geo::Coder::Free->new())   # the local data
  268:         ->push(Geo::Coder::OSM->new());   # OpenStreetMap's Nominatim
  269: 
  270: C<Geo::Coder::Free> answers from data on this machine.  A place it does not know
  271: is asked of Nominatim, over the network, through an L<LWP::UserAgent::Throttled>
  272: that keeps Nominatim's usage policy: one request a second, from a client that
  273: names itself (C<Database-BI/I<version>>), with a ten-second time-out.  The user
  274: agent is shared by every lookup in the process, so the gap holds across
  275: requests.  Nominatim is told the place name and nothing else.
  276: 
  277: A table column holds something less tidy than a place name: values repeated
  278: thousands of times, blank cells, numbers that drifted in from an adjacent
  279: column.  This module does the three things the column then needs.
  280: 
  281: =over 4
  282: 
  283: =item B<Ask once per distinct value.>
  284: 
  285: The column is reduced to a set before any lookup happens.  A repeated city name
  286: costs one lookup, so a 100,000-row file with a dozen cities costs twelve lookups,
  287: not 100,000.
  288: 
  289: =item B<Refuse a value that is not a location before any backend sees it.>
  290: 
  291: C<< $geocoder->valid_location($value) >> is the gate the geocoder's own guard
  292: applies before looking anything up.  This module asks the same question first, so
  293: a pure-digit string (a row number that ended up in the wrong column), an empty
  294: cell, or a Perl reference is counted and reported as skipped rather than sent to
  295: a backend that would reject it anyway.
  296: 
  297: =item B<Look the rest up without letting one value end the batch.>
  298: 
  299: Each place goes down a C<Geo::Coder::List> on its own: the local data, then
  300: Nominatim when it is in the chain.  With the local data alone the list holds
  301: only C<Geo::Coder::Free>, which is given the C<region> hint (C<Geo::Coder::OSM>
  302: would put it in the Nominatim query).  Either way the list's cache answers what
  303: it has found before.  C<Geo::Coder::List> catches what a geocoder throws and
  304: asks the next one, so a throw does not end the request; a place whose lookup
  305: threw and found nothing is held (put in C<not_attempted>, not cached), because "not found" is
  306: remembered for good and an error is not an answer.
  307: 
  308: An injected C<geocoder> is asked for one C<geocode_many()> batch instead,
  309: requested with C<< on_error => 'undef' >>.  A value it refuses after the
  310: pre-filter is a miss; a backend that throws is still a throw, because nothing
  311: here wraps it in an C<eval>.
  312: 
  313: =item B<Tell a Nominatim that failed from a place it does not know.>
  314: 
  315: C<Geo::Coder::OSM> answers nothing in both cases.  The chain's log says whether
  316: Nominatim was asked, and its last response says whether it answered.  A place
  317: it failed on is held, not remembered as not found, and Nominatim is not asked
  318: again in that request: the rest are asked of the local data alone, and the ones
  319: it does not know are held too.  The page is told Nominatim's status line and how
  320: many places wait, never which.
  321: 
  322: =back
  323: 
  324: The counts the module returns add up, always.
  325: 
  326:     skipped + cached + attempted + not_attempted  ==  distinct
  327:     resolved + unresolved                         ==  cached + attempted
  328: 
  329: C<lookups> is the number of places that reached a geocoder rather than the
  330: chain's own cache.  For an injected geocoder it is the number that geocoder
  331: reports for the batch, which C<Geo::Coder::Free> 0.48 and later keeps lower than
  332: C<attempted> when a value is answered from a warm process cache.  It never exceeds
  333: C<attempted>.  C<online> is how many of them were asked of Nominatim.
  334: 
  335: =head2 The cache
  336: 
  337: A cache entry is a C<[lat, lon]> arrayref for a place that resolved, or the
  338: scalar C<0> for a place that was looked up and not found.  That C<0> sentinel
  339: prevents a column of unresolvable values from being retried on every page
  340: request.
  341: 
  342: The cache is passed per call and returned per call.  The caller's hashref is
  343: never modified: a request that dies part way through cannot leave a half-written
  344: cache behind.  The controller is responsible for persisting the returned cache,
  345: which keeps the C<model_dir>-inside-C<data_dir> guard in the one place that
  346: already owns it.
  347: 
  348: A previously stored cache is used even when the geocoder is not available.
  349: Places already resolved continue to be plotted; only new lookups are unavailable.
  350: 
  351: =head2 Without the geocoder
  352: 
  353: C<Geo::Coder::Free> and C<Geo::Coder::List> are recommended dependencies, not
  354: required ones.  They are loaded the first time they are needed, not at compile
  355: time.  C<Geo::Coder::OSM> and C<LWP::UserAgent::Throttled> are recommended too;
  356: without them the chain is the local data alone, and a request with places it
  357: did not know says so (C<warn_map_geocoder_local_only>).  When
  358: C<Geo::Coder::Free> or C<Geo::Coder::List> is absent or older than its minimum
  359: version:
  360: 
  361: =over 4
  362: 
  363: =item *
  364: 
  365: C<< $geocode->geocoder_available() >> returns C<(0, $reason)>.
  366: 
  367: =item *
  368: 
  369: C<resolve_column> and C<resolve_values> still return a complete result: all
  370: values are placed in C<not_attempted>, cached answers are still plotted, and
  371: the C<error_map_geocoder_missing> message explains the situation.
  372: 
  373: =item *
  374: 
  375: Nothing croaks.  The page renders with whatever the cache already holds.
  376: 
  377: =back

  470: =head2 resolve_column
  471: 
  472:     my $result = $geocode->resolve_column(\@rows, $column_name, %options);
  473: 
  474: Resolve one named column of a table.  C<\@rows> is an arrayref of hashrefs
  475: (the records from the data pipeline), and C<$column_name> is the key to look
  476: up in each row.
  477:

  479: resolution as L</resolve_values>, then adds per-marker row counts and the

  481: 
  482: =head3 API SPECIFICATION
  483: 
  484: =head4 INPUT
  485: 
  486:     \@rows          => arrayref of hashrefs, required
  487:     $column_name    => non-empty string, required
  488:     cache    => hashref,            # optional; { value => [lat, lon] | 0 }
  489:     region   => two-letter string,  # optional; country hint for the geocoder (e.g. 'GB')
  490:     max      => positive integer,   # optional; max new lookups; default 500

  493: C<\@rows> is the full record set as returned by the pipeline.  Rows that are
  494: not hashrefs produce an C<undef> cell, which is classified as skipped.
  495: 
  496: C<$column_name> must be a non-empty string.  It is used as a hash key; it is
  497: not validated against a schema, so a column name with spaces or special
  498: characters is accepted if the data uses one.
  499: 
  500: C<cache> holds the already-known answers for this column.  Entries are either
  501: a C<[lat, lon]> arrayref (resolved) or C<0> (looked up and not found).  The

  503: updated copy.

  505: C<region> is passed straight through to the geocoder as a country hint.  It

  507: country.
  508: 
  509: C<max> is counted in new lookups, not rows.  A cached answer costs nothing
  510: and does not count toward it.  Values held back by the cap go into
  511: C<not_attempted> and are not stored in the cache, so the next request picks
  512: them up.
  513: 
  514: C<lookup =E<gt> 0> plots from C<cache> alone and asks the geocoder nothing.
  515: The places it would have asked (up to C<max>, in first-seen order) are returned
  516: in C<pending>, and are counted in C<not_attempted> meanwhile.  A caller can then
  517: look them up one at a time with L</resolve_values>, saving each answer as it
  518: comes, which is how the map page shows its progress and can be cancelled.  The

 2034: 
 2035: =over 4
 2036: 
 2037: =item B<The cache sentinel 0 is not "false -- never looked up".>
 2038: 
 2039: A cache entry of C<0> means the place was looked up and not found.  An absent
 2040: key means it has never been attempted.  The module treats these two states
 2041: differently: a C<0> entry contributes to C<counts.unresolved> without
 2042: triggering a new lookup; an absent key enters the classification loop and may
 2043: reach the geocoder.
 2044: 
 2045:     # WRONG -- checking definedness misses the 0 sentinel.
 2046:     my $resolved = defined($cache{$place});
 2047: 
 2048:     # CORRECT -- use the internal _has_position logic.
 2049:     my $resolved = (ref($cache{$place}) eq 'ARRAY');

 2051: =item B<Pure-digit strings are skipped, not attempted.>
 2052: 
 2053: A value like C<'42'> fails C<valid_location()> and goes into C<@skipped>.  It
 2054: is never stored in the cache.  This is the correct behaviour for a row number
 2055: that ended up in the wrong column, but it surprises callers who expect every
 2056: non-empty value to be attempted.

 2059: 
 2060: Do not compare C<$cache_you_passed_in> with C<$result->{'cache'}> expecting
 2061: them to be the same reference.  The update is in C<$result->{'cache'}>.
 2062: 
 2063: =item B<resolve_column croaks when the column is absent; resolve_values does not.>
 2064: 
 2065: C<resolve_column> checks that the named column appears in at least one row.
 2066: If it does not, it croaks with C<error_map_loc_column>.  C<resolve_values>
 2067: does not do this check, because it receives values, not rows.
 2068: 
 2069: =item B<max counts new lookups, not rows or distinct values.>
 2070: 
 2071: A value already in C<cache> does not count toward C<max>, even if it was
 2072: looked up in a previous request.  A value skipped by C<valid_location()> does
 2073: not count either.

 2385: =head1 STATE DIAGRAM
 2386: 
 2387: The object is in one of three states, according to whether it has a geocoder yet.
 2388: A geocoder given to C<new> is one straight away; otherwise one is looked for on
 2389: the first call that needs it.
 2390: 
 2391:     new()
 2392:       |
 2393:       +--[bad arguments, or a geocoder lacking
 2394:       |   valid_location or geocode_many]-----> croaks; no object
 2395:       |
 2396:       +--[geocoder => $g]---------------------> READY
 2397:       |
 2398:       v
 2399:   +-------------------+
 2400:   |    CONSTRUCTED    |  Geocoder not yet lazy-loaded.
 2401:   |  _geocoder not    |  resolve_*() and geocoder_available()
 2402:   |  yet called       |  may trigger a load on first call.
 2403:   +-------------------+
 2404:        |          |
 2405:   first call,     first call,
 2406:   module OK       module absent, too old or will not
 2407:        |          load, or its new() answers nothing
 2408:        v          v
 2409:   +---------+  +------------+
 2410:   |  READY  |  | UNAVAILABLE|
 2411:   |         |  |            |
 2412:   | Geocoder|  | No lookups |
 2413:   | loaded  |  | possible.  |
 2414:   | and     |  | Cache still|
 2415:   | working.|  | served.    |
 2416:   +---------+  +------------+
 2417:        |          |
 2418:   resolve_*()  resolve_*()
 2419:   geocodes +   cache only;
 2420:   cache        not_attempted
 2421:        |          |
 2422:        v          v
 2423:   +---------+  +------------+
 2424:   |  READY  |  | UNAVAILABLE|
 2425:   | (no     |  | (no        |
 2426:   | change) |  | change)    |
 2427:   +---------+  +------------+
 2428: 
 2429: Once the object is READY or UNAVAILABLE that does not change: neither a module
 2430: that appears nor one that goes away moves it, and the module is looked for once.
 2431: 
 2432: There are two ways for a call to croak and leave the state as it was.  Arguments a
 2433: resolve_*() call refuses are refused before any load is attempted.  A module that
 2434: loads and whose new() dies sends that exception to the caller and remembers
 2435: nothing, so the object stays CONSTRUCTED and the next call tries again.
 2436: 
 2437: Resolution itself is stateless: all state is in the result hashref and the cache
 2438: the caller manages.
 2439: 
 2440:     Valid state transitions summary:
 2441: 
 2442:     [START]          -> CONSTRUCTED      (new() with no geocoder)
 2443:     [START]          -> READY            (new() given a geocoder)
 2444:     [START]          -> ERROR            (new() refuses its arguments; croaks, no object)
 2445:     CONSTRUCTED      -> READY            (first call, module OK)
 2446:     CONSTRUCTED      -> UNAVAILABLE      (first call, no module that can be used)
 2447:     CONSTRUCTED      -> CONSTRUCTED      (arguments refused, or the module's new() dies; croaks)
 2448:     READY            -> READY            (resolve_*(), or arguments refused)
 2449:     UNAVAILABLE      -> UNAVAILABLE      (resolve_*(), or arguments refused)
 2450: 
 2451: Value-level state transitions within a single resolve_* call.  Each distinct value
 2452: takes the first of these that applies, from the top.  CACHE is the C<cache> in the
 2453: result, a copy: the cache the caller passed in is never modified.
 2454: 
 2455:     RECEIVED
 2456:        |
 2457:        +--[undef / ref / empty]-----------> SKIPPED
 2458:        |
 2459:        +--[in cache, has position]---------> CACHED_RESOLVED --> POINTS
 2460:        |
 2461:        +--[in cache, no position (= 0)]----> CACHED_UNRESOLVED --> UNRESOLVED
 2462:        |
 2463:        +--[geocoder unavailable]-----------> NOT_ATTEMPTED
 2464:        |
 2465:        +--[valid_location() throws]--------> EXCEPTION
 2466:        |
 2467:        +--[valid_location() = false]-------> SKIPPED
 2468:        |
 2469:        +--[within cap]--------------------> ATTEMPT
 2470:        |                                        |
 2471:        |                                        +--[geocoder returns position]--> RESOLVED_NEW --> POINTS, CACHE==[lat,lon]
 2472:        |                                        |
 2473:        |                                        +--[geocoder returns no position]--> UNRESOLVED_NEW, CACHE==0
 2474:        |                                        |
 2475:        |                                        +--[geocoder throws]--> EXCEPTION
 2476:        |
 2477:        +--[beyond cap]-------------------> NOT_ATTEMPTED
 2478: 
 2479: EXCEPTION is the whole request failing, on purpose: it goes to the caller, who has
 2480: no result and a cache exactly as it was, so nothing can be half-written.
