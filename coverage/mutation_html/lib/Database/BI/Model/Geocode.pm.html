  258: =head1 DESCRIPTION
  259: 
  260: The geocoder is a L<Geo::Coder::List> chain:
  261: 
  262:     Geo::Coder::List->new()
  263:         ->push(Geo::Coder::Free->new())   # the local data
  264:         ->push(Geo::Coder::OSM->new());   # OpenStreetMap's Nominatim
  265: 
  266: C<Geo::Coder::Free> answers from data on this machine.  A place it does not know
  267: is asked of Nominatim, over the network, through an L<LWP::UserAgent::Throttled>
  268: that keeps Nominatim's usage policy: one request a second, from a client that
  269: names itself (C<Database-BI/I<version>>), with a ten-second time-out.  The user
  270: agent is shared by every lookup in the process, so the gap holds across
  271: requests.  Nominatim is told the place name and nothing else.
  272: 
  273: A table column holds something less tidy than a place name: values repeated
  274: thousands of times, blank cells, numbers that drifted in from an adjacent
  275: column.  This module does the three things the column then needs.
  276: 
  277: =over 4
  278: 
  279: =item B<Ask once per distinct value.>
  280: 
  281: The column is reduced to a set before any lookup happens.  A repeated city name
  282: costs one lookup, so a 100,000-row file with a dozen cities costs twelve lookups,
  283: not 100,000.
  284: 
  285: =item B<Refuse a value that is not a location before any backend sees it.>
  286: 
  287: C<< $geocoder->valid_location($value) >> is the gate the geocoder's own guard
  288: applies before looking anything up.  This module asks the same question first, so
  289: a pure-digit string (a row number that ended up in the wrong column), an empty
  290: cell, or a Perl reference is counted and reported as skipped rather than sent to
  291: a backend that would reject it anyway.
  292: 
  293: =item B<Look the rest up without letting one value end the batch.>
  294: 
  295: Each place goes down a C<Geo::Coder::List> on its own: the local data, then
  296: Nominatim when it is in the chain.  With the local data alone the list holds
  297: only C<Geo::Coder::Free>, which is given the C<region> hint (C<Geo::Coder::OSM>
  298: would put it in the Nominatim query).  Either way the list's cache answers what
  299: it has found before.  C<Geo::Coder::List> catches what a geocoder throws and
  300: asks the next one, so a throw does not end the request; a place whose lookup
  301: threw and found nothing is held (put in C<not_attempted>, not cached), because "not found" is
  302: remembered for good and an error is not an answer.
  303: 
  304: An injected C<geocoder> is asked for one C<geocode_many()> batch instead,
  305: requested with C<< on_error => 'undef' >>.  A value it refuses after the
  306: pre-filter is a miss; a backend that throws is still a throw, because nothing
  307: here wraps it in an C<eval>.
  308: 
  309: =item B<Tell a Nominatim that failed from a place it does not know.>
  310: 
  311: C<Geo::Coder::OSM> answers nothing in both cases.  The chain's log says whether
  312: Nominatim was asked, and its last response says whether it answered.  A place
  313: it failed on is held, not remembered as not found, and Nominatim is not asked
  314: again in that request: the rest are asked of the local data alone, and the ones
  315: it does not know are held too.  The page is told Nominatim's status line and how
  316: many places wait, never which.
  317: 
  318: =back
  319: 
  320: The counts the module returns add up, always.
  321: 
  322:     skipped + cached + attempted + not_attempted  ==  distinct
  323:     resolved + unresolved                         ==  cached + attempted
  324: 
  325: C<lookups> is the number of places that reached a geocoder rather than the
  326: chain's own cache.  For an injected geocoder it is the number that geocoder
  327: reports for the batch, which C<Geo::Coder::Free> 0.48 and later keeps lower than
  328: C<attempted> when a value is answered from a warm process cache.  It never exceeds
  329: C<attempted>.  C<online> is how many of them were asked of Nominatim.
  330: 
  331: =head2 The cache
  332: 
  333: A cache entry is a C<[lat, lon]> arrayref for a place that resolved, or the
  334: scalar C<0> for a place that was looked up and not found.  That C<0> sentinel
  335: prevents a column of unresolvable values from being retried on every page
  336: request.
  337: 
  338: The cache is passed per call and returned per call.  The caller's hashref is
  339: never modified: a request that dies part way through cannot leave a half-written
  340: cache behind.  The controller is responsible for persisting the returned cache,
  341: which keeps the C<model_dir>-inside-C<data_dir> guard in the one place that
  342: already owns it.
  343: 
  344: A previously stored cache is used even when the geocoder is not available.
  345: Places already resolved continue to be plotted; only new lookups are unavailable.
  346: 
  347: =head2 Without the geocoder
  348: 
  349: C<Geo::Coder::Free> and C<Geo::Coder::List> are recommended dependencies, not
  350: required ones.  They are loaded the first time they are needed, not at compile
  351: time.  C<Geo::Coder::OSM> and C<LWP::UserAgent::Throttled> are recommended too;
  352: without them the chain is the local data alone, and a request with places it
  353: did not know says so (C<warn_map_geocoder_local_only>).  When
  354: C<Geo::Coder::Free> or C<Geo::Coder::List> is absent or older than its minimum
  355: version:
  356: 
  357: =over 4
  358: 
  359: =item *
  360: 
  361: C<< $geocode->geocoder_available() >> returns C<(0, $reason)>.
  362: 
  363: =item *
  364: 
  365: C<resolve_column> and C<resolve_values> still return a complete result: all
  366: values are placed in C<not_attempted>, cached answers are still plotted, and
  367: the C<error_map_geocoder_missing> message explains the situation.
  368: 
  369: =item *
  370: 
  371: Nothing croaks.  The page renders with whatever the cache already holds.
  372: 
  373: =back

  436: 
  437: =head2 resolve_column
  438: 
  439:     my $result = $geocode->resolve_column(\@rows, $column_name, %options);
  440: 
  441: Resolve one named column of a table.  C<\@rows> is an arrayref of hashrefs
  442: (the records from the data pipeline), and C<$column_name> is the key to look
  443: up in each row.
  444: 
  445: This is the main entry point for the map controller.  It runs the same
  446: resolution as L</resolve_values>, then adds per-marker row counts and the
  447: C<markers> list that a map rendering loop needs.
  448: 
  449: =head3 API SPECIFICATION
  450: 
  451: =head4 INPUT
  452: 
  453:     \@rows          => arrayref of hashrefs, required
  454:     $column_name    => non-empty string, required
  455:     cache    => hashref,            # optional; { value => [lat, lon] | 0 }
  456:     region   => two-letter string,  # optional; country hint for the geocoder (e.g. 'GB')
  457:     max      => positive integer,   # optional; max new lookups; default 500
  458:     lookup   => 0 | 1,              # optional; 0 asks nothing and lists what it would ask; default 1
  459: 
  460: C<\@rows> is the full record set as returned by the pipeline.  Rows that are
  461: not hashrefs produce an C<undef> cell, which is classified as skipped.
  462: 
  463: C<$column_name> must be a non-empty string.  It is used as a hash key; it is
  464: not validated against a schema, so a column name with spaces or special
  465: characters is accepted if the data uses one.
  466: 
  467: C<cache> holds the already-known answers for this column.  Entries are either
  468: a C<[lat, lon]> arrayref (resolved) or C<0> (looked up and not found).  The
  469: caller's hashref is never modified; the returned C<cache> key holds the
  470: updated copy.
  471: 
  472: C<region> is passed straight through to the geocoder as a country hint.  It
  473: is not derived from the Accept-Language header, because a language is not a
  474: country.
  475: 
  476: C<max> is counted in new lookups, not rows.  A cached answer costs nothing
  477: and does not count toward it.  Values held back by the cap go into
  478: C<not_attempted> and are not stored in the cache, so the next request picks
  479: them up.
  480: 
  481: C<lookup =E<gt> 0> plots from C<cache> alone and asks the geocoder nothing.
  482: The places it would have asked (up to C<max>, in first-seen order) are returned
  483: in C<pending>, and are counted in C<not_attempted> meanwhile.  A caller can then
  484: look them up one at a time with L</resolve_values>, saving each answer as it
  485: comes, which is how the map page shows its progress and can be cancelled.  The
  486: geocoder is still loaded, because its rule decides which values are places.
  487: 
  488: =head4 OUTPUT
  489: 
  490: Returns a hashref:
  491:

  494:         points        => { $value => { lat => $n, lon => $n, rows => $n, first_row => $n, backend? => $s } },

  518:         capped        => 0 | 1,

  520: 
  521: C<points> holds one entry per value that produced a position, whether the
  522: position came from the cache or from this request.  C<markers> is the same

  525: 
  526: C<backend> on a point entry is set only for values looked up in this request;

  530:

  532:

 1876: 
 1877: =over 4
 1878: 
 1879: =item B<The cache sentinel 0 is not "false -- never looked up".>
 1880: 
 1881: A cache entry of C<0> means the place was looked up and not found.  An absent
 1882: key means it has never been attempted.  The module treats these two states
 1883: differently: a C<0> entry contributes to C<counts.unresolved> without
 1884: triggering a new lookup; an absent key enters the classification loop and may
 1885: reach the geocoder.
 1886: 
 1887:     # WRONG -- checking definedness misses the 0 sentinel.
 1888:     my $resolved = defined($cache{$place});
 1889: 
 1890:     # CORRECT -- use the internal _has_position logic.
 1891:     my $resolved = (ref($cache{$place}) eq 'ARRAY');
 1892: 
 1893: =item B<Pure-digit strings are skipped, not attempted.>
 1894: 
 1895: A value like C<'42'> fails C<valid_location()> and goes into C<@skipped>.  It
 1896: is never stored in the cache.  This is the correct behaviour for a row number
 1897: that ended up in the wrong column, but it surprises callers who expect every
 1898: non-empty value to be attempted.
 1899: 
 1900: =item B<The returned cache is a copy; the caller's hashref is never modified.>
 1901: 
 1902: Do not compare C<$cache_you_passed_in> with C<$result->{'cache'}> expecting
 1903: them to be the same reference.  The update is in C<$result->{'cache'}>.
 1904: 
 1905: =item B<resolve_column croaks when the column is absent; resolve_values does not.>
 1906: 
 1907: C<resolve_column> checks that the named column appears in at least one row.
 1908: If it does not, it croaks with C<error_map_loc_column>.  C<resolve_values>
 1909: does not do this check, because it receives values, not rows.
 1910: 
 1911: =item B<max counts new lookups, not rows or distinct values.>
 1912: 
 1913: A value already in C<cache> does not count toward C<max>, even if it was
 1914: looked up in a previous request.  A value skipped by C<valid_location()> does
 1915: not count either.
 1916: 
 1917: =item B<new() always succeeds; geocoder load failure is not a constructor error.>
 1918: 
 1919: You can always call C<new()> without checking whether C<Geo::Coder::Free> is
 1920: installed.  The load failure is deferred to the first call that needs the
 1921: geocoder, and is reported through C<geocoder_available()> and the
 1922: C<messages> array in the result, not through an exception.
 1923: 
 1924: =item B<cache_from_models and models_with_cache are class methods.>
 1925: 
 1926: You may call them on an instance for convenience, but the invocant is not used.
 1927: The pattern C<< Database::BI::Model::Geocode->cache_from_models(...) >> is
 1928: clearer.
 1929: 
 1930: =item B<An injected geocoder's batch receives on_error => 'undef'.>
 1931: 
 1932: A value an injected geocoder rejects after the C<valid_location()> pre-filter is
 1933: returned as C<undef> from the batch; it does not croak.  A backend that throws
 1934: an exception (a real database error, a network failure) still propagates

 1940: 
 1941: =over 4
 1942: 
 1943: =item B<Place names (values in the location column)>
 1944:
