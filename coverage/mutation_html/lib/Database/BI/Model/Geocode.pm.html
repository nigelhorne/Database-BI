  255: =head1 DESCRIPTION
  256: 
  257: The geocoder is a L<Geo::Coder::List> chain:
  258: 
  259:     Geo::Coder::List->new()
  260:         ->push(Geo::Coder::Free->new())   # the local data
  261:         ->push(Geo::Coder::OSM->new());   # OpenStreetMap's Nominatim
  262: 
  263: C<Geo::Coder::Free> answers from data on this machine.  A place it does not know
  264: is asked of Nominatim, over the network, through an L<LWP::UserAgent::Throttled>
  265: that keeps Nominatim's usage policy: one request a second, from a client that
  266: names itself (C<Database-BI/I<version>>), with a ten-second time-out.  The user
  267: agent is shared by every lookup in the process, so the gap holds across
  268: requests.  Nominatim is told the place name and nothing else.
  269: 
  270: A table column holds something less tidy than a place name: values repeated
  271: thousands of times, blank cells, numbers that drifted in from an adjacent
  272: column.  This module does the three things the column then needs.
  273: 
  274: =over 4
  275: 
  276: =item B<Ask once per distinct value.>
  277: 
  278: The column is reduced to a set before any lookup happens.  A repeated city name
  279: costs one lookup, so a 100,000-row file with a dozen cities costs twelve lookups,
  280: not 100,000.
  281: 
  282: =item B<Refuse a value that is not a location before any backend sees it.>
  283: 
  284: C<< $geocoder->valid_location($value) >> is the gate the geocoder's own guard
  285: applies before looking anything up.  This module asks the same question first, so
  286: a pure-digit string (a row number that ended up in the wrong column), an empty
  287: cell, or a Perl reference is counted and reported as skipped rather than sent to
  288: a backend that would reject it anyway.
  289: 
  290: =item B<Look the rest up without letting one value end the batch.>
  291: 
  292: Each place goes down a C<Geo::Coder::List> on its own: the local data, then
  293: Nominatim when it is in the chain.  With the local data alone the list holds
  294: only C<Geo::Coder::Free>, which is given the C<region> hint (C<Geo::Coder::OSM>
  295: would put it in the Nominatim query).  Either way the list's cache answers what
  296: it has found before.  C<Geo::Coder::List> catches what a geocoder throws and
  297: asks the next one, so a throw does not end the request; a place whose lookup
  298: threw and found nothing is held (put in C<not_attempted>, not cached), because "not found" is
  299: remembered for good and an error is not an answer.
  300: 
  301: An injected C<geocoder> is asked for one C<geocode_many()> batch instead,
  302: requested with C<< on_error => 'undef' >>.  A value it refuses after the
  303: pre-filter is a miss; a backend that throws is still a throw, because nothing
  304: here wraps it in an C<eval>.
  305: 
  306: =item B<Tell a Nominatim that failed from a place it does not know.>
  307: 
  308: C<Geo::Coder::OSM> answers nothing in both cases.  The chain's log says whether
  309: Nominatim was asked, and its last response says whether it answered.  A place
  310: it failed on is held, not remembered as not found, and Nominatim is not asked
  311: again in that request: the rest are asked of the local data alone, and the ones
  312: it does not know are held too.  The page is told Nominatim's status line and how
  313: many places wait, never which.
  314: 
  315: =back
  316: 
  317: The counts the module returns add up, always.
  318: 
  319:     skipped + cached + attempted + not_attempted  ==  distinct
  320:     resolved + unresolved                         ==  cached + attempted
  321: 
  322: C<lookups> is the number of places that reached a geocoder rather than the
  323: chain's own cache.  For an injected geocoder it is the number that geocoder
  324: reports for the batch, which C<Geo::Coder::Free> 0.48 and later keeps lower than
  325: C<attempted> when a value is answered from a warm process cache.  It never exceeds
  326: C<attempted>.  C<online> is how many of them were asked of Nominatim.
  327: 
  328: =head2 The cache
  329: 
  330: A cache entry is a C<[lat, lon]> arrayref for a place that resolved, or the
  331: scalar C<0> for a place that was looked up and not found.  That C<0> sentinel
  332: prevents a column of unresolvable values from being retried on every page
  333: request.
  334: 
  335: The cache is passed per call and returned per call.  The caller's hashref is
  336: never modified: a request that dies part way through cannot leave a half-written
  337: cache behind.  The controller is responsible for persisting the returned cache,
  338: which keeps the C<model_dir>-inside-C<data_dir> guard in the one place that
  339: already owns it.
  340: 
  341: A previously stored cache is used even when the geocoder is not available.
  342: Places already resolved continue to be plotted; only new lookups are unavailable.
  343: 
  344: =head2 Without the geocoder
  345: 
  346: C<Geo::Coder::Free> and C<Geo::Coder::List> are recommended dependencies, not
  347: required ones.  They are loaded the first time they are needed, not at compile
  348: time.  C<Geo::Coder::OSM> and C<LWP::UserAgent::Throttled> are recommended too;
  349: without them the chain is the local data alone, and a request with places it
  350: did not know says so (C<warn_map_geocoder_local_only>).  When
  351: C<Geo::Coder::Free> or C<Geo::Coder::List> is absent or older than its minimum
  352: version:
  353: 
  354: =over 4
  355: 
  356: =item *
  357: 
  358: C<< $geocode->geocoder_available() >> returns C<(0, $reason)>.
  359: 
  360: =item *
  361: 
  362: C<resolve_column> and C<resolve_values> still return a complete result: all
  363: values are placed in C<not_attempted>, cached answers are still plotted, and
  364: the C<error_map_geocoder_missing> message explains the situation.
  365: 
  366: =item *
  367: 
  368: Nothing croaks.  The page renders with whatever the cache already holds.
  369: 
  370: =back

  473: and does not count toward it.  Values held back by the cap go into

  475: them up.

 1845: =head1 COMMON PITFALLS
 1846: 
 1847: =over 4
 1848: 
 1849: =item B<The cache sentinel 0 is not "false -- never looked up".>
 1850: 
 1851: A cache entry of C<0> means the place was looked up and not found.  An absent
 1852: key means it has never been attempted.  The module treats these two states
 1853: differently: a C<0> entry contributes to C<counts.unresolved> without
 1854: triggering a new lookup; an absent key enters the classification loop and may
 1855: reach the geocoder.
 1856: 
 1857:     # WRONG -- checking definedness misses the 0 sentinel.
 1858:     my $resolved = defined($cache{$place});
 1859: 
 1860:     # CORRECT -- use the internal _has_position logic.
 1861:     my $resolved = (ref($cache{$place}) eq 'ARRAY');
 1862: 
 1863: =item B<Pure-digit strings are skipped, not attempted.>
 1864: 
 1865: A value like C<'42'> fails C<valid_location()> and goes into C<@skipped>.  It
 1866: is never stored in the cache.  This is the correct behaviour for a row number
 1867: that ended up in the wrong column, but it surprises callers who expect every
 1868: non-empty value to be attempted.
 1869: 
 1870: =item B<The returned cache is a copy; the caller's hashref is never modified.>
 1871: 
 1872: Do not compare C<$cache_you_passed_in> with C<$result->{'cache'}> expecting
 1873: them to be the same reference.  The update is in C<$result->{'cache'}>.
 1874: 
 1875: =item B<resolve_column croaks when the column is absent; resolve_values does not.>
 1876: 
 1877: C<resolve_column> checks that the named column appears in at least one row.
 1878: If it does not, it croaks with C<error_map_loc_column>.  C<resolve_values>
 1879: does not do this check, because it receives values, not rows.
 1880: 
 1881: =item B<max counts new lookups, not rows or distinct values.>
 1882: 
 1883: A value already in C<cache> does not count toward C<max>, even if it was
 1884: looked up in a previous request.  A value skipped by C<valid_location()> does
 1885: not count either.
 1886: 
 1887: =item B<new() always succeeds; geocoder load failure is not a constructor error.>
 1888: 
 1889: You can always call C<new()> without checking whether C<Geo::Coder::Free> is
 1890: installed.  The load failure is deferred to the first call that needs the
 1891: geocoder, and is reported through C<geocoder_available()> and the
 1892: C<messages> array in the result, not through an exception.
 1893: 
 1894: =item B<cache_from_models and models_with_cache are class methods.>
 1895: 
 1896: You may call them on an instance for convenience, but the invocant is not used.
 1897: The pattern C<< Database::BI::Model::Geocode->cache_from_models(...) >> is
 1898: clearer.
 1899: 
 1900: =item B<An injected geocoder's batch receives on_error => 'undef'.>
 1901: 
 1902: A value an injected geocoder rejects after the C<valid_location()> pre-filter is
 1903: returned as C<undef> from the batch; it does not croak.  A backend that throws
 1904: an exception (a real database error, a network failure) still propagates
 1905: upward, because nothing here wraps the geocoder in an C<eval>.
 1906: 
 1907: =back

 1909: =head1 ENCODING
 1910: 
 1911: =over 4
 1912: 
 1913: =item B<Place names (values in the location column)>
 1914: 
 1915: Passed to the geocoder as byte strings.  UTF-8 place names such as
 1916: "Koeln" or "Beijing" are supported if the geocoder backend handles them.
 1917: The internal code does not re-encode or validate the bytes; it compares them
 1918: as opaque strings for deduplication and caching.
 1919: 
 1920: =item B<Column names>
 1921: 
 1922: Matched against row hash keys with a string equality test.  The column name
 1923: must be byte-for-byte identical to the key in the row hashrefs.  Column names
 1924: with non-ASCII bytes are accepted.
 1925: 
 1926: =item B<Spec keys (the $spec_key argument)>
 1927: 
 1928: Used as hash keys in the model store.  Any byte sequence is safe; UTF-8 spec
 1929: keys are stored and retrieved without modification.
 1930: 
 1931: =item B<Message strings>
 1932: 
 1933: The built-in C<%MESSAGES> table contains ASCII-only text.  If your application
 1934: needs non-ASCII messages (for example, a French translation), supply an C<i18n>
 1935: object to C<new()> whose C<maketext> method renders the key in the desired
 1936: locale.
 1937: 
 1938: =item B<Geocoder result strings (backend names)>
 1939: 
 1940: Stored and reported as returned by the geocoder.  The module does not impose
 1941: any encoding on them.
 1942: 
 1943: =back

 2190: =head1 STATE DIAGRAM
 2191: 
 2192: The object is in one of three states, according to whether it has a geocoder yet.
 2193: A geocoder given to C<new> is one straight away; otherwise one is looked for on
 2194: the first call that needs it.
 2195: 
 2196:     new()
 2197:       |
 2198:       +--[bad arguments, or a geocoder lacking
 2199:       |   valid_location or geocode_many]-----> croaks; no object

 2201:       +--[geocoder => $g]---------------------> READY
 2202:       |
 2203:       v

 2205:   |    CONSTRUCTED    |  Geocoder not yet lazy-loaded.
 2206:   |  _geocoder not    |  resolve_*() and geocoder_available()
 2207:   |  yet called       |  may trigger a load on first call.
 2208:   +-------------------+
 2209:        |          |
 2210:   first call,     first call,
 2211:   module OK       module absent, too old or will not
 2212:        |          load, or its new() answers nothing
 2213:        v          v

 2215:   |  READY  |  | UNAVAILABLE|
 2216:   |         |  |            |
 2217:   | Geocoder|  | No lookups |
 2218:   | loaded  |  | possible.  |

 2222:        |          |

 2225:   cache        not_attempted

 2240: nothing, so the object stays CONSTRUCTED and the next call tries again.
