  257: =head1 DESCRIPTION
  258: 
  259: The geocoder is a L<Geo::Coder::List> chain:
  260: 
  261:     Geo::Coder::List->new()
  262:         ->push(Geo::Coder::Free->new())   # the local data
  263:         ->push(Geo::Coder::OSM->new());   # OpenStreetMap's Nominatim
  264: 
  265: C<Geo::Coder::Free> answers from data on this machine.  A place it does not know
  266: is asked of Nominatim, over the network, through an L<LWP::UserAgent::Throttled>
  267: that keeps Nominatim's usage policy: one request a second, from a client that
  268: names itself (C<Database-BI/I<version>>), with a ten-second time-out.  The user
  269: agent is shared by every lookup in the process, so the gap holds across
  270: requests.  Nominatim is told the place name and nothing else.
  271: 
  272: A table column holds something less tidy than a place name: values repeated
  273: thousands of times, blank cells, numbers that drifted in from an adjacent
  274: column.  This module does the three things the column then needs.
  275: 
  276: =over 4
  277: 
  278: =item B<Ask once per distinct value.>
  279: 
  280: The column is reduced to a set before any lookup happens.  A repeated city name
  281: costs one lookup, so a 100,000-row file with a dozen cities costs twelve lookups,
  282: not 100,000.
  283: 
  284: =item B<Refuse a value that is not a location before any backend sees it.>
  285: 
  286: C<< $geocoder->valid_location($value) >> is the gate the geocoder's own guard
  287: applies before looking anything up.  This module asks the same question first, so
  288: a pure-digit string (a row number that ended up in the wrong column), an empty
  289: cell, or a Perl reference is counted and reported as skipped rather than sent to
  290: a backend that would reject it anyway.
  291: 
  292: =item B<Look the rest up without letting one value end the batch.>
  293: 
  294: Each place goes down a C<Geo::Coder::List> on its own: the local data, then
  295: Nominatim when it is in the chain.  With the local data alone the list holds
  296: only C<Geo::Coder::Free>, which is given the C<region> hint (C<Geo::Coder::OSM>
  297: would put it in the Nominatim query).  Either way the list's cache answers what
  298: it has found before.  C<Geo::Coder::List> catches what a geocoder throws and
  299: asks the next one, so a throw does not end the request; a place whose lookup
  300: threw and found nothing is held (put in C<not_attempted>, not cached), because "not found" is
  301: remembered for good and an error is not an answer.
  302: 
  303: An injected C<geocoder> is asked for one C<geocode_many()> batch instead,
  304: requested with C<< on_error => 'undef' >>.  A value it refuses after the
  305: pre-filter is a miss; a backend that throws is still a throw, because nothing
  306: here wraps it in an C<eval>.
  307: 
  308: =item B<Tell a Nominatim that failed from a place it does not know.>
  309: 
  310: C<Geo::Coder::OSM> answers nothing in both cases.  The chain's log says whether
  311: Nominatim was asked, and its last response says whether it answered.  A place
  312: it failed on is held, not remembered as not found, and Nominatim is not asked
  313: again in that request: the rest are asked of the local data alone, and the ones
  314: it does not know are held too.  The page is told Nominatim's status line and how
  315: many places wait, never which.
  316: 
  317: =back
  318: 
  319: The counts the module returns add up, always.
  320: 
  321:     skipped + cached + attempted + not_attempted  ==  distinct
  322:     resolved + unresolved                         ==  cached + attempted
  323: 
  324: C<lookups> is the number of places that reached a geocoder rather than the
  325: chain's own cache.  For an injected geocoder it is the number that geocoder
  326: reports for the batch, which C<Geo::Coder::Free> 0.48 and later keeps lower than
  327: C<attempted> when a value is answered from a warm process cache.  It never exceeds
  328: C<attempted>.  C<online> is how many of them were asked of Nominatim.
  329: 
  330: =head2 The cache
  331: 
  332: A cache entry is a C<[lat, lon]> arrayref for a place that resolved, or the
  333: scalar C<0> for a place that was looked up and not found.  That C<0> sentinel
  334: prevents a column of unresolvable values from being retried on every page
  335: request.
  336: 
  337: The cache is passed per call and returned per call.  The caller's hashref is
  338: never modified: a request that dies part way through cannot leave a half-written
  339: cache behind.  The controller is responsible for persisting the returned cache,
  340: which keeps the C<model_dir>-inside-C<data_dir> guard in the one place that
  341: already owns it.
  342: 
  343: A previously stored cache is used even when the geocoder is not available.
  344: Places already resolved continue to be plotted; only new lookups are unavailable.
  345: 
  346: =head2 Without the geocoder
  347: 
  348: C<Geo::Coder::Free> and C<Geo::Coder::List> are recommended dependencies, not
  349: required ones.  They are loaded the first time they are needed, not at compile
  350: time.  C<Geo::Coder::OSM> and C<LWP::UserAgent::Throttled> are recommended too;
  351: without them the chain is the local data alone, and a request with places it
  352: did not know says so (C<warn_map_geocoder_local_only>).  When
  353: C<Geo::Coder::Free> or C<Geo::Coder::List> is absent or older than its minimum
  354: version:
  355: 
  356: =over 4
  357: 
  358: =item *
  359: 
  360: C<< $geocode->geocoder_available() >> returns C<(0, $reason)>.
  361: 
  362: =item *
  363: 
  364: C<resolve_column> and C<resolve_values> still return a complete result: all
  365: values are placed in C<not_attempted>, cached answers are still plotted, and
  366: the C<error_map_geocoder_missing> message explains the situation.
  367: 
  368: =item *
  369: 
  370: Nothing croaks.  The page renders with whatever the cache already holds.
  371: 
  372: =back

  436: =head2 resolve_column
  437: 
  438:     my $result = $geocode->resolve_column(\@rows, $column_name, %options);
  439: 
  440: Resolve one named column of a table.  C<\@rows> is an arrayref of hashrefs
  441: (the records from the data pipeline), and C<$column_name> is the key to look
  442: up in each row.
  443: 
  444: This is the main entry point for the map controller.  It runs the same
  445: resolution as L</resolve_values>, then adds per-marker row counts and the
  446: C<markers> list that a map rendering loop needs.
  447: 
  448: =head3 API SPECIFICATION
  449: 
  450: =head4 INPUT
  451: 
  452:     \@rows          => arrayref of hashrefs, required
  453:     $column_name    => non-empty string, required
  454:     cache    => hashref,            # optional; { value => [lat, lon] | 0 }
  455:     region   => two-letter string,  # optional; country hint for the geocoder (e.g. 'GB')
  456:     max      => positive integer,   # optional; max new lookups; default 500
  457:     lookup   => 0 | 1,              # optional; 0 asks nothing and lists what it would ask; default 1
  458: 
  459: C<\@rows> is the full record set as returned by the pipeline.  Rows that are
  460: not hashrefs produce an C<undef> cell, which is classified as skipped.
  461: 
  462: C<$column_name> must be a non-empty string.  It is used as a hash key; it is
  463: not validated against a schema, so a column name with spaces or special
  464: characters is accepted if the data uses one.
  465: 
  466: C<cache> holds the already-known answers for this column.  Entries are either
  467: a C<[lat, lon]> arrayref (resolved) or C<0> (looked up and not found).  The
  468: caller's hashref is never modified; the returned C<cache> key holds the
  469: updated copy.
  470: 
  471: C<region> is passed straight through to the geocoder as a country hint.  It
  472: is not derived from the Accept-Language header, because a language is not a
  473: country.
  474: 
  475: C<max> is counted in new lookups, not rows.  A cached answer costs nothing
  476: and does not count toward it.  Values held back by the cap go into
  477: C<not_attempted> and are not stored in the cache, so the next request picks
  478: them up.
  479: 
  480: C<lookup =E<gt> 0> plots from C<cache> alone and asks the geocoder nothing.
  481: The places it would have asked (up to C<max>, in first-seen order) are returned
  482: in C<pending>, and are counted in C<not_attempted> meanwhile.  A caller can then
  483: look them up one at a time with L</resolve_values>, saving each answer as it
  484: comes, which is how the map page shows its progress and can be cancelled.  The
  485: geocoder is still loaded, because its rule decides which values are places.
  486:

  488: 
  489: Returns a hashref:

 1875: 
 1876: =over 4
 1877: 
 1878: =item B<The cache sentinel 0 is not "false -- never looked up".>
 1879: 
 1880: A cache entry of C<0> means the place was looked up and not found.  An absent
 1881: key means it has never been attempted.  The module treats these two states
 1882: differently: a C<0> entry contributes to C<counts.unresolved> without
 1883: triggering a new lookup; an absent key enters the classification loop and may
 1884: reach the geocoder.
 1885: 
 1886:     # WRONG -- checking definedness misses the 0 sentinel.
 1887:     my $resolved = defined($cache{$place});
 1888: 
 1889:     # CORRECT -- use the internal _has_position logic.
 1890:     my $resolved = (ref($cache{$place}) eq 'ARRAY');
 1891: 
 1892: =item B<Pure-digit strings are skipped, not attempted.>
 1893: 
 1894: A value like C<'42'> fails C<valid_location()> and goes into C<@skipped>.  It
 1895: is never stored in the cache.  This is the correct behaviour for a row number
 1896: that ended up in the wrong column, but it surprises callers who expect every
 1897: non-empty value to be attempted.
 1898: 
 1899: =item B<The returned cache is a copy; the caller's hashref is never modified.>
 1900: 
 1901: Do not compare C<$cache_you_passed_in> with C<$result->{'cache'}> expecting
 1902: them to be the same reference.  The update is in C<$result->{'cache'}>.
 1903: 
 1904: =item B<resolve_column croaks when the column is absent; resolve_values does not.>
 1905: 
 1906: C<resolve_column> checks that the named column appears in at least one row.
 1907: If it does not, it croaks with C<error_map_loc_column>.  C<resolve_values>
 1908: does not do this check, because it receives values, not rows.
 1909: 
 1910: =item B<max counts new lookups, not rows or distinct values.>
 1911: 
 1912: A value already in C<cache> does not count toward C<max>, even if it was
 1913: looked up in a previous request.  A value skipped by C<valid_location()> does
 1914: not count either.
 1915: 
 1916: =item B<new() always succeeds; geocoder load failure is not a constructor error.>
 1917: 
 1918: You can always call C<new()> without checking whether C<Geo::Coder::Free> is
 1919: installed.  The load failure is deferred to the first call that needs the
 1920: geocoder, and is reported through C<geocoder_available()> and the
 1921: C<messages> array in the result, not through an exception.
 1922: 
 1923: =item B<cache_from_models and models_with_cache are class methods.>
 1924: 
 1925: You may call them on an instance for convenience, but the invocant is not used.
 1926: The pattern C<< Database::BI::Model::Geocode->cache_from_models(...) >> is
 1927: clearer.
 1928: 
 1929: =item B<An injected geocoder's batch receives on_error => 'undef'.>
 1930: 
 1931: A value an injected geocoder rejects after the C<valid_location()> pre-filter is
 1932: returned as C<undef> from the batch; it does not croak.  A backend that throws
 1933: an exception (a real database error, a network failure) still propagates
 1934: upward, because nothing here wraps the geocoder in an C<eval>.

 1939: 
 1940: =over 4
 1941: 
 1942: =item B<Place names (values in the location column)>
 1943: 
 1944: Passed to the geocoder as byte strings.  UTF-8 place names such as

 1953: with non-ASCII bytes are accepted.
 1954: 
 1955: =item B<Spec keys (the $spec_key argument)>
 1956: 
 1957: Used as hash keys in the model store.  Any byte sequence is safe; UTF-8 spec

 1965: locale.
