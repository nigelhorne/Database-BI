1#!/usr/bin/env perl
2# bi-alert -- Digest and threshold CLI for Database::BI
3#
4# Evaluates one saved analysis's measures, prints a digest to STDOUT, and
5# exits 1 when a threshold condition is crossed.  It makes no mail or network
6# call: delivery is the caller's job, which is what lets cron (or a wrapper
7# that pipes STDOUT into mail, a webhook or a ticket) decide what an alert is.
8# Scheduling is likewise cron's.
9#
10# A threshold that stays crossed is not news a second time, so --suppress gives
11# an (analysis, threshold) pair a throttle: the first crossing is announced, and
12# repeats inside the period are not.  The memory for that is one small JSON file
13# in the model directory, written only when --suppress is used (or once such a
14# file exists); with no --suppress the script behaves exactly as it always has
15# and writes nothing.  When the threshold clears, its entry is dropped, so the
16# next crossing alerts straight away rather than staying quiet about it.
17#
18# The end of a crossing is news as well, and --recovery announces it: the run
19# that sees the threshold clear prints THRESHOLD RECOVERED and exits 3, so a
20# wrapper that mails on a non-zero status mails the recovery too.  The state
21# file is what makes this possible, since an entry is the record of a crossing
22# that was announced: finding one is what tells this run that an incident has
23# ended rather than that a threshold was never crossed.  That is also why
24# --recovery keeps that file even with no --suppress to throttle, and why the
25# recovery is said once per crossing rather than on every run after it.
26#
27# Delivery is optional as well: --notify-cmd runs a command when, and only
28# when, something is announced, with the run's own text on STDIN and the
29# verdict in the environment.  That makes a cron line one command instead of a
30# shell wrapper around this one, and it keeps the rule the script has always
31# had -- nothing leaves the machine unless somebody asked it to.
32#
33# Usage:
34#   bi-alert --analysis <id> [--threshold <alias>:<op>:<value>]
35#             [--suppress <duration>] [--state-file <path>] [--recovery]
36#             [--notify-cmd <command>]
37#             [--model-dir <dir>] [--data-dir <dir>] [--dry-run]
38#
39# Exit codes:  0 = ok / threshold not crossed / crossed but suppressed
40#              1 = threshold crossed, and announced
41#              2 = error (bad args, analysis not found, data unavailable)
42#              3 = a crossing that was announced has ended, and is announced
43#                  as a recovery (--recovery)

460The digest goes to STDOUT and nothing leaves the machine until you say where.
461Pipe STDOUT into mail, curl or a ticket creator if the alert has to travel, or
462let --notify-cmd run that for you:

465           --notify-cmd 'mail -s "$BI_ALERT_SUBJECT" oncall@example.com'
466
467The command runs through the shell, exactly once, and only when something is
468announced: a crossing (exit 1), or a recovery with -r (exit 3).  A suppressed
469repeat, a threshold that is not crossed, an error and a --dry-run run it not at
470all, so it never says the same thing twice.  The announcement arrives on STDIN,
471and three variables say what it is:
472

474  BI_ALERT_SUBJECT       the verdict line, ready for mail -s
475  BI_ALERT_MESSAGE_FILE  the same text in a file, for a command that cannot
476                         read STDIN: curl -d @$BI_ALERT_MESSAGE_FILE ...

479would have been, but the crossing is not written to the state file: the alert
480has not reached anybody, so the next run announces it again rather than losing
481it for the whole period.

492
493  */5 * * * * cd /path/to/app && out=$(./script/bi-alert --analysis abc123 \
